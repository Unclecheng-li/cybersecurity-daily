门是账号自己开的，一分钟之后连开门的记录都没了

Aikido Security 命名 wfx-loot · 2026-11-10 起 · 无 CVE · 4,837 个账号 / 61,764 个仓库 没有 GitHub 平台漏洞 · 只靠偷来的写权限

这条放在最前面，因为它连一个漏洞编号都没有。

11 月 10 日中午开始，有人拿着 4,837 个被盗的 GitHub 账号，向 61,764 个仓库发起拉取请求。标题统一是 docs: dependency audit notes，来源分支统一叫 wfx-docs，内容看起来就是一份依赖审计笔记。这些请求的作用不是提交代码，是测权限：能建成功，就说明这个被盗账号对那个仓库有写权限。Aikido 报告发布时，92% 的探测请求还开着，说明绝大多数仓库主人根本没注意到。

写权限确认之后，投递只有三条路，都很普通：改一个已有的 GitHub Actions 工作流、在一个短命分支上新建一个工作流、或者在 package.json 的 postinstall 钩子里加一步。真正干的活是一个约 1,500 行的 shell 脚本。它拿的东西按类别列出来，基本覆盖了一家公司的全部钥匙。

它不止偷，还留后门。脚本用 GitHub 的 OIDC 令牌去换云上的短期会话，然后在权限允许的地方做两件事：在 AWS 建长期 access key，并把某个 IAM 角色的信任策略改成任何 AWS 账号都能扮演；在 Azure 给应用加一个以 wfx-ci- 开头的联邦凭据。这两类东西改密码改不掉，它们不是密码。

外传走 HTTP POST，打包成 tarball 送到两个攻击者控制的端点，后续样本改成走 Telegram。送完之后，它在一分钟内把提交回滚、把临时分支删掉、把工作流运行记录连同日志一起删掉。查的人打开仓库，看到的是干净的代码。只有编号会断：工作流的 run 编号是递增的，删掉一条就留下一个空档。这是这批攻击唯一稳定留下的痕迹，而且攻击者没打算留。

这几个数不能互相替代。收到探测 PR 不等于被攻陷，收到恶意提交也不等于脚本执行成功。真正坐实的是那一千八百多个跑起来并外传成功的。

被波及的账号里，有财富 100 强企业的员工、美国总务管理局、法国政府，还有 Nextcloud 的 nextcloud/docker 与 WebdriverIO。Aikido 说约 50 个账号看起来在 npm、PyPI、Go、crates 或 Packagist 上有发布权限，这件事的性质就变了：从偷密钥变成能往供应链里塞东西。已经确认被自动发布带出去的是 Packagist 的 digitalelvis/neuronai-studio 3.14.3，以及 Go 模块 github.com/onuragtas/docker-env 的 v1.0.278 和 v1.0.280。

口径要划清两处。第一，Aikido 明确说这次没有用到 GitHub Actions 自身的漏洞，StepSecurity 也是同样的判断，被盗的是账号。第二，它和 2025 年的 GhostAction 有重叠，但 Aikido 的原话是 "we don't attribute November to the same actor at this stage"，本期不合并成同一拨人。

为什么值得关注：这是"账号即边界"最干净的样本。全程没有一个 CVE，没有一个补丁能打。防守方要做的四件事都不在漏洞管理流程里：查 run 编号的空档、给 .github/workflows 设强制 code owner 复核、把 GITHUB_TOKEN 设成只读、CI 里用 npm ci --ignore-scripts。前两件是流程，后两件是配置，一件都不需要等厂商发版。

还有一句要记住：回滚提交不会把已经外传的密钥要回来，删日志只会让事后判断变得更难。看到探测 PR 而没法排除工作流跑过，就按已泄露处理，把工作流能碰到的每一样东西都轮换掉，再去翻 CloudTrail 和 Entra 的日志，找新建的 key 和被改的信任策略。

少了一行判断，密码这一栏就不起作用了

CVE-2026-129483 · Cyrus SASL 至 2.1.28 · CVSS 4.0 记 9.3 · 3.1 记 9.1 发 A 等于 N，共享密钥算成零

这条的技术含量不在利用难度，在于它错得极其具体。

Cyrus SASL 是认证的底座。它不是某个应用，是 IMAP、SMTP AUTH、LDAP 这些协议做认证时调用的那层库。SRP 是它支持的机制之一，特点是不用把密码传出去，双方各算一个共享密钥，对上了就算通过。

srp_server_mech_step2 里缺了一句判断：客户端发来的公开值 A，如果是模数 N 的整数倍，必须拒绝。

数学上这件事很直白。SRP 的共享密钥里 A 是要参与取模的，A 一旦取成 N 的倍数，取模之后整个式子归零。共享密钥变成 0，双方"对上"了。服务端不知道对面没有密码，它只知道算出来的密钥和自己算的一样。后果是三个：冒充任意已存在的用户、不需要知道密码、还能顺带拿到会话密钥，因为密钥是 0，攻击者自己知道。

为什么值得关注：第一，这是密码学实现里的经典失效模式，数学上不可能成立的输入没有被拒绝。凡是自己实现大数运算的协议库，都该拿这个当检查项。

第二，SRP 部署得少，但一旦部署就是"唯一的门"。这类组件的特点是上线之后没人再碰，不在资产清单前排，出问题时才发现它管着所有人的登录。

第三，处置很干脆，没有配置能绕，只能升级。CVSS 4.0 的 E:X 说明厂商自己也还没看到公开利用，这给了修复窗口，但不该用来把排期往后挪。

工具的名字没变，变的是它指向哪里

CVE-2026-110178 · IBM ContextForge MCP Gateway 1.0.0 至 1.0.11 · CVSS 3.1 记 4.1 S:C：影响越过了攻击者所在租户

分数只有 4.1，但 MCP 网关是 AI 基础设施里最容易被当成"中立管道"的那一层。

ContextForge 是 IBM 开源的 MCP 网关，GitHub 上叫 IBM/mcp-context-forge，Apache-2.0。它的作用是在多租户环境里统一注册、管理、代理工具、资源、提示词和上游 MCP 服务器。多租户是关键词：一个网关后面挂着多个团队的智能体。

问题在配置导入。/v1/import 支持 conflict_strategy=update，用来"同名就更新"。更新的时候，代码按名称和可见性去查已存在的公共实体，没限定租户，也没校验调用者是不是它的主人。批量注册里 _process_single_tool_for_bulk 的 update 分支直接赋值 existing_tool.url、existing_tool.headers、existing_tool.auth_value。更关键的一处是导入流程调 update_gateway() 时没有把用户身份传进去，于是网关更新路径上那道所有权防护被整条跳过。

结果就是：持有团队级 admin.import 权限的账号，一个 POST 就能覆写别的租户的公共工具、资源、提示词和网关的端点地址、请求头、认证凭据。

这个洞的性质不是"多了一段代码"，是"同名实体被换了指向"。

为什么值得关注：第一，巡检看不见这件事。名字没变，列表没变，权限没变，变的只是它指向哪个主机、带哪个请求头、用哪把凭据。人工核对名单是核不出来的。

第二，被换掉的是凭据，不只是地址。下游智能体把数据送到攻击者主机的同时，也把那把凭据交了出去，而这个凭据原本是网关自己持有的。

第三，S:C 就写在这里：影响范围越过了攻击者自己所在的租户。4.1 分是按 PR:H 算的，可它要求的是"团队级"，而在真实部署里团队级权限往往是最容易拿到的那一档。

处置建议只有一句：MCP 网关这类组件，现在大多不在安全评审清单里，先把它加进去。

CVE-2026-97799（音频服务签名校验）· CVE-2026-116714（AppX 部署授权）· 均 7.8 26H2（10.0.26300.9457）实测 · 不需用户配合

该在五年前删掉的卡号，还在库里没加密

良品计画（MUJI 母公司）· 11-12 记者会 · 无 CVE · 109 万条 / 约 44 万名会员 34.5 万张卡仍有效 · 2021 年 7 月就该删

这起事件的分量不在攻击，在留存。

10 月 30 日，良品计画披露 MUJI App 遭未授权访问，最多约 2726 万条客户信息可能泄露。两周后的 11 月 12 日，社长清水智在东京开记者会道歉，说后续调查发现另有约 109 万条 MUJI Card 会员数据可能被访问，涉及约 44 万名会员的完整信用卡号、会员识别码与出生日期。

《读卖新闻》等日本媒体点出的那个问题，比数字更值得抄下来：公司没有对客户信用卡号做屏蔽保护。而按规定，这批数据本应在 2021 年 7 月系统升级、停止用卡号识别会员之后就删掉，没有落实。也就是说，从 2021 年 7 月到今天，这批卡号在库里躺了五年多，没删、没加密、没遮蔽。

为什么值得关注：第一，这条把"泄露规模由谁决定"讲清楚了。规模不只由攻击者决定，还由企业手里还留着什么决定。同一次入侵之所以变成一起信用卡事件，是因为五年前该删的字段还在，而且没遮蔽。

第二，日本这一轮的密度值得单独看。日本个人信息保护委员会统计，本财年（2026 年 4 月起）泄露约 2.6 亿人次，接近全国人口两倍；MM 综研统计到 10 月底是 3.76 亿条，是去年同期的 7 倍以上，仅 10 月就约 1.85 亿条，百万级事件 45 件为近五年最多。这是系统性问题的密度，不是单家公司的失误。

第三，处置动作里最便宜的一条，恰好是这次没做的那条：做一次数据留存盘点，把"业务已经不用了但还在库里"的字段列出来，先删，再谈加密。加密要改系统，删字段只要一次评审。

问题在 labeled-response 模块。IRCv3 的 label 是客户端给请求打的标记，服务端要在回复里原样回显。这个模块在回显前没有转义 IRC 协议的分隔符（CWE-140，红帽的跟踪条目归成 CWE-93 CRLF 注入）。攻击者在 label 里塞进换行，这段内容跨服务器链路时被对端当成一条新的服务器间命令执行。服务器间链路默认互信，于是"能加入这个网络的普通用户"，直接变成了"服务器"。

触发条件是两台及以上互联服务器。单机不成立，但生产 IRC 网络基本都是互联的。

发现过程值得单列。公告原话是 "During an internal audit, with the help of AI, several important security issues were found"。这批洞是一次AI 辅助的内部审计挖出来的，一次九个。这跟"AI 找出来的洞没人修"是两件事：这一次修复当天就到了，第二天就被利用了。

处置有三步，顺序不能反。第一，升到 6.2.7.1；不能立刻重启的先上 hot-patch ./unrealircd hot-patch bundle-20261107（适用 6.0.0 至 6.2.7，不停机），再用 ./unrealircd module-status | grep labeled-response 确认。第二，只 rehash 不够，要 ./unrealircd upgrade 真正重启，才会用上打过补丁的模块，这一步是这类热补丁最常见的失效点。第三，5.x 加 blacklist-module "labeled-response" 并重启（不是 rehash），同时排迁移。

作为临时护栏，IRCOp 可以加一条 SPAMFILTER 正则拦非法 label，但它只在所有互联服务器都是 6.0.4 及以上时才保护整个网络。

为什么值得关注：第一，这是"补丁发了但机器没变"的标准案例。修复版 11-07 就发了，KEV 11-13 才收，今天到期。中间这九天里，装了就完事的和装了但没重启的，处境完全不同。

第二，C:N 这个分数读法要留意。字面上机密性无影响，但一个能拿到服务器级命令的人，后面的窃听与横移只是他愿不愿意的问题，不是能不能的问题。按分数排期会把它排到队尾。

第三，这条同时给了两个信号：AI 参与内审确实能挖出十五年没被发现的问题；而挖出来之后，从披露到在野利用是两天。

普通用户 只要能加入这个网络 label 里塞换行 回显前没转义 跨服务器链路 被当成新命令 服务器间默认互信 直接拿到服务器权限 11-07 修好 11-09 已在被利用 只 rehash 不生效 必须 upgrade 重启 今天到期 配置没改的仍是别人的

7. Cisco BroadWorks 那条 XXE 进了 KEV，同一天还有两条 Cisco 在被利用

CVE-2026-20320（CVSS 7.5，AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N）是 BroadWorks 的 Open Client Interface（OCI）XML 解析器默认允许外部实体解析，未认证的远程攻击者给 OCI-P 服务发一条构造好的 XML，就能以 BroadWorks 用户的权限读服务器上的敏感文件。8 月就发了修复，11 月才进 KEV。同批还有 CVE-2026-111793（Openwave Messaging Webtop，4.3，认证后，来源是 JVN 转述开发者"已观察到利用"）。Cisco 另有两起在野：CVE-2026-20127（Catalyst SD-WAN，10.0）与 CVE-2026-76418（ASA/FTD，8.6）。联邦整改期限 11-24。该活动的归因与命名部分本期不转述，只记 CVE 事实与 KEV 状态。

8. Apache Shiro 的 LDAP 认证缓存，开着就等于任何密码都能过

CVE-2026-129349，CVSS 4.0 记 9.1，影响所有版本至 3.0.0。条件是 DefaultLdapRealm（或 JndiLdapRealm）开了 authenticationCachingEnabled=true，这不是默认值。开了之后，一个用户成功登录过一次，之后他用任意密码都能再登进来：缓存命中会跳过 LDAP bind，而 DefaultLdapRealm 默认装的是 AllowAllCredentialsMatcher，它接受任何凭据。修在 3.0.1（不再默认装这个 matcher）。临时办法是关掉认证缓存，或配一个真的会校验的 matcher。这类洞只在"为了性能打开的那个开关"之后存在，而那个开关常常是某次性能优化时开的，没人记得。
