1 PoC 公开

镜像里的 rootfs 是一个指向 / 的符号链接，主机就交出去了

08-21 NVD 收录 · 11-06 GitHub 一次性公开六份公告含 PoC · 修复已在 7 月落地 CVE-2026-48769 / 48749 等六条 · CVSS 3.1 9.9 · CWE-20 与 CWE-73 · 不在 KEV

11 月 6 日，GitHub 上一次性公开了六份针对 Canonical LXD 与 Linux Containers Incus 的安全公告，全部给 CVSS 3.1 9.9，向量统一是 AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H。这个向量里最该看的是 S:C——范围变更：容器管理层里的一个缺陷，最终打到的是它下面那台主机。六份都不在 KEV 里，CISA 给它们附的 SSVC 决策记录只把其中三条标为 poc。

时间线本身就值得注意：NVD 在 8 月 21 日就收录了这批 CVE 记录，而细节与可用 PoC 到 11 月 6 日才一起放出来。补丁其实早就有——LXD 的 5.0.7 LTS 与 5.21.5 LTS 在 7 月 1 日发布，Incus 修在 7.2.0。三个月里风险等级没变，可利用性变了。

CVE-2026-48769 把"顺序反了"写在了代码里。Incus 支持 source.type=url 的镜像导入，远端服务器在 HEAD 响应里用 Incus-Image-Hash 头告诉客户端"这个镜像的 SHA-256 应该是多少"。守护进程拿到这个字符串之后，没有检查它是不是合法的 64 位十六进制，直接当成指纹变量 fp，用 filepath.Join(destDir, fp) 拼路径。Go 的 filepath.Join 会调 filepath.Clean，把 .. 段解析掉——于是值 ../../../../etc/cron.d/payload 就拼成了主机上的 /etc/cron.d/payload。

路径拼好，os.Create() 立刻打开文件，开始把 GET 的响应体流式写进去。哈希校验发生在整个响应流结束之后。攻击者只要让自己的服务器把响应挂住不关，清理函数就一直不执行。PoC 里挂的是 90 秒，这个数字是算过的：cron 每 60 秒扫一次 /etc/cron.d/，挂 90 秒保证在扫描窗口内被读到并执行。等连接关掉，守护进程算完哈希发现对不上、去 unlink 的时候，命令已经以 root 跑完了。

CVE-2026-48749 走的另一条路，代价更低，不需要守护进程能出网，只要能把镜像包导进来。构造方式很朴素：先做一个合法镜像目录（最小的 metadata.yaml 加一个空的 rootfs/）打成 tar，然后删掉本地 rootfs/、创建一个指向 / 的同名符号链接，用 tar --append 追加进同一个包——tar 允许同名成员，解包时后一条覆盖前一条。导入、incus init 建一个不启动的实例，然后对这台停着的容器做文件操作，特权辅助程序 forkfile 解析 rootfs 时不做限制，直接 chroot 进主机的 /。file pull 读 /etc/shadow，file push 写 /etc/crontab 或 /root/.ssh/authorized_keys，都是 root。

修复也是两段式：对 rootfs 与 templates 做 os.Lstat() 检查、符号链接直接拒，再改用 Go 的 os.OpenRoot / os.Root（底层是 Linux openat2 的 RESOLVE_BENEATH）把后续操作关在实例目录里，顺带把 TOCTOU 也堵了。受影响区间：LXD < 4.0.11 / < 5.0.7 / < 5.21.5 / < 6.9.0，Incus < 7.2.0。

值得关注的原因：

  • 受影响人群不是"用旧版本的人"，是"用 LTS 的人"。LXD 5.0 LTS 与 5.21 LTS 的用户天然不升级，而 5.0.7 与 5.21.5 是 7 月才发的点版本。snap 装的、发行版仓库自带的、把代码 vendor 进自己项目里的三类部署，得分别核。
  • 检测基本没法从主机侧做。守护进程的日志会显示导入成功或恢复成功，和一次正常操作完全一样——它在动手那一刻之前都相信内容是真的。有用的工作得往前挪：谁能往项目里加镜像源、谁能推快照，这个名单要收窄。
  • "客户机对象被信任得太早"这个模式今年在 hypervisor 逃逸上反复出现。只要产品线是"用别人的镜像、快照、模板来建东西"，就值得按这个模式自查一遍：先验后用的顺序有没有写反。
镜像头返回 Incus-Image-Hash 值未校验是否为 64 位十六进制 filepath.Join 解析出镜像目录 os.Create 打开主机文件并写入 攻击者挂住连接 90 秒 cron 60 秒窗口内执行 连接关闭才校验哈希

EPSS 也帮不上忙。抽查几条都在 0.6% 上下（约 52 百分位），都不在 KEV，没有公开 PoC。低 EPSS 在批量披露场景下解释力很弱——它衡量的是历史同类漏洞的利用频率，不是这 247 条里哪一条明天会被人捡起来。

值得关注的原因：

  • 247 不是一个产品有 247 个洞，是把历史欠账一次结了。里面大量是长期存在的代码质量问题——注入、路径遍历、属性控制、租户隔离——过去没集中报。批量披露的处理成本和单条完全不同：拿到一张 247 行的表，实际上无法逐条评估。

  • 实操上别试图读完全部 247 条。按 PR:N（不需要凭据）先筛一遍，再把 S:C 与租户隔离相关的挑出来，剩下的按季度排。

3 已在公开仓库

点了"别再问了"，密码就被原样存进项目里那个 JSON

11-05 Apiiro 研究 · 104,185 份公开副本 · 63 家组织 · 1 家确认密钥仍然有效 2,539 个密钥 / 1,994 个仓库 · 无 CVE · 产品设计行为

Claude Code 执行 shell 命令前会请求批准。选 "Yes, and don't ask again" 时，它把那条命令的完整字符串——包含里面的密码、令牌、连接串——作为 allow 规则写进项目目录下的 .claude/settings.local.json。它不清洗参数，因为规则本身就是命令原文。

它确实试过把这个文件留在本机：在 git 仓库里创建时会把它加进用户级全局 git ignore。但这层保护漏掉三种场景——文件夹先建、后来才变成仓库；别人克隆到另一台机器；文件已经被提交过。项目自己的 .gitignore 里从来没有这条规则，保护不跟着项目走。更麻烦的是 Claude 自己会提交它：在追踪到的 1,105 个含真实密钥的仓库里，有 539 个是"一次 Claude 作为共同作者的提交改动了这个文件"，提交记录点名了从 Sonnet 4.5 到 Opus 5.5 的每一代模型。

规模：扫到 104,185 份公开副本（分布在 103,617 个公开仓库），其中 1,122 份至少含一个真实密钥，去重后 1,379 个。再加上 git 历史、团队共享的 .claude/settings.json、agent 聊天记录，总数是 2,539 个密钥、1,994 个仓库、63 家组织。历史版本里已经不在当前文件中的密钥有 734 个，74 个仓库的凭据被 fork 复制到了 211 个副本。

泄露的构成：379 个数据库密码、122 个 Supabase service-role 密钥、103 个 Supabase 账号令牌、43 条 SSH 凭据（包括直接写在 sshpass 命令里的 root 登录）、42 个 GitHub / GitLab / npm 令牌、23 个 AWS 密钥、6 个私钥。Apiiro 特意点了两个案例：一家数据库厂商自己的管理员级云密钥，和一个病历数据库的 owner 密码。

最有价值的是漏报数据。同一批 1,122 个文件：Gitleaks 命中 564 个，TruffleHog 命中 643 个，两个都没命中的有 215 个。原因很具体——以 PGPASSWORD=、sshpass -p、mysql -p 形式出现的密码没有可识别的厂商前缀。结构化密钥检测和命令行上下文里的凭据识别，是两种能力。还有一层反讽：Shai-Hulud npm 蠕虫在受害机器上跑的就是 TruffleHog，那个能命中 643 个文件的工具同时也是攻击者的批量收割工具。

值得关注的原因：

  • 这是"便利性设计"直接生成了凭据泄露管道。不是开发者手滑粘贴，是产品为了少问几次把命令原文落盘。审批记忆是刚需，但实现方式有多种：存命令模式而不是完整命令、存到不可提交的位置、自动写进项目 .gitignore。Apiiro 对比了 16 个编码 agent，Claude Code 是唯一一个默认把完整已批准命令持久化到项目文件的。
  • 响应顺序必须是先轮换、再清理。删当前文件不影响历史里那 734 个旧密钥，也不影响 211 个 fork 里的副本。先轮换，再 git rm --cached、加 .gitignore、git filter-repo 清历史、请 GitHub 清缓存视图、通知能联系上的 fork 所有者。
  • .claude/ 这类目录应当按"存密钥的目录"对待。把 agent 配置目录加进全组织的 .gitignore 模板，并把扫描扩展到"命令里的密码"这种形态——215 个两个主流工具都看不见的文件，说明现有覆盖率在这类资产上是空的。
  • Anthropic 的回应是缺失的。报道提到 2025 年 8 月的一份 bug 报告被自动化机器人以 not planned 关闭，随后四份相关报告也被机器人无回应关闭；截至报道发布未公开回应。

4 供应链

42 个仓库被同一个蠕虫拿下，13MB 封装器让搜索和 API 都看不见它

11-06 JFrog 研究成稿转述 · 触发点从"运行代码"挪到"打开文件夹" testmetest 蠕虫 · Bun 1.2.18 · 四个常用检测手段同时失效

JFrog 定位到 42 个被接管的 GitHub 仓库，作用是给同名 npm 包做"掩护项目来源"——仓库是真的、提交历史是真的、README 是真的，只有里面被塞了东西。塞进去的清单本身就值得抄下来做自查项：.github/init.js（Actions 侧发布器）、.claude/settings.json（SessionStart 钩子）、.gemini/settings.json、.cursor/mcp.json 与 .cursor/rules/setup.mdc、.vscode/tasks.json（文件夹打开任务）、异常的 composer.json 与 Makefile 钩子、带 skip-checks:true 的提交，以及短命的 chore/ci-*、deps/upd-* 分支。

一位分析师的评价被反复引用：.claude/settings.json 已经成了新时代的 autorun.inf。

最值得记的细节是文件体积伪装：那些封装器约 13MB，有两个作用——超过 GitHub 代码搜索的索引上限，也超过内容 API 能返回的范围，所以早期分析明明找到了钩子文件，却把载荷文件误判成空文件；同时让"用 GitHub 搜索查一遍"这种自查方式直接失效。JFrog 的建议很直白：不要依赖代码搜索或内容 API，得直接枚举仓库文件树。攻击者显然读过检测工具的文档。

载荷是一个 npm 蠕虫。加载器对一组字符码数组施加逐版本变化的凯撒密码变换，解出一个 AES-128-GCM 加密的阶段二，然后去找或下载 Bun 1.2.18；按版本不同，解密内容要么被管道送进 bun run，要么写进临时的 .b-* 目录、执行完删掉。完整载荷收集凭据、污染仓库和 CI 配置、通过包注册表传播。被激活的 ci.js 里，发布程序被设计成在 GitHub Actions 里跑，用 npm 令牌或可信发布机制生成更多恶意版本——包分发和仓库入侵形成闭环。

另一个细节更麻烦：这个原生插件本身不携带载荷，并且拒绝在 CI 系统、容器环境、小型虚拟机、调试器监控状态下运行；Windows 上检测到 Wireshark 或 Process Monitor 在跑，它也会停。扫描工具看到的是占位程序，开发者的笔记本上跑的才是真的。

值得关注的原因：

  • 触发点从"运行代码"搬到了"打开文件夹"。十年来供应链威胁模型都假设恶意代码在安装或执行时运行，防御建在 install 钩子和构建脚本上。这次植入的是 AI 编码工具的会话钩子与文件夹打开任务——开发者在受支持的工具里打开一个项目，载荷就跑起来了。而这个动作今天已经不算"执行代码"。
  • 开发者的笔记本握着王国的钥匙。GitHub 令牌、npm 令牌、云密钥、AI 服务商凭据都在同一个用户目录下。攻击者找到的不是新漏洞，是新的收割点。
  • 这一类感染只能按"已被入侵"处理。装过完整蠕虫版本的主机，应立即撤销并轮换 GitHub、GitLab、npm、PyPI、RubyGems、云服务、SSH、Vault、Kubernetes 以及 AI 服务商的全部凭据，再审计受影响身份能访问的所有仓库。
  • 自查方式必须换。搜索引擎查不到、内容 API 查不到、装时扫描看不到、沙箱里运行不起来——四个常用手段全部失效，剩下的办法只有枚举文件树。

5 数据泄露

一个半月一亿一千万条，和一份 100 亿日元的预算

11-08 07:00 国家安全部通报 · 11-06 日本敲定中央抗黑客团队 1.15 亿条 · 近三成大企业承认 · 成因三条与建议三条

11 月 8 日上午，国家安全部微信公众号发布《仅一个半月，就有上亿条信息泄露！》。事实层面：仅 2026 年 9 月至 10 月中旬，日本已获悉的信息泄露量超过 1.15 亿条，其中大型软件企业逾 2,200 万条客户记录遭窃，某知名餐饮品牌上千万条会员信息外泄，物流巨头同样未能幸免；一项最新调查显示近三成日本大企业承认曾发生泄露或疑似泄露。

成因归为三类，措辞很实。数据管理不规范：多数涉事企业长期无差别采集、超期留存用户信息，造成大量数据长期堆积，形成高风险的"数据宝库"，系统老旧、漏洞修复滞后、后台权限粗放进一步放大隐患。人员安全意识薄弱：误发邮件、未经核实即提供信息、弱口令，文中有个例子——某员工因误以为邮件来自合作伙伴且情况紧急，未电话核实就把敏感信息给了出去。供应链安全失守：多起案例里泄露不是因为自家系统被攻破，而是外包服务商、第三方平台防护不足、运维松散，原文明确供应链攻击已成为网络攻击的优先路径之一。

风险给了三条：侵害个人权益（精准诈骗、定向骚扰、身份冒用）、冲击行业秩序（投诉纠纷、合规处罚、信任危机）、危害国家安全（海量民生数据与行为轨迹可能被境外间谍情报机关用于用户画像、行为分析、精准渗透）。建议也是三条：分类分级管理、严控采集范围与存储时限、常态化清理冗余过期数据、定期漏洞扫描与权限清查与日志审计；杜绝弱口令、共用账号、权限粗放、私连外网；建立第三方服务商的安全准入、动态考核、定期排查与退出机制。

日本那边的动作是另一半。政府决定投入 100 亿日元（约 4.2 亿元人民币）组建中央抗黑客团队，首相高市早苗 11 月 6 日召开网络安全阁僚会议，指示修订《网络应对能力强化法》。她的表述是"就在此刻，未经授权的访问和数据泄露事件正在发生"，要求"调动政府的一切资源"。团队将用 AI 对抗黑客、检测系统薄弱环节，与会者用电影《捍卫战士》作比喻，把它定位成精锐部队。10 月倒下的清单：Times 集团约 660 万条、汉堡王约 1,118 万条、GMO 互联网集团 10 月 24 日证实被勒索 100 万美元并有客户资料外泄。日本当局分析后认为，这些企业委托的网安公司在防护措施上存在漏洞——和国家安全部说的"供应链安全失守"是同一个判断。

值得关注的原因：

  • "1.15 亿条"的成因不是某一次高明攻击，是长期的采集与留存习惯。不采就不会丢，不长期留就不会一次丢一亿条。数据最小化在这里不是合规话术，是直接的损失上限控制。
  • 供应链那一句是两份独立材料的共同结论。一边是中国国家安全部，一边是日本当局对本国企业的分析，都指向外包与第三方平台。但企业的第三方安全评估普遍还停留在问卷层面。
  • 监管口径正在从"企业合规"往"国家安全"抬。这篇的落点是"数据安全是国家安全的重要组成部分"和 12339 举报渠道，泄露事件的后果评估里要加进这一层。
  • 100 亿日元买的是响应能力，不是预防能力。中央团队、AI 对抗、漏洞检测都是事后与事中的能力。真正的下降只能来自减少留存和收紧第三方，而这两件事在任何国家都比建一支团队难。
6 PoC 公开

只核了"你有没有权改自己的项目"，没核"这个文件是谁的"

11-07 细节与 PoC 一起公开 · 1.20 至 2.18.0 全部受影响 · 尚无在野 GHSA-8qqw-wm58-45v7 · CVSS 9.9（开放注册时 10.0）· WebSocket 7.7

Penpot 是开源的设计协作工具，后端是 Clojure。攻击面在 import-binfile 这个 RPC 路由上，缺陷类型是 CWE-862（缺少授权检查）加 CWE-639（通过用户可控键做授权绕过）。

调用这个路由时，服务端只检查了调用者对"自己那个项目"有没有编辑权，从来没检查 file-id 参数指向的文件属于谁。于是攻击者把受害者的文件 UUID 填进去，后端就进入原地覆盖模式：数据库查询只按 ID 取那个文件，不带团队或项目条件，然后把攻击者的数据直接写进受害者的数据库行，同时把文件的 project-id 改成攻击者自己的项目。

结果有三层。受害者失去设计稿，而且用不了恢复功能——行是被改写，不是被删除。攻击者成为新所有者，可以读、改、导出。如果被劫持的是共享库，其他团队所有引用它的文件在下一次同步时会拉进攻击者的改动。配套的 WebSocket 缺陷单独给 7.7：subscribe-file 与 subscribe-team 两个处理器都没有对目标 UUID 做访问检查，任何已登录用户只要知道文件或团队 UUID，就能实时看别人的编辑流、角色变更、光标移动。

受影响区间是 1.20 起（2025 年 7 月引入 file-id 导入功能）到 2.18.0 之前的所有自建部署。修复在 2.18.0，具体两个 PR：10994 从 import-binfile 的 schema 里删掉不安全的 file-id 字段，11069 给所有 WebSocket 文件与团队流加上严格访问检查。临时缓解只有三件事：关闭开放注册、限制网络访问到可信人员、检查数据库日志里有没有跨团队的 project-id 异常变更。

值得关注的原因：

  • 这是"两段式授权"缺失的教科书样本。检查了"你能操作这个项目"，没检查"这个对象属于你能操作的项目"。凡是接口里同时出现容器 ID 和对象 ID 的地方，都该问一遍：第二个 ID 的归属核了吗。
  • 设计协作工具的资产不是数据，是文件本身。共享库是一层层引用的，劫持一个库能污染一整片文件。这种"供应链式的内部污染"在传统 DLP 里基本没覆盖。
  • 自建部署的升级率是真实风险点。官方云会自己升，Docker 和自建实例不会。细节和 PoC 在 11 月 6 日到 7 日一起放出来，正好是自建用户最该动手的窗口。
  • 1.20 到 2.18.0 跨度接近一年。一个默认开启的功能从引入到修掉，中间所有版本都受影响——这类"功能引入即缺陷引入"的情况，版本区间往往比想象的长。
攻击者登录 Penpot 服务端只核自己项目的编辑权 未核 file-id 的归属 原地覆盖受害者的数据行 project-id 改为攻击者项目 共享库被污染并同步扩散

8. ForgeRock OpenAM 一次性 18 条，含一条 CVSS 4.0 满分

NVD 在 11 月 8 日收录了一批 OpenAM 的 CVE，共 18 条，全部修复在 16.1.4。其中 CVE-2026-123551 的 CVSS 4.0 评分为 10.0（向量里 VC/VI/VA 与 SC/SI/SA 全为 H），描述为未认证攻击者可获取敏感信息。技术含量较高的几条：123536 与 123537 都是 SSRF——前者允许管理员（含被委派的 realm 管理员）通过联邦相关配置让服务器抓取任意 URL，后者允许注册 UMA 资源集的一方通过未校验的 scope 描述 URL 触发内部请求；123538 更直接，OpenAM 不校验 SAML 1.x 断言或响应的签名者是否就是它声称的 issuer，只要签名来自 OpenAM keystore 里的任意一张证书就接受。SAML 的信任模型建立在"issuer 字段"与"签名证书"的绑定上，这个绑定不校验，keystore 里任何一张证书都能冒充任何一个合作方。做 SSO 集成的团队值得单独核一遍自己的 IdP 配置。
