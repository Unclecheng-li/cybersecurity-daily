LiteLLM 1.107.0 被投毒：一个连字符，把整条发布流水线指向了别人的仓库

2026-10-21 11:39 UTC 上线 · 13:20 PyPI 隔离 · 13:53 镜像下架 周下载约 2,300 万 · 四个 Docker 标签同时被污染 · 2026 年第二次

2026-10-21，PyPI 上发布了 litellm==1.107.0，同时被推到 LiteLLM 官方四个 Docker 标签。这个包会在任何 Python 进程启动时自动执行一个凭据窃取器——哪怕你从来没 import 过 litellm。整条链上唯一被动手改的东西，是发布时指向的那个仓库比真名少一个连字符。

窗口只有两小时。按 Datadog Security Labs 的 UTC 时间轴：11:39 恶意版发布到 PyPI；13:20 PyPI 隔离该版本；13:53 受影响的 Docker 镜像被移除。Upwind 记录约 90 分钟——差别在于"PyPI 隔离"与"镜像删除"哪个算结束。这不是"挂了一整天没人管"，而是两小时内被发现并处置；问题在于那两小时正好覆盖了 CI 的构建窗口。

每一层完整性证据，都是真的。这是今天最值得记住的一句：

  • v1.107.0 的 git tag 里没有恶意代码——恶意代码不在 tag 里，构建时才从别处拉进来
  • 提交上的 GitHub 签名是 Verified 绿标，提交通道本身合法
  • 镜像带 SLSA 溯源，指名了真实 builder 与"真实源仓库"——那个源仓库就是 Berri-AI/litellm
  • 发布走的是 LiteLLM 官方 PyPI 项目与官方 Docker 仓库

攻击者没有"突破"流水线，他们让流水线为他们构建。手法是：三名工程师账号的 GitHub CLI OAuth token 被盗（初步原因未公布），这三份凭据被用来启动 LiteLLM 的私有发布工作流、批准这次运行、并在事后删除证据；被构建的源码来自恶意 fork Berri-AI/litellm（真实组织是 BerriAI）。溯源信息没有撒谎，它只是如实记录了错误的仓库名。

落地文件（site-packages）作用
cook.pth（12 字节）内容只有一行 import cook；Python 启动时自动执行 .pth
cook.py（22,252 字节）凭据窃取器（自称 privcollect），zlib + base64 包裹
sitecustomize.py（25,509 字节）二阶段 RAT：每小时去固定 GitHub 仓库取域名，再下载执行代码

因为 .pth 与 sitecustomize.py 是解释器级的自动加载点，这个虚拟环境里任何一次 python、pip 调用都会重新触发它。删掉 litellm 目录不算清理，反而会在下一次 pip 时再中一次——这是本次处置最容易做错的一步。

它偷的东西，是按"这是一个 AI 网关"写的。常规项之外（AWS / GCP / Azure 含实例元数据、K8s / Docker / Vault / Terraform、SSH 与 GPG 私钥、.git-credentials / .npmrc / .pypirc、浏览器解密后的密码与 Cookie、/proc/*/environ），有两条是专门为这个包设计的：一是 AI 工具链凭据——Claude、Codex、Gemini、Qwen、Cursor、Windsurf、Kiro、VS Code MCP、Copilot、Hugging Face token，这是第一份把"AI 编码助手登录态"明确写进清单的窃取器；二是 LiteLLM 自己的数据库——只要有 DATABASE_URL，它就拉起 Prisma 去 dump LiteLLM_CredentialsTable 与 LiteLLM_ProxyModelTable，那两个表就是整家企业经由 LiteLLM 转发的全部上游 provider key。还有一个细节说明写载荷的人在验货：云元数据的角色凭据会先经 STS GetCallerIdentity 验证有效再外传，不白拿。

外传与二阶段都用了"看起来像官方"的地址。数据发往 www.litellm.dev/healthcheck——.dev，不是项目真正的 .ai；真站 2023-08-07 注册、在 GoDaddy、四把注册商锁全开，仿冒域名是 2026 年新注册。抓包能证明"连过"，但拿不到内容：AES-256-CBC，密钥用 RSA-4096-OAEP 包裹。二阶段指向 raw.githubusercontent.com/letters9813/pythonclient-test/main/domain.txt，该文件只放过测试值，因此未观察到二阶段载荷真正落地——这是运气，不是设计。

容器那条线更糟：四个标签一起指过去。受影响的除了 PyPI 1.107.0，还有 GHCR 与 Docker Hub 的 v1.107.0、latest、main-latest、main-stable。结果是：compose 文件里写着 litellm/litellm:latest 的人，没有任何机会"跳过 1.107.0"——他没有选版本，是版本选中了他。

处置顺序不能反：① 手动删掉 site-packages 里的 cook.pth、cook.py、sitecustomize.py（删 litellm 目录不够）；② 回退到 litellm==1.106.2；③ 在干净机器上轮换全部凭据，不是在被污染的机器上改密码；④ 查日志，并查 /tmp/.pc_once_72129118c59f5636c0bb 与 /tmp/remote_code_loader.lock 两个落地痕迹。

这是 LiteLLM 2026 年第二次供应链事件。上一次是 1.82.7 / 1.82.8，Datadog 归到 TeamPCP 活动（经 Trivy 的 CI/CD 流水线偷到 PyPI 发布令牌）。两次之间目前没有建立关联。

值得关注的原因：供应链攻防的战场已经从"污染源码"移到"决定这次构建从哪儿取源码"，而多数团队的检查清单还停在源码与产物两端。今天这条链上，tag 是真的、提交签名是真的、SLSA 溯源是真的、发布渠道是真的——四个真信号指向一个假来源。而攻击者挑得很准：一个 AI 网关的数据库里，装着全公司所有模型的 key。三条最便宜的加固：把发布工作流锁死到白名单仓库（而不是"任何有权限的 fork"）、把开发者 CLI token 当生产密钥管、在任何镜像里禁掉 latest。

GitLab CVE-2026-110264：满分 10.0、未认证、回溯到 2014 年的 7.0，而且这是同一个洞一个月内第四次

2026-10-21 发版 · 一次修 11 个问题 · 七个分支同时出补丁 CVSS 3.1 10.0 · CWE-190 整数溢出 · 不在 KEV · 无公开 PoC

GitLab 在 10-21 的例行安全发版里修了 11 个问题，其中 CVE-2026-110264 是 CVSS 3.1 满分 10.0：未认证远程攻击者可让服务器在编译一个精心构造的正则时发生整数溢出，进而执行任意代码。受影响范围回溯到 GitLab 7.0（2014 年），约十二年。

先划清一件事：这不是"又发现一个新洞"，是"上次没补干净"。同一个研究者（化名 joaxcar，经 HackerOne 报送）一个月内在 GitLab 的正则引擎上打出了第四个 RCE：9-23 修 CVE-2026-93577 与 CVE-2026-89078（均 9.9，需登录，只到 19.2 之后）；10-12 修 CVE-2026-97229（10.0、未认证，修在 19.2.8 / 19.3.5 / 19.4.2，10-14 期已报过）；10-21 修 110264（10.0、未认证）。关键一句是：97229 只补到 19.2 之后。所以九天前刚升到 19.2.8 把自己"修好"的实例，今天又在 110264 的范围内——因为 110264 修在 19.2.9 / 19.3.6 / 19.4.3 / 19.5.1 上。

根因在别人家的编译器里。出问题的是 Onigmo——Ruby 内置的正则编译器，GitLab 把它打进自己的包并自行打补丁。于是"缺陷存在于该引擎出现过的每一个版本"，而它从 7.0 起就一直在。

四个回移版本比正常支持线低两级。GitLab 的政策只覆盖当前版与之前两个月度版（19.5 / 19.4 / 19.3），18.11、19.0、19.1、19.2 属于"仅对严重问题破例"——这一条本身就是严重性的旁证。

最难受的地方：没有 workaround，也没法自查。GitLab 只说"在某些条件下"，没说什么条件，于是你无法通过检查自己的配置来证明"我不在范围内"，只能升。目前没有公开 PoC、不在 CISA KEV、GitLab 称未见利用迹象。同批还有两个值得注意：CVE-2026-15723（8.2），在管理员同时开启 SAML 与 LDAP 自动关联时，任意登录用户可无交互接管一个 LDAP 后端账号（LDAP 邮箱查找路径未净化）；CVE-2026-112212（7.5），OAuth / OIDC 端点的缓存投毒，可在共享缓存架构下把部分登录流重定向到攻击者服务器。

只影响自建。gitlab.com 已跑在修复版上；GitLab Dedicated 租户在 19.3.5-internal0 / 19.4.2-internal0 及以上即已覆盖。升级本身有成本：19.4.3 与 19.3.6 带数据库变更，单机部署会在迁移期间停机，多机可用官方零停机流程。

检测抓手是现成的。GitLab 在其开源 TLDR 框架里发了两条 Sigma 规则，读的是 GitLab 自己的应用日志：Onigmo native worker crash 与 Org mode render error burst——前者是编译器崩溃，后者是渲染错误爆发，都属于"打崩了但没打通"的痕迹。这类规则的价值在于它抓失败尝试，而失败尝试通常比成功早很多天。

值得关注的原因：一枚 10.0 分、无需登录、无需交互的 RCE，在补丁发出的同一时刻就公开了版本矩阵，而受害面里包含大量"跑在没人管的旧分支上"的自建实例——它们连 19.x 都不到，只能升到 18.11.13。更值得记的是节奏：同一个组件、同一个研究者、一个月四次，说明"把正则编译器当攻击面"这件事才刚开始被人系统性挖掘。有自建 GitLab 的，今晚就该升级；上不去就先把它从公网摘掉，别指望 WAF。

按 Tenable 的统计，Oracle 十月 Critical Patch Update 共 1,295 个补丁、修 1,209 个唯一 CVE、覆盖 33 个产品族；Oracle 自己的风险矩阵里 562 条属于"无需任何凭据即可远程利用"；六枚 CVSS 3.1 满分 10.0，全部网络可达、低复杂度、无权限要求、无用户交互，且 scope changed——打穿之后能往外扩。

Argo CD 三枚：只需要"读"权限，就能在 repo-server 里执行命令

2026-10-20 披露 · 113708 与 113709 均 NVD 9.9 · 另有 113672 任意文件读 最低前提：对已有 Application 的 get 权限 · 无在野 · 无缓解

三枚漏洞里，CVE-2026-113708 与 CVE-2026-113709 都是 NVD 9.9，都发生在 argocd-repo-server 容器内；第三枚 CVE-2026-113672 是 Jsonnet import 可读 repo-server 上的任意文件。三枚共同的恐怖之处不是分数，是最低前提只要对一个已有 Application 的 get 权限——不需要 update、不需要 sync、不需要仓库写权限。

  • 113708（CWE-88）：Kustomize 处理远程 base / component URL 时，把 URL 里的 query 值直接传给 git fetch，没有加"选项结束"分隔符 --。于是 URL 里以连字符开头的值会被 git 当成参数解析——具体是 --upload-pack。当远程传输是本地传输（file://）时，命令就在 repo-server pod 内执行，权限即 repo-server 运行用户，这个用户能读仓库凭据；命令输出可以通过"清单生成报错"回显，既确认执行也顺手带数据出去。历史背景：Kustomize 5.0.0 起接受 file://，4.5.7 会拒绝；单纯升级 Kustomize 并不能修好，缺的是分隔符本身
  • 113709（CWE-829）：Kustomize 构建时若开了 --enable-helm，helmGlobals.configHome 可指向Git 仓库内的路径。Helm 会自动加载 .data/plugins 下的插件，不需要任何安装步骤；只要让 helmCharts 的仓库 URL 用上该插件的协议，恶意下载器插件就会在 repo-server 进程里跑起来。Kustomize 4.1.0 起把 configHome 透传给 Helm，攻击面从那时开始

入口有两个，都便宜：一是往 Application 会构建的仓库里提交一个恶意 Kustomization（或 Kustomization + 插件文件）；二是 POST /api/v1/applications/manifestsWithFiles——只需要对已有 Application 的 get 权限，argocd app diff --local --server-side-generate 也暴露同一路径。

"封出站"在这里没用。本地传输不离开 pod，命令就在本机执行——这会打破很多团队"repo-server 不准出网所以安全"的假设。

顺带说 113672：一个 Jsonnet import 能读 repo-server 上的文件（CWE-22 路径穿越）。单看不致命，但它读的是同一个进程能读到的所有仓库凭据——和上面两条拼起来，就是"先读凭据，再执行命令"。

值得关注的原因：GitOps 把"谁能改集群"这件事集中到了 repo-server：它手上有所有 Git 仓库的凭据，又能渲染出任意清单。今天这三枚说明，在 Argo CD 的权限模型里，"读"这个字一点也不便宜——一个只读账号足以在渲染进程里执行命令。所以真正要审的不是"谁有 sync 权限"，而是"谁有 Application 的 get 权限"，以及"哪些仓库有资格被这个 Application 构建"。

Lazarus 的 Operation FlashHole：把 NIST 的后量子算法，第一次用在恶意载荷投递上

Kaspersky GReAT · Sojun Ryu · 2026-10-21 公开 · 最早痕迹 2025-07 无 CVE · 韩国 3 家受害 · 滥用 INISAFE CrossWeb EX

卡巴斯基公开 Operation FlashHole：针对韩国软件、建筑、有线通信设备制造三个行业，至少 3 家受害，最早痕迹追到 2025-07。整条链的进入点，是韩国人为了网银和政务网站必须安装的那款安全软件——INISAFE CrossWeb EX。

入口伪装得极其耐心。鱼叉邮件把目标引向 GitHub Pages 上的水坑站：一个伪装成"资深网络设备开发者简历"的页面（研究者判断照片是 AI 生成）；到 1 月，同一个站点被换成室内设计作品展示——显然是为建筑公司准备的。页面从仿冒域名 javadevhouse.co[.]kr 或 pythonapischool[.]com 加载 JS，随后触发链走到 CrossWeb EX（INISAFECrossWebEXSvc.exe，V3 3.4.1.2）：它以高完整性拉起合法的 fsquirt.exe（Windows 蓝牙文件传输向导）并注入 shellcode。CrossWeb EX 具体被怎么滥用，卡巴斯基没有给出结论——这是本案最大的未知。

组件作用
TechHub下载器，GitHub API（issue 与文件当留言板）作信道；第一阶段几乎不落地

后量子那一段要单独拆开，因为它是首例。LPEClient 先从 C2 取回四个 1,568 字节的块，每块装着一把 ML-KEM-1024 公钥（NIST 已标准化的后量子 KEM）；用它生成四组"共享密钥 / 密文"对，密文用 GOST 加密后经 ClientHub 回传；C2 侧解出的共享密钥成为 Threefish 的密钥材料，用来解密 C2 响应——里面是参数和一份反射加载的可执行载荷，也就是 Cubridge。ML-KEM 本来是被用来防"先存后解"的防御性标准，这里被拿去保护恶意载荷在传输途中的机密性；这是已记录的首个国家级行为体把 NIST 标准后量子算法用于攻击载荷投递的案例。

C2 藏在真新闻站里。Cubridge 的信道看起来像在看新闻：在被攻陷的真实韩国媒体与设计站点上，请求随机的 /news/economy/article/12345678 这类路径。域名合法、路径合理、内容正常——这类流量靠域名信誉抓不到。

归因与关联（按报告口径）：卡巴斯基以中到高置信度归到 Lazarus，并把它放进更宽的 Cascade Hole 活动簇，与 2025 年的 Operation SyncHole（同样滥用 Cross EX 的水坑）关联，共同工具是 LPEClient；TechHub、Cubridge、TouchShift 是 Lazarus "Dream Job" 系列工具（CLOUDBURST / SIDESHOW / LightlessCan）的新版本，ClientHub 像是 CookiePlus 的进阶版。两次活动共同命中的唯一行业是软件制造——研究者把这条读成对源码的需求。另外，卡巴斯基还描述了韩国自 7 月以来的另一簇 COPPERHEDGE 后门活动，那一簇最终落到勒索与泄露站；FlashHole 本身是纯间谍活动。

值得关注的原因：两句话。第一，"全国强制安装的安全软件"是最高效的发射台——它必须运行、必须和浏览器对话、通常以高权限运行，而且几乎没有用户会去质疑它；CrossWeb EX 在 2021、2022、2023 都被 Lazarus 用过，这是第四次。第二，后量子加密进入攻击方的工具箱，意味着"抓流量以后再说"这条退路变窄了：如果 C2 与载荷投递都用 ML-KEM 保护的会话，今天录下来的流量，未来也解不开。防守方唯一还站得住的抓手是行为，不是内容——异常的服务名（真服务名加两个字母）、RasConv 目录下不该存在的 ImeBroker.exe 与 mscoree.dll、时间戳来自 monitor.sys 的文件、以及"浏览器在访问新闻站"但进程不是浏览器的流量。

印度国家银行：37.5 万条里筛出 3,897 条真实 PII，暗网挂出五天后才披露

2026-10-16 收到 DCA 与 CERT-In 告警 · 10-21 向交易所披露 无 CVE · 涉手机号、生日、住址、CIF 与 lead ID · 已聘 CERT-In 名录机构

10-21，印度最大的银行 SBI 依 SEBI 第 30 条向交易所提交披露：暗网上约 37.5 万条记录中，初步分析确认 3,897 条含真实个人可识别信息（PII）。银行称客户余额安全、核心业务无重大影响，已聘请 CERT-In 名录内的独立机构调查。

时间线值得注意：10-16，威胁情报供应商、Defence Cyber Agency 与 CERT-In 同时发出疑似泄露告警；同日，自称 Siriusim 的团伙在暗网"首发"数据集，被安全监测账号 CyberPulse56 在 X 上记录；10-21（周三），SBI 才披露并启动事件响应。

被确认泄露的字段：注册手机号、出生日期、姓名、性别、邮箱、住址、分行与 CIF 编号（客户信息文件号）、lead ID（潜客线索唯一编号），以及贷款/线索记录的元数据。

为什么 3,897 条也不能当小事。这些字段凑在一起不是"联系方式泄露"，而是一份现成的诈骗脚本：知道你在哪家分行、什么时候申请过贷款、CIF 号是多少——来电者一开口就能报出你自己的故事。Grant Thornton Bharat 的合伙人 Akshay Garkel 提醒得对：其余那 37.1 万条"没识别出 PII"的记录，不应自动当成无害；63SATS Cybertech 的 Srinivas L 说得更直白："泄露的密码一分钟就能改，泄露的贷款档案改不了。"

团伙声称的规模远大于银行确认的数字。Siriusim 声称持有约 37.5 万条 CSV 记录 + 2,722 份 PDF，内容含贷款申请与开户文件——这些是攻击方单方面说法，SBI 既未确认来源，也未说明数据是从银行系统、供应商、还是旧泄露里流出的。

值得关注的原因：这是本月第四次"服务型 / 数据型"事件（10-18 的 ConnectWise 一个应用身份开 173 个租户、10-20 的日经第三次 183 万条、10-21 的 Bullhorn 停摆）。它们的共同形状是：受害方都在事件后强调"核心系统未受影响"——这句话在技术上多半成立，在业务上几乎没有意义，因为泄露的从来不是"核心系统"，是核心系统里存着的那些人。另一件要记住的事：告警来自外部（DCA 与 CERT-In），不是自查发现的。这意味着从 10-16 到 10-21 的这五天，是别人替你在看你的数据。

7. PHP2Shell 跟踪：首波攻击比补丁早六小时，PoC 已公开，在野利用已被确认

（前情见第 193 期，本条只记 10-21 至 10-22 的新增事实。）Cloudflare 记录到首批攻击发生在 10-21 07:43 UTC，而补丁发布在 13:30 UTC（PHP 官方口径）／13:40（ENISA 口径）——攻击者比补丁早动手约六小时，起点是 10-20 的泄密帖。10-22，奇安信 CERT 宣布已成功复现两枚漏洞，并把状态从"未发现在野"改为"已发现在野利用"，PoC 与 EXP 均标为已公开，同时给出天眼规则 0x10022A87（15155 版本覆盖）。欧洲反应升级到最高级：欧盟委员会 DG CNECT、ENISA、CERT-EU、Europol EC3 与 CSIRTs 网络发布联合声明；NSA 也发布紧急建议，核心是"修不了就先下线"。暴露面出现新数字：Palo Alto Cortex Xpanse 遥测识别出超过 2,260 万个公网暴露的、可能受影响的 PHP 实例。两个处置禁区必须记住：① 不要用 RLIMIT_AS / RLIMIT_DATA 当缓解——它们会让 mmap() 失败，正好触发 109618 依赖的 longjmp() 路径；② memory_limit=-1 只能缓解 109618，对 109619 的陈旧全局状态无效，而且必须用 php_admin_value 固定住才不会被应用覆盖。另外 rpms.remirepo.net 这个第三方仓库在发布日不会更新，用它的人要么换发行版包要么自己编译。升级后必须重启 Apache / PHP-FPM / 所有常驻 worker——只换二进制不重启进程，风险一点没减。

8. CISA KEV 一次加入六枚：三枚只给三天

CISA 在 10-20 一次性把六枚已确认在野利用的漏洞加进 KEV：Plex2Shell 四枚（96652 / 96654 / 96655 / 96656）、Siemens Software Center 的 110936（8.4，DLL 旁加载，经 ROMULUS 的 ClickFix 投放）、EG Secure Solutions SiteGuard 的 106931（8.5，OS 命令注入）。其中 106931、96656、96654 的联邦修复期限是 10-23——从列入到到期只有三天，这是新规 BOD 26-04（按风险排优先级） 的实际效果：CISA 认为最急的那批不再给标准窗口，其余三枚给到 11-03。这三条在往期都单独报过（SiteGuard 见 10-19 期、Siemens 见 10-21 期），本条只记 KEV 状态与期限。

9. 333 个 Tor 出口节点被植入 Ebury：SSH 密码在三天里被批量收割

研究者 KABA 在 10-20 的复盘里完整还原了一次基础设施级攻击：10-02 09:35 UTC 起，333 个已被植入后门的 Tor 出口中继（约占全网出口的十分之一）把 22 端口的 SSH 连接重定向到 12 台拦截服务器。网页流量全部正常转发，所以没人觉得坏了——陷阱只对 SSH 用户合上。受害者的第一反应通常是 REMOTE HOST IDENTIFICATION HAS CHANGED 告警；忽略告警继续登录的人交出去三样东西：输进攻击者服务器的密码、之后敲的每一条命令（拦截器同时向真服务器建一条连接，做实时中间人）、以及服务器本身——第二条并行连接会在受害者机器上装 Ebury。本次版本 1.8.3，落成单个 setuid 库 /usr/lib/x86_64-linux-gnu/libkeyutils.so.1.10.2 加一个 libkeyutils.so.1 软链；系统自带的那个库没被改，所以 dpkg -V 与 debsums 都查不出来，sshd / sudo / PAM 的包校验也全过。中继侧至少潜伏两个月（8 月起），操作者的根因老实得扎心：一个密码同时用于 SSH 登录、sudo 和备份口令，明文存在两台服务器上，而管理机的 SSH 密码认证还开着。处置阶段：目录权威在 10-04 18:00 UTC 开始投 BadExit 与 MiddleOnly 票，21:00 进共识；到 10-05 17:00 UTC 带攻击者策略的中继全部出局；Tor Metrics 的出口数在 10-03 至 10-05 之间掉了约 370 个，到 10-18 都没恢复。一句话：10-01 至 10-05 之间在 Tor 上输过 SSH 密码的，按泄露处理——改密码，并去查那台服务器。

10. Signal CVE-2026-113380（9.3）：挂断之后，音频还在继续

10-20 公开、CVSS 4.0 9.3，缺陷在 Signal 的 RingRTC 通话库（2.72.0 之前，修复提交于 9-04）。攻击者只要是通话中的一个远端参与者，就能灌满通话内部的事件队列，让挂断动作失败——结果是音频（可能还有视频）在对方"结束通话"之后继续传输。问题在客户端（Android / iOS / Desktop），不在服务器。不在 KEV，无在野报告，Signal 也没说哪些版本号包含修复。动作很简单：所有手机和已链接的桌面端今天都更新。

11. Frenos：前沿模型能给出可用的 OT 攻击计划，约九成

Frenos 在 10-21 发布的研究跑了 10 个模型（6 个前沿闭源 + 4 个开放权重）、16,980 次测试，时间跨度 2025-10 至 2026-09。结果：最强的三个前沿模型，针对电力、水务这类 OT 系统给出的攻击计划，约 90% 是"可用"的；但只有 60–74% 的计划在每次重跑中都通过全部检查——一次能对，重复未必能对。Frenos 估计距离"可靠的 AI 攻击规划"大约还有两年，并明确说AI 目前还没有把新手变成国家级攻击者。这条要和今天第五条对着看：Lazarus 用后量子算法做交付层，AI 在做规划层——两件事都还没到"自主"，但都已经不再需要人类从零开始。
