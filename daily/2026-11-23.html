九月修好的洞，现在有十条进门的路

Ghostscript CVE-2026-125396 · Upload2Shell · 10.08.0 于 2026-09-08 静默修复 · CVE 记录 11-09 进 NVD Type 1 字体加载器 UAF · -dSAFER 仍开着但被改掉 · 命令以渲染进程身份执行

9 月 8 日，Artifex 发布 Ghostscript 10.08.0。这个版本里悄悄修掉了一个 Type 1 字体加载器的 use-after-free，没有安全公告，CHANGELOG 里也看不出这是一次安全修复。11 月 9 日，CVE-2026-125396 的记录进了 NVD。11 月中下旬，pwn.ai 的研究员 Paulos Yibelo 把完整利用链公开，取名 Upload2Shell。关于公开日期，不同来源给的是 17 日与 21 日两个说法，本文按 11 月中下旬记。

机制不复杂。Ghostscript 的 -dSAFER 是一个软沙箱，靠进程内部一张检查表限制 PostScript 能碰什么。字体加载的辅助函数在写入一块内存前没有校验输入类型，构造的文档能在这里报错，然后在错误处理路径上把那次受限的写操作捞回来，用来越界改写内存，最后改掉那几条安全检查的判断结果。全程 -dSAFER 都是开着的。沙箱没有被关掉，它被改掉了。

让这件事变严重的是进门的路。受影响的服务器不需要直接暴露 Ghostscript，只要它有缩略图、预览、格式转换这类功能，文件就会自动被递进去。而这些库判断类型看内容不看扩展名：一个叫 quarterly.jpg 的文件，里面装的是 PostScript，ImageMagick、Pillow、libvips、Qt 的图像插件都会照单转交。

云修好了，设备上的后门还在

GL.iNet GoodCloud · 安全通告 2026-11-20 · 稳定版安全固件 11-22 开闸 · 涉及路由器与 KVM-over-IP IOC 进程 crond -i /tmp/.log · 部分恶意文件时间戳 2025-12 · 公司未公布受影响数量

11 月 20 日，GL.iNet 发了一份安全通告：攻击者利用 GoodCloud 远程管理服务里的一个漏洞，在部分路由器和 KVM-over-IP 设备上装了恶意软件。公司说云端漏洞已修、攻击路径已切断，紧接着补了一句关键的：这些措施不会清除已被感染设备上的恶意软件。

这句话把事件劈成了两半。云端是修好了，设备是另一回事。

公开的证据来自第三方。RemoteToHome 是一家做 GL.iNet 设备群管理的公司，它自查了持有或代管的 183 台路由器，152 台有可疑活动：24 台存在指向攻击者地址的 root 级反向 shell，47 台有更早的持久化后门，81 台留下了命令执行痕迹。部分恶意文件的时间戳是 2025 年 12 月，如果属实，这批设备被控制的时间接近一年，跟十一月这次不是同一件事。

对一台被拿下的设备，BleepingComputer 分析了一个叫 ni.sh 的投放脚本：识别型号，从硬编码地址下载 gl-helper 与 gb 两个可执行文件；通过启动脚本和计划任务做持久化，重启和杀进程都清不掉；替换 netstat，让管理员看不到通往 66.245.219.252 的连接；写入 SSH 公钥；定时拉取并执行远端命令；最后把自己伪装成 crond -i /tmp/.log。

最后那条就是通告里给的唯一 IOC。公开的 C2 与反弹地址包括 170.39.226.219、66.245.219.252、65.20.71.131。

值得关注的原因：

  • 云修好不等于设备修好。这是所有云端下发架构的通病。控制面被攻破之后，端侧留下的东西与云端是否修好完全解耦。修云端只是关掉了再来一次的门，屋里的东西还在。
  • 自查命令只能证明现在。看到那个伪装进程就是中招，看不到只能说这个特征此刻没在跑。论坛里已有人报告发现其他后门与反向 shell，RemoteToHome 的说法更刺：它管的设备里没有一台命中官方这个 IOC，包括那些确认存在远程 shell 的。
  • 重置也有讲究。出厂重置之后不要恢复旧配置备份，恶意文件可能就藏在配置目录里，普通升级会把它一起带过去。重置完换掉管理员与 Wi-Fi 密码，重新签发 VPN 配置。
  • KVM 是通往内网的跳板。这类产品本身就是用来远程控制电脑和服务器的，它被拿下意味着背后接的那些机器可能一起暴露，公司说还在查。排查范围要按它能碰到什么来划，不按它自己是什么来划。

一个注册页面，替一百七十八家挂了马

Optimizely Web Experimentation CVE-2026-132224 · 攻击窗口 2026-11-16 00:37 至 22:24 UTC · 全部经 cdn.optimizely.com 下发 剪贴板劫持 7,040 美元 · 表单抓卡 · Cookie 与截图 · iOS 18.6 及以下加载第二阶段

11 月 16 日，一个攻击者用 Optimizely Web Experimentation 账号注册流程里的缺陷，把恶意 JavaScript 写进了客户的 Project JavaScript 配置项。这段代码由 cdn.optimizely.com 直接下发，带着 Optimizely 自己的 TLS 证书。访问者去的是 BBC、CNN、Zoom、Salesforce、GitLab、HSBC、IKEA、Equifax、Ledger 的正规域名，地址栏是干净的。

入侵路径值得单独看：注册流程的缺陷让攻击者能建号，然后拿公开片段里可见的账号 ID 与项目 ID，去猜客户员工邮箱的各种变体，对单个客户最多试到几千次，直到命中一个管理员。登录态是真的，身份是猜出来的。

载荷四件事一起做：替换剪贴板里的钱包地址（Report URI 追到约 7,040 美元，通过一个三月和 11 月 3 日都用过的地址提走）；从页面表单抓卡号、有效期、CVV；偷 Cookie 与截图；对 iOS/iPadOS 18.6 及以下加载第二阶段，指向 Coruna 与 DarkSword 两套工具，但没有设备被攻破的证据。

  • CSP 是这类攻击唯一的现场防线，而它大面积缺席。对 178 家的分析显示：68 家完全没有 CSP，50 家的策略宽松到拦不住，只有 24 家配得足够严，约 15%。脚本来自可信域名、走自家证书、域名没变，浏览器侧能分辨的只剩策略白名单。

重置链接发给了输入的那个地址

Weblate CVE-2026-134838 · reset_password 视图 · accounts/forms.py · 配套 PR 22506 Unicode 大小写折叠 · 无点 i 变体 · 查账号与发信读的不是同一个字符串

CVE-2026-134838，影响 2026.11 之前的 Weblate，reset_password 视图存在账号接管。CVSS 4.0 记 9.1，未认证可用。

机制只有一句话：账号查询是大小写不敏感的，邮件投递是照原样发的。

表单在匹配邮箱时做了 Unicode 大小写折叠，所以在它看来 user@example.com 与 USER@example.com 是同一个账号。但重置链接是发到用户刚刚输入的那个地址上，不是发到数据库里存的地址上。攻击者只要控制一个只在大小写上不同、或者用了无点 i 之类折叠后等价的邮箱，输入那个变体去请求重置，链接就会进他的信箱，然后他给受害者的账号设一个新密码。

修复提交在 weblate/accounts/forms.py，配套 PR 22506。

值得关注的原因：

  • 两个动作读的不是同一个字符串。查账号用规范化后的值，发信用原始输入。这类缺陷在任何做身份归一化的系统里都可能重演，包括 SSO 回调、邀请链接、工单系统里的邮箱匹配。
  • 改密码这件事不需要密码。攻击面只剩一个表单，没有任何前置凭据。对自建翻译平台来说，账号里往往连着仓库写权限与 CI 令牌。
  • 邮箱的本地部分理论上区分大小写。RFC 5321 把 @ 前面的部分交给收信服务器自行决定，所以 User@ 与 user@ 在有的服务上是两个人。系统做折叠是为了体验，但折叠的结论不能外溢到投递环节。
  • 这类漏洞不会有告警。日志里是一条正常的重置请求、一条正常的邮件发送、一条正常的密码修改。要发现它，得比对请求里的地址与账号上的地址是否字面一致。
输入受害者邮箱的大小写折叠变体 reset_password 视图查询账号 折叠后匹配到受害者 生成重置令牌 链接发到用户输入的那个地址 攻击者信箱收到链接 设置新密码 账号接管

换一个协议入口，就没人查权限了

Portainer CVE-2026-134804 · 2.39.0 至 2.39.9 前 / 2.40.0 至 2.45.4 前 / 3.0.0 至 3.1.0 前 AV:N / AC:L / PR:L · /api/websocket/attach 与 /api/websocket/exec · 只需一个泄漏的容器 ID

CVE-2026-134804，影响 Portainer 2.39.0 至 2.39.9 之前、2.40.0 至 2.45.4 之前、3.0.0 至 3.1.0 之前。CVSS 4.0 记 8.7，AV:N / AC:L / PR:L，只要有一个普通账号就能打。

Portainer 的容器操作有两条路：REST 接口，和 WebSocket 的升级通道。/api/websocket/attach 用来接管一个容器的标准输入输出，/api/websocket/exec 用来在容器里执行命令。在受影响版本里，这两个 handler 没有做「这个容器是不是你的」这类授权判断，只校验了「你是不是登录用户」。结果是同一个环境里的 Standard 用户，只要拿到别人的容器 ID 或 exec ID，就能通过这两条通道挂上去，拿到一个可以交互的 root shell。

ID 从哪来并不困难。容器 ID 出现在部署日志、监控面板、截图、工单、CI 输出里，很多还会被直接贴进聊天群。它不是一个需要猜的秘密。

修复提交改的就是这两个 handler，分别对应 api/http/handler/websocket/attach.go 与 exec.go。

值得关注的原因：

  • 授权写在一条路上，另一条路就废了。同一份能力，两套入口，两套实现，最后只有一套被加固。这种形状在管理平台里很常见：REST 有人审，WebSocket 是后来加的。
  • PR:L 才是这类洞的真实威胁模型。8.7 的分数由低权限加网络可达撑起来。Portainer 通常部署在运维网段，账号来自企业目录，一个离职没删的账号就够。
  • 容器里的 root 往往就是宿主机的 root。Portainer 的正常部署方式是挂载 /var/run/docker.sock。拿到容器内 root 之后能做什么，取决于这个挂载还在不在，而大多数部署都没动过它。
  • 升级前先想清楚谁有账号。修在 2.39.9、2.45.4、3.1.0。补丁之外，把 Standard 用户清单过一遍，比改版本号更值得花时间。
Standard 角色账号登录 从日志或工单里拿到容器 ID 走 REST 接口查容器 改走 /api/websocket/attach handler 只校验是否登录 未校验容器归属 用 exec 通道执行命令 容器内 root shell

先解压，再量大小，等于从来没量

Faye websocket-driver / Casdoor 4.27.1 前 / Gunicorn 25.2.0 至 27.0.0 前 / msgpackr 2.1.4 前 · 2026-11-22 同日公开 PR:N · 均在解压或缓冲之后才比对上限 · 无在野报告 无公开 PoC

11 月 22 日进来的这批里有四条 DoS，彼此不认识，语言不同，形状一样：大小上限是在内容被展开之后才检查的。

Faye 的 websocket-driver、permessage-deflate、websocket-extensions 三件套里，消息先被完整 inflate，之后才套 maxLength，未认证客户端协商 permessage-deflate 就能撑爆内存；Casdoor 的 decodeSamlMessage 对 DEFLATE 压缩的 SAML 消息不设边界，/api/saml/logout/:owner/:application 收一个小包能展开成几个 GB；Gunicorn 纯 Python 的 ASGI HTTP/1 解析器缓冲协议行时不设上限，缺 CRLF 的请求行、头、chunk 长度行、trailer 都能把 worker 内存拉高；msgpackr 是重复结构导致的算法复杂度问题。

四个组件的缺陷对照：

组件缺陷分数
Faye websocket-driver 系先 inflate 后查 maxLength8.7
Casdoor 4.27.1 前SAML 消息解压无边界8.7
Gunicorn 27.0.0 前ASGI 解析器不设行长上限8.7
msgpackr 2.1.4 前重复结构导致算法复杂度8.7

四条都是 PR:N，不需要账号。四条都没有在野利用报告，也没有 PoC 流出，它们只是被同一批公开了出来。

值得关注的原因：

  • 顺序错比阈值错更难发现。代码里 maxLength 这个数字是有的，审查看到了会以为已经防护。要看的是它出现在 inflate() 之前还是之后。
  • 协议层把这件事交给了应用层。permessage-deflate、SAML 的 DEFLATE、HTTP 的 chunked，压缩都是协议自带的选项，由应用决定要不要协商。协商了却没在上限上做文章，等于把一个放大倍数交给对端。
  • 拒绝服务在评分体系里永远垫底。8.7 不低，但四个 8.7 加起来也换不来一次紧急变更窗口。这类补丁通常随下个常规版本走，中间那段时间服务就是可以被一个连接打挂的。
  • 改法都一样。流式解压加边解边计数，超限立即中断；或者先看声明长度，超过直接拒。四种实现，一个思路。

速览

7. 今天四条 KEV 到期，目录停在 1,790 条

CISA 目录仍是 2026.11.20 版、1,790 条，361 条标注与勒索软件相关，11-21 到 11-23 没有新增。11 月 20 日那批四条的整改期限就是今天：vCenter 的 CVE-2026-123890、Cisco Expressway 的 CVE-2026-76466、Apache Roller 的 CVE-2026-129448、SAP NetWeaver 的 CVE-2025-42884。往前一批里，Apache Axis 的 CVE-2026-90436 与 Synology DSM 的 CVE-2024-10441 已经在 11-21 过期。过期不等于安全，只等于你已经在违规名单上。

8. simple-git 与 binary-parser 都是 9.2：守卫清单漏了一个参数

CVE-2026-134815，simple-git 4.1.0 之前，allowUnsafePack 这道守卫只拦 push 类操作，攻击者能影响 listRemote() 或 raw() 的参数时，给 ls-remote、archive、fetch-pack、send-pack 塞一个 --exec 就能在宿主机执行命令。CVE-2026-134814，binary-parser 2.3.1 之前，Context.generateOption() 把字符串型选项不做校验直接拼进生成代码，控制解析器定义的人可以在编译解析器时执行任意 JavaScript。两条都是 AC:H，都需要攻击者能影响某个参数。

9. N-able MailAssure 9.3：LDAP 同步连接检查没有目标限制

CVE-2026-134624，MailAssure（原 SpamExperts）20261121.1943 之前。配置中继时触发的 LDAP 同步连接检查不限制目标地址，一个已认证的 API 用户可以让服务器去连任意内网主机和端口，探测哪些可达，并把构造的数据送给内网服务。9.3 但 PR:H，入口是一个 API 账号。

10. Kirby 8.7：分块上传的竞态把 SVG 清洗绕了

CVE-2026-134765，Kirby 5.6.4 之前。processChunk() 里同名的并发分块上传可以互相覆盖：先传一个干净的 SVG 过清洗，再让另一个分块把它换成带脚本的版本，最终在站点源上形成存储型 XSS。需要上传权限，AC:H，8.7。

11. Dashy 8.6：前缀判断把凭据送给了相似域名

CVE-2026-134836，Dashy 4.9.12 之前。isLocalRequest 用前缀比对判断是不是本站，攻击者用 config 参数指向一个相似域名，已登录用户的 bearer token 或 HTTP 认证头会被一起带过去，进而读走配置里存的 API 密钥；管理员受害时还能改。8.6。

12. 窗口统计：401 条新记录，零个 10.0

11-22 00:00 至 11-23 15:00，NVD 收 401 条，9.0 以上 24 条，10.0 零条，7.0 以上 229 条。133 条是 Linux 内核的合并提交，其中 12 条记 9.8；剩下 268 条里 9.0 以上 12 条，其中两条是 WordPress 插件的反序列化（Simple Shopping Cart 与 APCu Manager，均 9.8）。窗口里最值得处置的东西，分数往往不是最高的那条。
