看起来最干净的那一格

一个人往请求里塞了个空对象——{}——就拿到了虚拟化管理平台的管理员会话，进而 root 掉整台 XCP-ng 节点，而这个洞到今天还没有 CVE 编号。一家 RMM 厂商在被公开 33 个零日之后能做的最安全的事，是让所有客户把自己的产品关掉。一个 Ruby gem 在安装时就已经跑完了，而事件响应手册的第一步"先撤销被盗令牌"会触发它删掉你整个家目录。微软这个月修了一千多条，其中唯一被在野利用的那条评了 6.5 分、等级 Moderate。Adobe 同一份公告上写"不需要权限"，Adobe 自己提交的 CVE 记录上写"需要低权限"，三行都不一样。Chrome 今年第八个在野零日，已经写不进"重大"这个词里了。每一个判断依据看起来都没问题，问题是它们指向的方向。

1 空对象

一个空 JSON 对象，换一张管理员令牌

VSA-2026-062 · 11-10 公告 · 无 CVE 编号 · 无 CVSS 评分 · 影响 Xen Orchestra 与 XOA 已在野利用 · 修复见 6.9.1–6.10.0 与 6.9.2–6.10.1 两种口径

2026 年 11 月 10 日，法国 Vates VMS 发布安全公告 VSA-2026-062，说 Xen Orchestra 里有一个严重的认证绕过，并且已经在被利用。这份公告最刺眼的地方不是严重性，是它没有 CVE 编号，也没有 CVSS 评分。

Xen Orchestra 是管 XCP-ng 虚拟化环境的 Web 控制台——虚拟机、主机、资源池都从这里管。这类东西一旦被拿管理员，结果不是"一个后台被登录"，是整批宿主机。

缺陷本身只有一句话。公告原文是这么写的：REST 的 cookie 解析会把 authenticationToken=j:%7B%7D 变成 {}，REST 认证不要求这个值必须是字符串就把它交给 XO 的 token provider；token 集合把 {} 当成"没有过滤条件"的查询，返回它拿到的第一条令牌；如果这条令牌没过期，provider 就以它的所有者身份通过认证。进去之后，/rest/v0/users/me/authentication_tokens 这个已经认证过的路由会把"可复用的登录令牌 ID"一并交出来。

也就是说：攻击者不需要密码、不需要劫持会话、不需要过 MFA。他只需要让服务端相信"我手上这个空对象，就是某个人的令牌"。

Vates 自己的影响描述是：攻击者可以以 Admin 权限执行操作，Xen Orchestra 被攻陷可导致受管资源池上的任意代码执行，以及以 root 身份完全接管 XCP-ng 节点。发现者是 TDC NET Security 的 Filip Magic（@mad31k）和 Christoffer Olsen，修复提交是 PR #10748。

版本号对不上，这件事要单独说。BleepingComputer 与 The Hacker News 都写修复版本是 Xen Orchestra 6.9.1（stable）与 6.10.0（latest），对应 xo-server 包 5.211.2 与 5.213.1。但另有一份逐条读公告的分析指出，Vates 现行公告列的是 6.9.2 与 6.10.1，早期报道引的是上一版。这种情况下的正确做法是回厂商公告本身核当前版本，不是照着新闻里的数字验收——两个都是"官方说过"的数字，但只有一个是最新的。

最难的部分是"发现了也没记录"。Vates 明确说，这种利用不会在日志里留下任何标识——它就是一次带着怪 cookie 的正常 HTTP 请求，认证通过了，后面全是合法 API 调用。没有崩溃、没有告警、没有可用性抖动。所以只能靠 HTTP 层的流量监控（tcpdump、Wireshark、代理或 WAF 日志）去捞那串 j:%7B%7D。历史日志要往前翻，因为这种会话可以在里面躺几天到几周没人看。

没有 CVE 编号的副作用：所有按 CVE 匹配的扫描器都不会标出这台机器，核对版本只能手工对公告。这是这类"厂商自有编号"漏洞的固定成本，而它出现的位置——虚拟化管理面——恰好是扫不到就最危险的那种。Vates 也给了个降风险的判断：大多数 XO 部署并不对公网开放，暴露面有限。这句话既是安慰也是提醒，真正需要今天动手的，是那批把管理口开在公网上的。

塞一个空对象进 cookie 不校验类型 直接交给令牌提供方 集合当成无过滤查询 返回第一条未过期令牌 取可复用登录令牌 ID Admin 权限 接管整片资源池 日志里什么都不会留下
2 全量下线

三十三条零日公开后，厂商让客户把产品关掉

N-able N-central · 11-08 公开带 PoC · 11-09 14:00 UTC 托管版三区下线 · 11-10 发 2026.4 HF2 33 条零日对 7 个 CVE · Censys 记 1,728 台公网暴露 · 单 IP 18 小时 68 次尝试

一家软件厂商让客户把自己的产品关机，这件事不常发生。2026 年 11 月 10 日，N-able 这么做了。

起因是 11 月 8 日（周日）晚，独立安全研究者 Sean Bales（GitHub 账号 Oracle-Security）公开了一个名叫 Able2Shell 的仓库，里面是 N-able N-central 的 30 多条零日漏洞和可用的利用代码——安全公司 Huntress 数的结果是 33 条。他测的是 N-central Appliance 2026.4.0.31，一个预发布构建，并在仓库文档里说这些洞"大多数或全部"同样影响更早的版本，包括当前最新发布版。他自述挖掘过程用了 AI 辅助。

N-central 是 MSP 和 IT 团队用来远程监控、打补丁、支持终端的 RMM 平台。一台 N-central 服务器上挂着这家 MSP 所有客户的机器，所以它的失陷不是一家的事。

33 条拼成四条链，最狠的那条不需要任何凭据。链路一：service-import 功能的未认证 XXE 窃取本地可信会话，重置某个账号密码，以 nable 服务账户执行命令，同一条链还能直接创建一个已启用、密码由攻击者指定的 Default Administrator 账号。链路二：设备有一套可预测的 passcode，匿名攻击者借此注入恶意补丁元数据，管理员查看补丁详情时存储型 XSS 在管理员浏览器里执行，调用以 nable 身份运行命令的接口。链路三：同一个 XSS 可以劫持管理员会话，提交一份构造好的审计导出配置，命令以 root 执行。链路四：软件仓库功能的目录穿越把一个可执行的网页写进服务器 Web 目录，再通过一个免密码安装程序升到 root。

另有一条原生 GenericTCP 栈溢出，单独也能到 root。披露清单里还包括凭据泄露、任意文件写入、目录穿越、认证绕过，以及审计日志篡改——最后这条意味着：如果一台控制台在被关机之前就已经失陷，它自己的日志可能证明不了什么。

HF2 列的七个 CVE 是：125883（多条 XXE）、125878（多条 OGNL 注入）、125879（通过 nable 可写的 syslog-ng 配置本地提权到 root）、125880（MMS3 补丁元数据存储型 XSS，管理员上下文）、125881（service import schema 校验的 schema-hint SSRF）、125882（文件仓库上传路径穿越导致 RCE，致谢 Nate Fair / Sprocket Security）、91000（不安全 IPC 通道导致本地提权）。33 条对 7 条——厂商自己也没说这七个覆盖了多少。

三个必须一起看的数字：Censys 记到 1,728 台公网暴露的 N-central；Previdian 那个 68 次、单 IP、18 小时的数字说明扫描已经开始得很彻底；而 N-able 反复强调"没有证据表明客户环境被成功利用"。这三句话不矛盾，但它们回答的是三个不同的问题——暴露多少、被戳多少、成了几个。第三个问题的答案取决于你有没有日志能回答它，而审计篡改正好在攻击链里。

为什么是这时候爆的：Bales 对 BleepingComputer 说，他之所以不预警直接公开，是因为 N-able 对他报在另一个产品里的漏洞拖了几个月没修。这是 15 个月里 N-able 第四次被迫紧急响应——2025 年 8 月它修 CVE-2025-8875 和 8876 时，那两个洞已经作为零日被打了。Huntress 的一个实操提醒值得单独抄下来：补好的构建可能不会带新的版本号，别拿版本字符串当验收依据。

3 装包即感染

装包那一刻就已经跑完了，撤销令牌会删掉家目录

RubyGems 上的 strutil-core 1.0.1 · 5.48 MB 载荷 · 上架到下架约 5 小时 · 发布后 70 秒被标记 读取 51 个凭据存储 · 令牌一旦返回 401 就删掉整个主目录 · Miasma 家族第一个 RubyGems 构建

一个自称"轻量字符串处理助手"的 Ruby gem，在 11 月 1 日上架，两个小时后被换成带载荷的版本，五小时后被下架。这五个小时里，任何人跑一次 gem install 或 bundle install，就已经完成了感染——不需要 require，不需要调用，不需要在应用里用到它。

Socket 在 11 月 6 日公开了分析。时间戳精确到秒：11-01 02:19:56，账号 jamnajiea 发布干净的 1.0.0，沙箱跑下来无恶意行为；04:05:04 同一账号发布 1.0.1，带 5.48 MB 载荷；04:06:14 Socket 的 AI 扫描器标记为已知恶意代码——发布后 70 秒；08:52–09:13 RubyGems 下架两个版本，前后约 5 小时。

载荷为什么能"装的时候就跑"：gem 声明了一个原生扩展，而 ext/strutil-core/extconf.rb 里面一行构建逻辑都没有。在 Linux 和 macOS 上，它把 Bun 1.2.18 运行时从官方 Release 下到临时目录，用 Bun 跑旁边的 index.js，清理现场，然后写一个目标为空的 Makefile——这样安装过程不会报错，看起来一切正常。

最值得记的一点是：这个 gem 是蠕虫自己的注入器输出的产物。解码后的载荷里带一个 RubyGems 传播模块——拿到偷来的 API key 之后，逐个下载可发布的 gem，把载荷和安装器塞进去，改 gemspec 的版本号，用伪装成 gem 客户端的 User-Agent 推上去。把载荷里的安装器模板用自己的常量填满，能逐字节复现出这次发出去的 extconf.rb（SHA-256 c5264f3b…9c749）；安装器 36 行非空代码里，33 行与 2026 年 6 月那份为防御研究而公开的 Miasma 载荷逐字相同。

这也顺手解释了一个很蠢但很好用的追踪线索：注入器只改 gemspec 的版本号，不改源码，所以那个发布为 1.0.1 的 gem，里面仍然写着 VERSION = '1.0.0'。十一月这版与六月相比改了四处：Bun 从 1.3.13 换成 1.2.18、把下载 URL 拆开以打断静态签名、换了新的客户端 UA、加了进度日志和 dry-run 开关。

它偷什么：先做一次 locale 检查，遇到俄语、白俄语、哈萨克语、乌兹别克语、吉尔吉斯语、塔吉克语、亚美尼亚语、阿塞拜疆语、乌克兰语、格鲁吉亚语、土库曼语、摩尔多瓦语的系统直接退出。然后收集云、包仓库、Git 托管、SSH、Docker、Kubernetes、Vault、密码管理器、系统钥匙串、钱包，以及 AI 编码工具的凭据——.claude/.credentials.json 和 .codex/auth.json 都在里面。Bitbison 的沙箱记录到它读了 51 个凭据存储。拿到 AWS 凭据会调 STS，在 17 个区域枚举 Secrets Manager 与 SSM 参数，在 11 个区域申请 ECR token。

在 GitHub Actions runner 上它会去 /proc 里找 worker 进程，通过免密码 sudo 把一段内嵌 Python 管道过去抓进程内存里的密钥（2025 年 3 月 tj-actions/changed-files 那次的手法），接着通过 docker socket 杀掉 StepSecurity 的 Harden-Runner 容器，再装一个特权 Alpine 容器给 runner 免密码 sudo。数据用 AES-256-GCM 加密、密钥用 RSA-OAEP 包裹，POST 到 paleasbest[.]top/v1/api；失败就回退到公开 GitHub 仓库（描述写 project-utils，commit 前缀 AutoSyncComplete）或 GitLab。

AI 工具投毒是这轮最该看的部分：它会在用户主目录里找 AI 编码工具的配置，加一个叫 workspace-tools 的 MCP 服务器，用 node 把载荷再跑一遍；再加 SessionStart 钩子，会话一开就执行。有可用 Git 凭据的话，它把这套东西推进仓库：.claude/settings.json、.cursor/mcp.json、CLAUDE.md、AGENTS.md、.vscode/tasks.json。生成的 AGENTS.md 会让编码代理在第一条命令之前先跑一个 setup 脚本——只要在带信任设置的 AI 工具里打开一个受影响的仓库，就可能重新触发它。

持久化和那个陷阱：它装一个 Python 后门 sync.py，注册成 systemd 用户服务 pkg-runtime 或 LaunchAgent，每小时去公开 GitHub commit 里搜标记 msync-3f7a，只执行带有效 RSA-PSS 签名的脚本。另有一个叫 net-health-checker 的监视器，每 45 秒验一次偷来的 GitHub token；一旦返回 401 或 403，就执行删掉整个主目录的命令。

这就是为什么处置顺序要反着写：事件响应的第一反应是"立刻撤销被盗 token"，而在这套设计里，撤销就是引爆。正确顺序是先在隔离的主机上清掉 net-health-checker 和 pkg-runtime，再从干净设备上轮换全部凭据，最后重装机器。卸载 gem 不能解除感染，因为载荷活在 gem 目录之外。同一套基础设施还出现在 PyPI 包 pystr-codec（0.1.0–0.1.2）上，记为 MAL-2026-18432。

干净版本上架两小时后被换掉 extconf 里一行构建逻辑都没有 下载 Bun 跑 index.js 读五十一处凭据 加密外传 往 MCP 配置里塞假服务器 四十五秒查一次令牌 失效就删家目录 先清进程再换设备轮换
4 口径三种

三个数字都算对，唯一在野的那条是六点五分

微软 2026 年 11 月补丁日 · MSRC 口径 1,094 条 · BleepingComputer 口径 1,235 条 · Tenable 口径 1,093 条 CVE-2026-124194 Outlook 欺骗 6.5 Moderate 唯一在野 · KEV 死线 11-24

十一月补丁日最大的新闻其实不是"又破纪录了"，而是一个月前刚破过——十月是 1,411（BleepingComputer）或 1,413（Tenable），十一月是 1,235 或 1,094，连续两个月过千之后，"一千多条"从紧急状态变成了地板价。

先把数字对齐，因为今天不同来源给的三个数都"对"。MSRC 官方发布说明写：这次发布含 1,094 条微软 CVE（Windows 726、Office 174、SQL Server 59、开发者工具 53、SharePoint 27、Azure 20、Exchange Server 9、Defender 1、其他 25），另外重新发布 165 条非微软 CVE 但不含 Chrome；这 1,094 条里有 1,093 条是微软自己作为 CNA 分配的，Tenable 报的 1,093 就是这一栏。BleepingComputer 报 1,235，因为它把 Edge（Chromium）那一栏 142 条也算进来了，并且不含本月早些时候已经修掉的 108 条（Entra 设备注册 1、Mariner 82、Edge 25）。

分类也跟着口径漂：BleepingComputer 的分布是 536 提权 / 296 RCE / 157 信息泄露 / 46 DoS / 27 安全功能绕过 / 22 欺骗 / 142 Edge；Tenable 的是 535 提权 / 296 RCE / 156 信息泄露 / 46 DoS / 27 绕过 / 22 欺骗 / 11 篡改。差异不大，但足够说明"这个月的严重漏洞有几个"这个问题没有唯一答案。

唯一被在野利用的那条，是本月的低分。CVE-2026-124194，Microsoft Outlook 欺骗漏洞，CVSS 3.1 6.5（AV:N/AC:L/PR:N/UI:R/S:U/C:H/I:N/A:N），微软自己的等级是 Moderate。机制是：未认证攻击者发一个特制的邮件文件，说服用户用 Outlook 打开；打开后 Outlook 会去连一个攻击者控制的网络位置，并且不显示平常那个"外部内容"警告；连接过程里 Windows 自动尝试认证，把用户的 NTLMv2 哈希送出去。哈希可以离线爆破，也可以直接拿去做中继。预览窗格不够，必须真的打开文件。

受影响的不只是 Windows：Outlook 2016、Office 2021 LTSC、Office 2024 LTSC、Microsoft 365 Apps 企业版都在列表里，所以只装 Windows 累积更新不够，得单独跑一次 Office 更新，再重启 Outlook。CISA 已在 11-10 把它收进 KEV，联邦机构死线 11 月 24 日。

一个值得记的细节：Tenable 说这条是一位与 Anthropic 的 Claude 模型合作的安全研究者报的，但没有点名研究者，也没说是哪个模型版本。同一周里，Mozilla 那边也说 Firefox 160 修的洞里约四分之一由 OpenAI 的研究员提交——两家浏览器的补丁量正在被 AI 一起推高。

同批的最高分反而是 Important：CVE-2026-120002（SharePoint 授权不当，9.9）和 CVE-2026-109467（Azure DevOps 认证不当，9.9）。四个 9.8 是 112967（Xbox Live 网络服务堆溢出）、116928（Windows Search 组件越界写，可经 Exchange 附件索引零点击触达）、119958（Windows LDAP 越界写）、119990（Azure OpenAI 关键功能缺认证）。ZDI 把其中 30 条判为"可能蠕虫化"。

另外记一笔不要被 feed 带偏：CVE-2026-100223（Windows NTFS 提权，7.8）这一周被若干个情报源标成"已在野利用"，而 MSRC 自己的公告写的是未公开披露、未被利用、"利用可能性较低"、仅本地。它是常规补丁，不是零日。

Adobe APSB26-191 · 11-10 发布 · 24 条 CVE · 18 Critical · 6 条 10.0 · Priority 2（30 天） 三行公告与 CVE 记录的 PR 值不一致 · 两次跨档 · Adobe 称无在野

11 月 10 日，Adobe 发布 APSB26-191，修 Adobe Connect（Windows 本地部署 12.12 及更早）的 24 条漏洞，定级 Priority 2。18 条 Critical、4 条 High、2 条 Medium。Adobe 明说：不知道有任何在野利用。

六条 10.0：CVE-2026-121351 与 121354（路径穿越，CWE-22）、121352（授权不当，CWE-863）、121353（CRLF 注入，CWE-93）、121356 与 121889（SSRF，CWE-918）。其中五条共用完全相同的向量 CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:N——四种不同的弱点类，一个向量字符串。

这不是今天的问题。问题是另外三行。Adobe 是这 24 条全部记录的 CNA，也是唯一给它们打分的机构；每条记录只有一份 CVSS（来源 psirt@adobe.com，类型 Primary），vulnStatus 全是 Received，NVD 还没分析，所以记录里没有任何"第二种读法"。而在三行里，Adobe 公告页上印的向量，和 Adobe 自己提交的 CVE 记录里的向量不一样，差的正是权限要求。

三次方向一致：公告说不需要权限，记录说需要低权限。Adobe 自己的评级页把 Critical 划在 9.0–10.0、High 划在 7.0–8.9，所以按公告读的人看到两个 Critical，按记录读只有 High；第三条方向相反——公告叫 High，记录把它抬成 Critical。第四行还能证明这不是统一规则：CVE-2026-121902 同样是 SQL 注入、公告上分数和向量与 121900 一字不差（9.4、PR:N/UI:N/S:U），但在记录里它保留了 PR:N 和 9.4 Critical，只有 121900 掉到了 8.3。

这件事的影响不是学术性的：PR:N 意味着"不用登录就能打"，PR:L 意味着"得先有一个低权限账号"。在补丁优先级排序里，这两个条件的差别经常就是"今晚加班"和"下周排期"的差别。而两句话都出自同一家厂商的同一次发布。

7. OpenSSH 已在野：16 条成功链，一个跑不起来的后门

这条我们在 11 月 6 日期写过本体（CVE-2026-123158，musl 的 crypt() 出错返回星号，刚好等于 shadow 里那个星号）。今天的新增量是它已经被打了。时间表极短：11 月 5 日 OpenSSH 10.6p2 修复发布；约 4 小时后出现 PoC；Previdian 记录 11 月 6 日首次成功利用；GreyNoise 记录的首个确认成功是 11 月 7 日 00:46 UTC，距修复约 40 小时。GreyNoise 追踪的活动方编号为 GT10，在其东南亚蜜罐上做了"成熟的入侵"：系统与容器侦察、查云元数据服务、读密码哈希与 root 的 SSH 密钥、改 authorized_keys 做持久化，共 16 条成功利用链 / 6 个源 IP。同期背景噪声是 2750 万次 22 端口扫描与 2010 万次 SSH 会话尝试——GreyNoise 自己提醒，这些不等于 SSHole 利用。一次得手后装了 TAC Agent：Python C2 代理，支持命令执行、系统侦察、文件上传下载、自更新，没有内置持久化（攻击者靠加开机服务补）。它的 C2 tac.vpnla[.]org 不可达，所以从未收到任务。注释、日志、报错都是中文，Ars Technica 说它看起来是 AI 生成的。Previdian 侧是 20 次尝试 / 13 个 IP / 9 个国家；watchTowr 在 11 月 6 日看到的活动与僵尸网络、挖矿相关；芬兰 Defused 的措辞最保守——"少数行为者"，未大范围扩散。KEV 已在 11-09 收录，死线 11-12。
