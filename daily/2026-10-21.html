十五分钟、九十四分钟、十二年半：今天所有的事，都是"窗口期"的事

PHP 的两枚 9.2 分核心 RCE 补丁还没发出，安全公司给出的预测是"发布后 15 分钟开始大规模攻击"；eMudhra 从收到报告到浏览器完成封锁只用 2 小时 53 分，可非浏览器客户端到今天还在信任那八把钥匙；OVHcloud 的 CLI 被换包 94 分钟后才下架，全程没经过 CI/CD；而英国监管机构刚公布的那起事件，入口是一个 2012 年创建、密码 Password1、活了十二年半的测试账号。防守方的反应速度差，比漏洞本身更能决定结果。

1 严重

PHP 双核心 RCE（PHP2Shell）：补丁还有一小时才发，而窗口期被算成了"15 分钟"

CVE-2026-109618 / CVE-2026-109619 · 补丁定于 2026-10-21 14:00 UTC（北京 22:00） CVSS v4.0 9.2 ×2 · 截至成稿无确认在野、不在 KEV

PHP 安全团队把两枚 CVSS v4.0 9.2 的核心远程代码执行漏洞的紧急修复定在 2026-10-21 14:00 UTC（北京时间 22:00），编号 CVE-2026-109618 与 CVE-2026-109619，社区昵称 php2shell。截至本文成稿（10-21 13:00 UTC），补丁尚未发布，官方仍未公布受影响版本、修复版本与根因。漏洞在解释器本身——不在插件、不在框架，改 CMS、换主题、升 WordPress 版本，一样挡不住。

这事的起点不是官方公告，是一次泄密。两枚漏洞原定 10-22 在禁运期内披露。10-20 白天 Hacker News 出现一个帖子，声称两枚 PHP RCE 是 CVSS 10.0、影响 PHP 5 起所有版本、自动化利用工具已经全网泄露；帖子随后被删除，发帖人自己承认证据只有 source: trust me, bro。但 PHP 团队当晚 19:33 UTC 就发布提前通知：发版提前到 10-21，并且保留随时再提前的权利——理由是"细节已经公开，或发现活跃利用证据"。这句话的分量比公告本身重。

已经被确认的部分：

  • 官方评分 9.2，不是 10.0：泄露帖里的满分是营销数字，PHP 官方给的是 CVSS v4.0 9.2；watchTowr 表示已复现 109618，并明确"漏洞是真的，细节要等补丁"。演示视频由 Kirill Firsov 放出，署名研究员 LCFR 与 Calif.io
  • 只有 8.2 / 8.3 / 8.4 / 8.5 有修复：预期版本号 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35（Kevin Beaumont 说法，官方未确认）；8.1 及更早为 EOL，PHP 官方不发补丁，只能指望发行版回移。注意 8.2 的安全支持到 2026-12-31 就结束——它只能当过渡，不是终点
  • 两个官方通告已到位：CERT-EU 2026-018；英国 NCSC 发警报，建议无法立即修复的系统考虑先下线
  • "没有在野利用"这句正在失效：10-21 Cloudflare CTO Dane Knecht 公开表示"已经看到早期攻击出现"，并已针对已知向量下发一版 WAF 规则（所有套餐含免费版），同时强调这是 STOPGAP only；这些规则也只对流量完全经过 Cloudflare 的站点有效。专做电商清马的 Sansec 给的时间表更直接：补丁发布后 15 分钟，大规模攻击开始

技术成因（官方未公布，两套独立分析都指向同一处）。两条路径都落在 ext/session/session.c 的 php_session_rfc1867_callback()，也就是 session.upload_progress 的上传进度处理：

  • 说法 A：堆 UAF。该回调把 post_bytes_processed 与 current_file_bytes_processed 两个 zval * 缓存进 HashTable；第二个请求触发 session 重读与 zend_hash_update，经 zval_ptr_dtor 销毁 HashTable，缓存指针悬空。攻击者在被回收的地址上放可控的 zend_fcall_info / zend_internal_function，下一次使用就会走进 zend_call_function，被导向 system()
  • 说法 B：session 文件格式混淆。filename 被原样写进 session 数据；写入用 php_serialize、读取用 php 处理器时，filename 里的 | 被当成 key/value 分隔符，|O:... 之后的内容被当作合法序列化对象反序列化 → 对象注入 → __destruct；POST 体里带 session id 还能绕过 session.use_only_cookies。关键一点：即使 decode 返回 FAILURE，__destruct 也已经执行完毕
  • 共同点才是重点：入口是预认证的 multipart/form-data POST，默认 php.ini 就够（session.upload_progress.enabled=1 默认开启），只需在上传文件段之前带上进度字段（默认名 PHP_SESSION_UPLOAD_PROGRESS）。前者需要每构建版本的偏移，后者需要应用侧一个 gadget
  • "改配置"这条路基本被堵死：PHP 的一位 release manager 说得直白——"ini 设置救不了你"；Aikido 已撤回早前"关掉 session.upload_progress.enabled 就行"的建议。不过在补丁到位前，关闭该特性、开 session.use_strict_mode、统一 session.serialize_handler，仍是多数团队实际在做的止血动作

暴露面有多大。W3Techs 的口径是 PHP 覆盖 69.3% 的"已知服务端语言"站点。Mallory 统计到约 88.4 万台公网主机 banner 报的是 PHP 8.1 或更早（约占报了版本的主机 59%），另有约 74 万台只报 PHP 不报版本；研究者 Silas Cutler 粗估可能受影响主机超过 130 万台，Henk Poley 用 Shodan 数到190 万台以上。这些是 banner 计数，不是已确认可被利用的系统——但 EOL 那部分性质确定：没人会给它们发补丁。

现实里的反应已经跑到监管前面。荷兰 NOS 报道，DigiD、MijnOverheid、荷兰众议院网站、Tweakers、以及荷兰国家网络安全中心（NCSC-NL）自己的站点在补丁发布前下线；日本 ITmedia 报道 Kodmon、Shadowverse: Worlds Beyond、Sakura Rental Server 紧急维护，BASE、Xserver 预期跟进；WordPress 插件 The SEO Framework 的开发者直接把自己服务器关了。

值得关注的原因：

  • 窗口期不再是周，是分钟。15 分钟不是危言耸听，它是 2026 年的操作现实：补丁 diff 一公开，反推利用以小时计。准备工作必须在补丁之前完成——盘点清楚每一台跑 PHP 的机器（含容器、镜像、控制面板、厂商设备内嵌的 PHP），并把"今晚谁能升、谁能重启"落到具体的人
  • EOL 池子是这次真正的死结。支持分支再快，也救不了那八十多万台跑 8.1 及更早的主机。它们只有三条路：升级、隔离（VPN / IP 白名单 / 反向代理后置）、下线
  • "没有在野"与"安全"之间没有等号。Cloudflare 已经看到早期攻击，官方公告还没出——这两个事实可以同时为真，而这正是最需要动手的时刻

eMudhra 八把中间 CA 私钥：取值是 4、56、66…… 浏览器两小时五十三分完成封锁

2026-10-17 20:06 UTC 收到报告 · 10-20 主流平台全部封锁 CVE-2026-113470 / CVE-2026-111943 · 不在 KEV · 无已知利用

印度 CA eMudhra（emSign 品牌）的 8 张中间 CA 证书私钥被发现在生成环节存在致命缺陷：P-384 私钥本应有约 384 位的密钥空间，实际取值是 4、56、66、115、155、156、230、237，全部小于 256。攻击者最多试 256 个数就能还原私钥，然后为任意域名签发一张会被信任的 HTTPS 证书。

时间线紧得罕见。Mozilla 10-17 20:06 UTC 收到报告，22:59 UTC 就完成 OneCRL / Remote Settings 分发——2 小时 53 分；Chrome 更早，19:45 UTC 通过 CRLSet 按 SPKI 哈希封锁 6 张 TLS 中间证书，不需要更新或重启浏览器，交叉签名证书一并覆盖；10-19 Apple 完成封锁、10-20 Microsoft 完成。Chrome 同时说明：封锁前 CT 日志里没有任何链到这 6 张 TLS 中间证书的证书，所以不存在"已被默认信任的伪造证书"。

成因初步指向"脚本写错"。eMudhra 在 Mozilla 的 bug 里说明：当日（2025-04-30，Utimaco HSM）密钥生成仪式所用脚本存在缺陷，额外产生了一套更弱的密钥，而这套弱密钥被误用于签发；RSA 中间证书走另一套流程不受影响。Mozilla 还注意到一个历史线索：这 6 张 TLS 中间证书曾在 2025 年一次 CRL 签名无效问题中出现过，正在追问"错误的密钥是怎么签出那些吊销列表的"——这是线索，不是成因定论。

发现者是个化名研究者。化名 Wayne 的独立研究者（据报可能借助 AI 辅助）找出这些密钥，通报了四家浏览器/平台厂商，并建了站点 emudhra.we-have-a-problem.com；10-20 他在上面发布了一条用其中一张受影响证书私钥签名的消息："We have a problem here – Wayne"。

结构性问题：浏览器封锁 ≠ 生态封锁。浏览器是唯一能"推送"吊销数据的客户端；而 Go 编译出的二进制、用 certifi 的 Python 程序、Node 服务、自建或内置信任库的设备、容器镜像、API 客户端、大量工控与网络设备——它们不看 CRL 也不看 OCSP，很多在查不到吊销状态时还会 fail-open。它们会一直信任这 8 张中间证书，直到各自的代码或根证书包被更新。所以修复清单是一张表：

软件 / 生态修复版本与状态

代价也是真的。移除根比封锁中间证书更狠，会连带切断所有正当链到该根的证书。Chrome 43 预计在 10-27（太平洋时间早晨）摘掉 emSign ECC Root CA - G3；eMudhra 估算约 3 万张证书需要迁移，其中约 97% 走 ACME，并提出把订户迁到链到 emSign Root CA - G1（RSA）的中间证书，之后称已停止在 G3 根下签发。Mozilla 提醒：根移除后部分服务器对非 Firefox 用户会不可用，直到它们换链——遇到这种报错不要用"关掉证书校验"去修。需要提前排查的是：自家服务端证书、mTLS 客户端证书、代码签名链，以及写死了指纹或内置 bundle 的设备。

值得关注的原因：这次不是"某个洞被打了"，而是信任锚本身失去完整性，失效方式还极其低级——一个能产出数值 4 的密钥生成脚本，运行了约 18 个月没有任何自检把它拦下来。eMudhra 声称除一张 G3C DV TLS 中间证书外其余未部署生产、所有受影响证书都未签发终端实体证书——这是 CA 声明加 CT 记录佐证，不是独立审计，Chrome 已表示还在复核 eMudhra 留在其根库里的另一张根证书。结论只有一句：把"根证书包"当成需要版本管理、需要盘点、需要重新构建的组件——它现在和操作系统补丁一样重要，而绝大多数资产清单里根本没有它。

OVHcloud CLI：五个已发布的版本被原地替换，94 分钟窗口，CI/CD 整条流水线根本没被碰过

0.11.0 – 0.15.0 · 10-19 14:47 → 16:21 UTC 下架 供应链投毒 · 官方已确认 · 建议更换磁盘上全部密钥

攻击者接管了一名贡献者的 GitHub 账号，进入 OVHcloud CLI 仓库，把 0.11.0 到 0.15.0 这五个已经发布出去的版本包与校验和直接替换掉。篡改版本于 10-19 14:47 UTC 上线，16:21 因客户报告被发现并阻断，存活约 94 分钟。

这件事最关键的一句话来自 OVHcloud 的 CEO 本人："整套 CI/CD 流水线——单元测试、功能测试、CVE 检测——都没有受到影响。" 原因是它根本没走流水线：当时 GitHub 的 release immutability（发布不可变性）是关闭的，一个有足够权限的账号可以绕过所有检查，直接改动已经发布的 release 资产。这不是"防线被突破"，是"防线外面有一条不需要过检的路"。修复方式是一个开关——现在打开了。

  • 干净的：0.10.0 与最新的 0.16.0、源码构建、Docker 镜像
  • 被污染的：0.11.0 – 0.15.0 的发布包，覆盖 macOS（Intel / ARM）、Linux（x86_64 / ARM64）、Windows（x86-64）
  • 载荷目的：从磁盘上捞密钥与令牌。厂商对恶意代码质量的评价很低（"二进制质量很差"），但目的明确；CEO 的原话是"如果中招，它可以一路做到底，请更换磁盘上的所有密钥"——不是删包，是换密钥
  • 溯源线索指向 GlassWorm，但这是线索不是定论：OpenSourceMalware 称该账号可能已被控制超过 6 个月，并用一个 Solana 钱包指标把活动关联到 GlassWorm；公开仓库中可见 2026-03-05 的一次脚本化历史重写，以及隐藏的 preinstall.js 加载器，解码后经 Solana memo 死信箱取第二阶段。该机构并未分析本次载荷

值得关注的原因：供应链攻击的入口正在从"污染源码"移到"污染已经签好名的分发产物"，而多数团队的防线假设还停在源码与 CI。这条链上每个环节都"正常"：仓库是真的、release 页面是真的、校验和文件也是真的（因为它一起被换了）、签名可以是有效的——唯一错的是这个产物不是作者构建的那一份。今天最便宜的一条加固，就是去把自家与依赖项目的 release immutability 打开，并让发布资产只能由 CI 产出。顺带一句：用过 0.11.0–0.15.0 的，按凭据泄露处理，不要只删包。

Phantom：勒索团伙把自己的 AI 工作台留在公网上，8257 条对话成了证据

SOCRadar · 2026-09 末发现 · 10-20 公开 INC 与 The Gentlemen 附属 · 7 台服务器暴露

SOCRadar 威胁研究团队在 2026 年 9 月底通过开放目录发现一台暴露在公网的攻击者服务器，里面有 AI 会话数据库、一个持久知识库，以及一套叫 Phantom 的"自主红队杀伤链框架"源码；顺着其中的凭据与配置又定位到另外 6 台，共 7 台。10-20 公开。

规模用数字说话：133 个会话 / 8257 条消息；界面是 OpenCode，模型经 OpenRouter 调用 Claude Opus 4.6 与 Kimi K3；AI 支出超过 23,920 美元（说明是持续使用，不是玩票）；关联 INC Ransomware 与 The Gentlemen 的附属成员；记录里出现 62 家具名组织（36 家在美国；工业制造 16.1%、医疗 14.5%）；俄语操作者在 06:00–14:00 UTC 最活跃。

AI 在里面干什么，记录写得很具体：侦察规划与目标评估、技术选型与命令生成、攻击工具排障、审阅窃得数据挑出有价值的、在失陷主机上协调 living-off-the-land、起草勒索话术。但人始终在环——指令里常见"协调任务并等待批准"，说明它是人类指挥的助手，不是自主攻击者。两个细节值得记：模型拒绝时，操作者会改口把活动重新描述成"授权的红队演练"；记录里还有一个标着 WormGPT 的人设提示，SOCRadar 判断那是提示标签与集成模式，不是真接入了另一个无审查模型。

加密不是计划，至少执行过一次。加密器是 Rust 写的，会终止备份与数据库进程、通过直接驱动调用删除卷影副本、给文件加 .INC 后缀；共 46 个按受害方定制的构建，为 6 家准备，计划 10-01 部署。配套工具还有 Phantom 本体（自称"自主红队杀伤链框架"，含 18 个技能模块）、Ghost C2、RevSocks 隧道，以及一枚针对 Quick Heal / Seqrite 的 BYOVD 安全软件杀手。9-30 的一张截屏（经 SimpleHelp 获取）显示某受害工作站正在加密——环境里不只有计划材料。

初始访问还是那几个没打补丁的边缘设备：FortiClient EMS CVE-2026-35616（7.4.5–7.4.6，04-05 修复，04-06 进 KEV；操作者记录称涉及 2,236 台系统 / 4,140 个受管端点）、SimpleHelp CVE-2024-57727（242 个独立 IP）、cPanel CVE-2026-41940（49 起声称的入侵）。

有独立印证，也有边界。Atos 的 Threat Research Center 另外发现一台配置错误的攻击者 HTTP 服务，里面有运营日志、工具、OpenCode 与 Phantom；Atos 联系可识别受害方后，发现部分记录中的组织后来确实出现在 INC 的泄露站上。但 Atos 没有复现 SOCRadar 给出的精确消息数与加密器数量——方向一致，细节口径不同。

值得关注的原因：这是攻击侧的 AI 智能体部署，不是"AI 被攻击"。攻防两侧第一次可以用同一套词汇描述同一件事：工具调用、知识库、人在环审批、上下文持久化。更值得记的是它的失败方式——这群人不是被溯源打掉的，是把自己的工作台留在了公网上。那份"共享记忆"帮他们维持了跨天、跨目标的连续性，也在服务器暴露的那一刻变成了最完整的证据链。对防守方这是一句反问：我们自己的 AI 会话、知识库、代理配置，现在躺在谁的开放目录里？

5 严重

APT28：把"一像素的 Edge 窗口"当下载器，在海军造船厂手动操作了两个月

Symantec Threat Hunter Team · 2026-10-20 公开 · 代号 Swallowtail 无 CVE · 两个北约成员国三家机构 · 2026-07-24 至 09-24

与俄罗斯 GRU 关联的 APT28（Symantec 代号 Swallowtail，亦称 Fancy Bear / Forest Blizzard；Recorded Future 称 BlueDelta）攻入两个北约成员国的三个机构——执法机构、海军造船厂、军机发动机厂商。全程使用 HOOKEDGE 后门，在造船厂那条线上手动操作了至少两个月。

先说清边界：受害机构名与两个国家都没有公开。有报道把这次联系到罗马尼亚、西班牙、土耳其，但那是 HOOKEDGE 上一轮（2025-09 至 2026-04）针对政府与外交目标的范围，不是这一批受害方。

入口是宏，手法很旧，包装很新。最早确认的感染发生在 2026-07-24 下午的造船厂：恶意 Word 文档直接从 Outlook 附件缓存里被打开（证明是收到的邮件附件）。AutoOpen 宏做了重度混淆——把 VBA 源码与字符串切成碎片、运行时再拼起来，专门躲静态扫描。执行后落四个文件：VBS 启动器、一对"加载即自动提交隐藏表单到 webhook"的 HTML/XHTML、以及一个批处理。

批处理干的事，是把一个已签名的浏览器变成下载器：① taskkill /f /im msedge.exe；② 清掉 Downloads 里的 *.000、*.tmp、*.crdownload；③ 用 --window-size=1,1 --window-position=10000,10000 --ignore-certificate-errors 启动 Edge，URL 位置放一段 base64 的 data:text/html JavaScript——窗口是 1×1 像素、跑到屏幕外一万像素处；④ 解码后的 JS 去取 webhook.site 上的资源、通过自动点击链接触发下载落盘，内容复制成 .cmd 执行，再把输出传回同一端点、删临时文件。一个完整的 fetch–execute–callback 循环，全部由"可信 SaaS + 已签名二进制"构成，链上没有一个组件是恶意的。

从 7-27 起，二阶段弃用 webhook.site，改用专用 IP 185.82.218.119:443 做任务下发与回传，走 TLS。"活人在敲键盘"有数据支撑：约 30 秒内下发 7 个任务，每个都在前一个完成后 2–8 秒内完成——不是自动化 beacon 的节奏。

  • 凭据手法一（SSH）：把 id_rsa 放进 C:\ProgramData\Adobe、改好权限，随即用它在后台拉起一条持久 SSH 隧道——从攻击者服务器直通目标内网，全程不装木马
  • 凭据手法二（NTLM）：一段自包含 PowerShell 在本机回环地址起监听，强制本机向它认证，抓走 NTLM 握手
  • 新工具 ld.exe：此前未见于文档的反射加载器，命令行收一个加密文件与一把解密密钥，内存解密后调用导出函数 ExecuteLoader；加密载荷未被取到，最终功能仍未知；经 SSH 用 curl 投放
  • 时间线：7-24 首次感染 → 7 月底一周内反复回到同一台主机、偷凭据、开隧道、铺工具 → 9-24 最后一次相关活动。上一轮 HOOKEDGE 由 Recorded Future Insikt Group 在 2026-08 首度公开，与 APT28 早年对 diplomats 使用的 HEADLACE 有大量代码与战术重叠

值得关注的原因：这件事一枚 CVE 都没有。防线是"宏 + 可信服务 + 已签名进程"三件套拼出来的，任何单点拦截都拦不住：邮件网关看到的是普通 Word 附件，EDR 看到的是签名正常的 msedge.exe，网络侧看到的是访问 webhook.site 这种合法 SaaS。所以检测抓手只能是行为：离屏的 1×1 像素浏览器实例、指向 webhook.site 的出站、回环地址上的 NTLM 认证、不该出现在工作站上的 SSH 隧道、父进程是浏览器或终端的 curl。而"三十秒七个任务"的节奏说明，这类行动不是撒网，是对着高价值目标做人工干预——也更难被"可疑流量阈值"发现。

6 治理

两份申诫：一个 2012 年的测试账号，密码 Password1，活了十二年半

ICO · 10-14 发出决定书 · 10-20 公开 · 无罚款 无 CVE · 42GB 被窃 + 182.7GB 被加密 · 3,300 人多数为儿童

英国信息专员办公室（ICO）在 10-20 公开对 Ogi Networks Limited（ONL） 与威尔士地方政府数据机构 Data Cymru 的申诫。起因是 2024-11-01 的一起勒索软件攻击：攻击者从一个 2012 年创建、密码为 Password1 的 Active Directory 测试账号进去，偷走 42GB、加密 182.7GB，涉及 3,300 人，大多数是儿童。

  • 入口：账号 Test2，ONL 于 2012-01-13 创建（当时为在正式用户迁移前测试访问），密码 Password1。ICO 引用 Bitwarden 强度工具：very weak，1 秒内可破。该账号存在超过 12 年，且"要么一直有效，要么在事件前被意外重新启用"；Data Cymru 的 AD 里没有例行审计能发现并停用多余账号
  • 横向：三台受影响系统的本地管理员账号用同一个密码，部署后从未复核，十二年半没换过——从一台机器抓本地哈希就能登进另外两台
  • 窃取先于加密：42GB 来自主域控制器、文件服务器与一台内部 SQL Server，随后 182.7GB 被加密。这意味着"从备份恢复"解决不了数据已经泄露这件事
  • 合规缺失：ONL 违反 UK GDPR 第 32(1)(b)、32(1)(d)；Data Cymru 违反第 28(4)、32(1)(b)、32(1)(d)——与 ONL 之间没有含法定数据处理条款的合同，未书面明确 ONL 提供的 AD 服务如何交付、监控、审计，责任划分留了空档，也未确保休眠的 Test2 被清除或升级密码
  • ICO 原话：调查负责人 David Doodson——"Password1 不是一个合适的密码，它是一扇对恶意行为者敞开的大门。"他同时强调责任不在单一方：ONL 建了测试账号，而 Data Cymru 保留对自身网络的整体控制权，包括指示 ONL 建号或删号的权力
  • 事后：两家已补签合规的数据处理合同、加强账号复核、在远程访问上启用 MFA；ONL 称攻击后一周内审完 Data Cymru 网络上的每个账号、关停不需要的、并引入独立专家，事件仅限于它为 Data Cymru 托管的那台服务器。ICO 未公布任何 IOC，也未公开归因

值得关注的原因：今天六件事里，唯一一件完全没有漏洞的。它把"窗口期"这条主线拉到另一个极端：前面几件的窗口是 15 分钟、94 分钟、2 小时 53 分，这件事的窗口是十二年半。它也戳破一个很常见的心理安慰——"安全是供应商的事"。当网络的所有权（Data Cymru）与账号的创建权（ONL）分属两家、而两家都没把"谁负责发现多余账号"写进合同，那个账号就会一直活着。外包转移的是工作，不是责任。

速览

7. PAN-OS CVE-2026-0257：勒索团伙开始从 VMDK 里离线刨凭据

Unit 42 在 10-20 的更新里给出战术演进：除此前已知的 Qilin（Spikey Scorpius）与使用 Settra 的团伙，INC（Tarnished Scorpius）也在用这枚 GlobalProtect 认证绕过建未授权 VPN 会话，覆盖教育、金融、医疗、高科技、酒店、制造、专业与法律服务、政府、交通物流、公用事业能源、批发零售共 11 个行业。最要命的一步是直插虚拟化层：某案例里攻击者从 VPN 网关进到 vCenter 管理设备，在那里关掉 ESXi 的 execInstalledOnly，再对域控的虚拟磁盘（VMDK）做离线凭据提取——全程在 guest OS 之外，虚拟机内的 EDR 看不见。Unit 42 还在多起响应里发现同一个误配：GlobalProtect 配置文件被映射到了管理接口的 443/HTTPS 端口（最常见 4443 与 3879），管理面就这么对着公网，浏览器直接连一下就能自测。检测三个抓手：GlobalProtect 日志里的可疑 host ID（aa:bb:cc:dd:ee:ff、00:11:22:33:44:55、WINDOWS-LAPTOP-001、DESKTOP-GP01、GP-CLIENT）、PoC 的硬编码客户端特征（endpoint_os_version 为 Microsoft Windows 10 Pro 64-bit、source_user_info.domain 为空）、以及 vCenter 异常登录与 execInstalledOnly 是否被改过。EPSS 96.9%，KEV 自 5-13。（该 CVE 的在野利用已在 10-12 期报过，本条只记新增战术）

8. Siemens Software Center CVE-2026-110936：8.4 分进了 KEV，因为攻击者用的是正版签名程序

DLL 旁加载（CWE-427 不受控搜索路径），CVSS v4.0 8.4，V4.0.9.8 之前所有版本受影响。Siemens 的说法把这件事讲透了：攻击者用的是一份正版、带有效签名的 Software Center 3.5.8.7，把自己的恶意 DLL 放在同一目录旁边；可执行文件一个字节都没改，签名与哈希全都正常。载体 AllMyBasic.msi 经 ROMULUS ClickFix 面板在官方渠道之外分发，落点是 AppData\Local\Programs 下的 "SM Software Provisioning Service" 目录，持久化走启动项/计划任务，外联 96.62.218.59 与 wizardexpensive.com。时间线值得注意：10-15 发公告（SSA-580366）→ 10-17 更新说明 4.0.9.8 已修复 → 10-19 才承认在野利用。漏洞由 Huntress 的 Jose Oregon 报送。检测思路：看 msiexec 从 AppData 拉起 SiemensSoftwareCenter.exe、同目录出现 activate.bak 或 statinfasta.DB、以及 FTSuite 目录下的 ftc.uml。

9. ROMULUS：一个被重复出租的 ClickFix 面板，六个 IP 在跑同一套后端

Forescout Vedere Labs 在调查一起事件时发现一台服务器上跑着一个叫 ROMULUS 的面板，进一步确认六个 IP 在跑同一套东西——其中 2.27.248.127 正是 Siemens 列出的 AllMyBasic.msi 分发地址。它提供 PowerShell 暂存脚本与被木马化的 MSI 安装包，两条路线：一条发 Stardock 系的 DLL 旁加载包（Huntress 先前报过），另一条发带密码的压缩包塞 LegionLoader；加载器藏在一个用填充膨胀到约 882MB 的可执行文件里，用 RC4 + Base64 与 C2 通信。研究者的判断很关键：这是可复用的投放后端，不是单一硬编码的马服务器——它可能是一个私有面板、一项商业化投放服务、一个附属框架，或者被不同操作者复制走的软件。这意味着"封 IP"只是暂时的。

10. 勒索快照：24 小时 26 家、10 月 677 家、2026 年累计 8704 家

按 10-20 13:50 UTC 的快照：过去 24 小时有 26 家被挂上泄露站，来自 7 个团伙（N0N 10 家、Qilin 9 家、Global Secret Group 2 家），前一日 24 家，7 日均值 37.6 家/天；10 月累计 677 家，2026 年累计 8,704 家。当天值得单独记两条：PingCAP / TiDB Cloud 被 Fulcrumsec 挂出；Baker Donelson 被 Redact 挂出 355GB / 102,390 个文件。以上全部是团伙单方面声称，不是已核实事件。

11. FortiSIEM CVE-2026-106173：补丁发了一周，Horizon3 的 PoC 就到了

CVSS 9.4、未认证路径穿越 → 代码执行，入口是 FortiSIEM 的 gRPC 服务（TCP 27918）。Horizon3.ai 的拆解很典型：根因在 QueryResultReq 的 SendQueryResult()——用户提供的 query-id 未校验就被拼进文件路径（拿到任意写位置），但文件名被固定成 result–0-0-.dat，所以只有任意写还不够；在参数里注入空字节把固定后缀截断，才把"只能写固定名"变成"想写什么写什么"，进而落到代码执行。Fortinet 在 10-12 那周就发了修复版本，PoC 晚一周到——这正是"补丁即地图"的标准节奏。打不了就把 27918 从公网收掉。（10-19 期已记过该 CVE 与厂商公告版本范围矛盾的问题，本条只记 PoC 落地）

12. Bullhorn 停摆与 Ymirlink 900 万条：两起"服务型"事件

10-19，攻击者让招聘/人力 SaaS Bullhorn 下线，并强制所有用户改密码；同日，日本 Ymirlink 称其 Cuenote 邮件投递服务后端系统被窃约 900 万条记录。两起都还没到可复盘的阶段，但指向同一件事："服务型"供应商一旦被打，受害名单不是按客户数算的，是按客户的客户算的。 对照 10-18 期的 ConnectWise（一个应用身份开 173 个租户）、10-20 期的日经（第三次事件、183 万条），这条线在这个月已经是第三次。
