1 无在野 · 公开 PoC · 十年老洞

十年前的账本算错一次，nginx 把 root 交了出去

CVE-2026-123007 · nginx2root · F5 与 Rapid7、Wiz、Xint、Ikotas 同日披露 · 修在 1.31.9 与 1.30.7 CVSS 4.0 记 9.2 · 五条独立 RCE 加一个内核提权 · 128 GB 流量才跑得完

11 月 18 日，F5 一次性发了十个 nginx 的 CVE，修在 1.31.9（mainline）和 1.30.7（stable）。最重的一条是 CVE-2026-123007，Xint 给整套取的名字是 nginx2root：五个 nginx 的 RCE，加一个 Linux 内核 SCTP 子系统的提权，六个洞拼起来能从公网直接拿到宿主机的 root。

先说这条洞本身。HTTP/2 用一套信用额度控制发送节奏：客户端告诉 nginx"你可以给我发这么多字节"，nginx 分两个计数器记账，一条流一个，整个连接再共用一个。客户端取消一个响应时，nginx 把没发出去的额度退回去，但没有检查退完之后有没有超过 2 的 31 次方减 1 这个协议上限。超了之后，下一次 WINDOW_UPDATE 做减法时无符号回绕，得到一个天文数字，再往后某个长度计算变成负数，负数到了内存拷贝那里就成了巨大的无符号计数，一次写穿缓冲区。CWE-191，整数下溢。

这段代码从 2015 年 nginx 引入 HTTP/2 起就在里面（1.9.5），一直到 1.31.8，包括 11 月 10 日的 master 分支。十年，每一个官方发行版都带着它。

Xint 的演示分两段。第一段用 123007 在容器里以 worker 权限执行命令，第二段用一个 Linux 内核 SCTP 的提权洞打到宿主机 root，测试覆盖 AWS、GCP、Azure 和裸机，其中 AWS 那一场是从公网 IP 直接打进去的。那个内核洞从 Linux 4.15（2018 年）就在，目前没有 CVE、没有补丁，Xint 说等各发行版能出修复再公开细节，现在只给结论。

工程门槛要说清楚，不然容易被标题带偏。Rapid7 的 Stephen Fewer 算过：跑通一次需要往目标灌大约 128 GB 的 HTTP/2 数据，10 Gbit/s 下两分钟，1 Gbit/s 下十七分钟，而 nginx 默认连接一小时就断，所以带宽低于 300 Mbit/s 的攻击者根本来不及做完。整条利用还依赖 x86-64 上 glibc 那个被 AVX-512 选中的 memcpy 实现（要 avx512f 与 avx512vl）。前面套了 HTTP/2 终结代理的话，攻击者控制的帧不会被原样转发，大概率也打不通。这些限制说明"打崩一个 worker"很容易，"拿到 shell"没那么容易。但打崩是免费的，公开 PoC 已经在 GitHub 上，一条命令就能让 worker 反复重启。

另外几条也值得单独记。CVE-2026-123633 有个外号叫 Drainbreak，是 worker_connections 快耗尽时的 use-after-free，Metnir 在开着 ASLR 的情况下十分钟打穿，并复现了 OpenResty、Kong、Apache APISIX、NGINX Gateway Fabric 与社区版 ingress-nginx 的崩溃，这几个默认都开 HTTP/2。CVE-2026-123634 要 resolver 加变量拼出来的 proxy_pass 再加一个子请求，Xint 明确说 SSI 也可能走到同一个 bug，所以"把 mirror 关掉"不等于安全。

为什么值得关注：第一，这次是 AI 找到的，而且是流水线找到的。123007 是一名研究员在做 ZeroDay Cloud 2026 准备时挖到的，剩下四条是 Xint 的自动化装置在没人干预的情况下扫出来的：指到 5 万行 nginx 代码上，90 分钟出高严重度结论，再过 10 分钟有可用利用。同一天独立撞上同一批洞的还有 Rapid7、Wiz、Ikotas Labs、Metnir 四家。当五支队伍用同一类工具在同一块代码上撞车，"这个洞以前没人看见"这句话正在失效。

第二，容器不是边界，今天又被演示了一遍。nginx 跑在 Docker 里，worker 权限被打穿，再用一个 2018 年就存在的内核洞提权，宿主机的 root 就到手了。所有把"我们跑在容器里"当成一层防护的架构，在拿到内核洞的攻击链面前都只是换了个进程树。

第三，修完之后的责任边界比补丁本身更难。自建 nginx、K8s Ingress 控制器、API 网关、托管负载均衡、CDN 边缘节点，这五样东西的补丁责任人不是同一个，而它们对外的表现都是"前面有个 nginx"。今天该做的第一件事不是升级，是先列出这张表：谁在替我们跑 nginx，他什么时候升。

第四，reload 这个习惯要改。Xint 在公告里专门提了一句，reload 只换配置不换可执行文件，升级完必须 systemctl restart nginx。这类"升了但没生效"的情况在事故复盘里出现频率极高。

客户端授额度 服务端响应排队待发 取消请求 nginx 退还剩余额度 不校验是否超过 2 的 31 次方上限 减法回绕 长度计算变成负数 负数当无符号计数 写穿堆缓冲 Worker 里执行 权限是 nginx 用户 内核 SCTP 提权 容器边界没了 十年所有官方版本 全部带有这段代码

一次更新四条 KEV，其中一条厂商明说不修

CVE-2026-90436 Apache Axis · CVE-2026-90817 REDCap · CVE-2024-10441 Synology · CVE-2026-40217 LiteLLM KEV 2026.11.18 版共 1,786 条 · 四条里三条只给 72 小时

CISA 在 11 月 18 日一次往 KEV 里加了四条。目录版本 2026.11.18，总数 1,786 条，其中 361 条标注了已知勒索利用。最该看的是 Axis 那条，因为它是唯一一条"没有修复版会来"的。

漏洞在 Axis 1.x 处理 SOAP fault 的时候。fault 里带一个 exceptionName 字段，Axis 会去加载这个字段点名的类，如果同时还带了 string 元素，还会用字符串构造函数把它实例化，全程没有先确认这个类是不是 AxisFault 的子类。光是把类加载进来，静态初始化块就跑了，classpath 上只要有一个可用的 gadget，代码就执行了。不需要凭据，不需要交互，不需要事先落脚。

真正要命的是时机。这段解析发生在 Axis 还在判断这条消息该投给哪个服务的阶段，而认证是在后面的 handler 链里做的。也就是说，一个"必须登录才能用"的 SOAP 端点，在这条洞面前和裸奔没有区别，攻击代码跑在认证之前。任何"我们有 API key 校验"的自我安慰在这里都不成立。

Apache 的话说得很直白：这个项目不打算为 Axis 1.x 出一个修复这个问题的版本。唯一的官方路径是一个源码 commit（41f3b4e），改的是 fault 反序列化的两头：加载类时不跑静态初始化，构造对象前先确认它确实是 AxisFault 子类。要修，自己编译自己部署。想省事就迁到 Axis2，那是另一套代码，没有平替升级路径。

剩下三条各有各的形状。Synology 那条是 2024 年的 CVE（CVE-2024-10441，9.8，Pwn2Own 2024 的产物，system plugin daemon 的输出编码问题），补丁当年就发了，DSM 修到 7.2.2-72806-1，BeeStation OS 修到 1.1-65374，两年半之后才进 KEV，说明这两年半里一直有人在打没升的机器。

REDCap 那条是 9.8 的代码注入，知道一个有效的公开调查问卷 hash 就能从问卷页面走到一个不该走到的控制器路由。Unit 42 在 10 月 7 日就记录了针对公网 REDCap 的 XMRig 挖矿，无文件执行、crontab 持久化、往里塞 SSH 公钥。LiteLLM 那条最"新派"：/guardrails/test_custom_code 这个 URI 允许对字节码做重写，等于把"执行任意代码"做成了一个功能，CISA 给的期限是 12-02。

为什么值得关注：第一，"EOL 组件"不是历史问题，是当下资产表里的空白。2026 年没人会主动装 Axis 1，但它被打包在中间件、集成平台、老 ERP 连接器、设备固件里卖了十几年，厂商通常不会在文档里写。一个安全团队完全可能真诚地认为自己没有 Axis 暴露，实际上某台 SOAP 网关底下跑着它。

第二，认证跑在漏洞后面，这类情况比想象的多。判断一个端点安不安全，不能只问"要不要登录"，要问"这段解析发生在认证之前还是之后"。Axis、昨天那条 Puppet、前几天的各种反序列化，全是同一个顺序问题。

第三，KEV 的期限正在从两周往三天压。四条里三条是 11-21，从加进去到截止只有 72 小时，而且 Synology 与 REDCap 两条都带强制取证要求。等 KEV 再动的人，现在连排期都排不出来。

第四，Axis 这条的最后手段是断网。如果三天内编不出补丁，就把 SOAP 端点从网络上摘掉，或者在入口把带 exceptionName 的 fault 报文拦掉。这不是修复，但能把窗口从敞开变成窄缝。

SOAP 报文里塞一个 fault 元素 exceptionName 点名任意类 直接加载 静态初始化块先跑 对象还没实例化 解析发生在认证之前 登录要求形同虚设 Apache 明确说不出 Axis 1.x 修复版 只剩一个 commit 要自己编译自己部署 三天内修不了 就把端点从网上摘掉
3 在野一年 · 签名驱动 · 主体无 CVE

签名是真的，杀毒软件也是真的被杀掉了

AuditTeam / OpsAgent · Kaspersky 11-18 公开 · CVE-2026-19193（BYOVD） 主体无 CVSS · 约 220 个进程被成批终止 · 勒索信写成审计账单

Kaspersky 在 11 月 18 日把这条讲完了：一个叫 AuditTeam 的团伙，用自己写的框架 OpsAgent 打了一整年，受害者分布在俄罗斯、意大利、菲律宾、中国香港、塞内加尔、芬兰、中国等地，时间跨度从 1 月 5 日（GitHub 上第一次提交）一直到至少 10 月。

这伙人有两个地方值得单独拿出来讲。

第一个是那个签名驱动。OpsAgent 带一个"杀软杀手"模块，装的是一个有正规数字签名的、伪装成江民杀毒（Jiangmin KV 系列）的驱动，通过 \KvCorePortX0 这个 minifilter 端口通信，收到 0x1D 命令加一个进程名，就把那个进程干掉。杀名单大约 220 条：Microsoft Defender、Sysmon、Splunk、Wazuh agent、TeamViewer、Veeam、Acronis，以及 SQL Server、MySQL、MongoDB、Redis 这些数据库进程。驱动签名是真的，所以 Windows 会信它，除非开了易受攻击驱动黑名单、HVCI，或者干脆用应用控制策略禁掉。这个驱动本身的问题被追为 CVE-2026-19193，公开 PoC 已经存在，教科书式的 BYOVD。

第二个是那份"审计报告"。加密完成之后落下的勒索信，不说自己被加密了，说的是"我们为你做了一次安全审计，请支付 Audit and Consulting fee，付了我们给你一份漏洞报告，不付就把数据公开"。这封信是加密模块自己落的，也就是说，读到这封信的时候文件已经加密完了。把勒索包装成专业服务，是今年明显的一个话术趋势：它降低受害者第一时间报警的意愿，也让内部沟通多绕一圈。

工具本身的成熟度也不像小团伙。OpsAgent 5.2.8 的功能被 Kaspersky 形容为"接近 Cobalt Strike"：文件与进程管理、提权、窃取与伪造令牌、键盘记录、截屏、经 SMB 和 HTTP 把受害机器串成链做横向。加载器一年换了三代，4 月的 C 加载器（OLLVM 控制流平坦化）、6 月的 .NET 加载器（NtQueueApcThread）、9 月的 Rust 加载器（在自己进程里解密执行，不再注入）。C2 走 CloudFront 子域，配置放在公开 GitHub 仓库里，按 IP 封堵没有意义，因为 CloudFront 的地址是共用的大众 CDN。研究者还注意到代码里有明显的大模型痕迹，比如几个注入例程几乎一模一样，只有参数不同。

为什么值得关注：第一，"签名"这两个字已经不是信任依据了。过去十年我们教用户看签名，现在攻击者直接买、借、偷一个签名来用。防线必须从"有没有签名"挪到"这个签名的主体应不应该出现在这台机器上"。

第二，杀软被杀的那几十秒是最关键的检测窗口。220 个进程被成批终止，这个行为本身噪音极大，但前提是你的日志不在被杀的那批里。把 EDR 日志实时外发、给安全代理加防篡改保护，比事后找 IOC 有用得多。

第三，AI 让"小团伙做出国家队工具"变成了常态。Kaspersky 的判断是，代码里那种高度重复的注入例程指向大模型辅助开发。这条和昨天 GTIG 那份自动化利用流水线、今天 nginx 那五个 AI 找出来的洞，是同一件事的三张脸。

第四，勒索话术在变，处置流程不能跟着变。不管信上写的是"审计费"还是"解密费"，读到它就意味着加密已经发生，第一步永远是隔离与取证，不是谈判。

4 四个 9.9 · 无 PoC · 低权限即可

构建服务器上一个参数，CI 里的密钥就全归别人

CVE-2026-132231 / 132232 / 132233 / 132234 · JetBrains TeamCity 2026.1.3 与 2025.11.7 之前 CVSS 3.1 均 9.9（PR:L，S:C）· 四条全在版本控制连接配置

JetBrains 在 11 月 18 日发了 TeamCity 的四个高危：2026.1.3 与 2025.11.7 之前的版本里，四条独立的远程代码执行，CVSS 3.1 全部 9.9，向量是 AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H。翻译一下：只要能登录，就能在构建服务器上执行代码，而且影响范围跨出 TeamCity 本身（S:C），因为构建服务器上挂着部署凭据、制品仓库密钥、云平台令牌。

四条分别是：Perforce 设置里的 best-fit 字符映射（132231）、Perforce 设置里的参数注入（132232）、构建属性注入（132233，CWE-23）、Mercurial VCS root 设置里的参数注入（132234）。四条全在"版本控制连接配置"这一块，这不是巧合，是同一个设计缺陷的四种表现：把用户填的仓库地址、用户名、分支名拼进命令行，而没有把它当成数据。

这条的时间线反而简单：披露当天进 NVD，没有公开 PoC，没有 KEV，CISA 的 SSVC 记 exploitation 为 none。但 TeamCity 的用户群体决定了它不能等：这是那种"装在内网、只给研发用、默认信任里面所有人"的系统。

为什么值得关注：第一，CI 服务器是供应链里最划算的目标。打一个开发者的笔记本，得到一个人的权限；打构建服务器，得到的是所有经过这条流水线的东西。签名、制品、发布通道全在这一层，而这一层通常放在内网，被默认为安全。

第二，PR:L 不代表门槛高。TeamCity 在很多公司是全员可登录的，任何能提 PR 的人大概率也能建分支、改自己的构建配置。9.9 分里那个 L 是"低权限"，不是"需要管理员"。

第三，参数注入这类洞扫不出来。没有畸形输入、没有异常日志、没有越界，请求在审计记录里长得完全正常。审查这类代码该问的问题是：这个字符串最终会进 exec 吗，进去的时候有没有被当成一个整体参数。

第四，修完之后要轮换。如果构建服务器被登录过，第一件该做的事不是升级，是假设环境变量里的所有令牌都已泄露，全部换掉，再看流水线里有没有多出来的步骤。

一个普通开发者账号就够 改项目 VCS root 或构建配置 Perforce 路径里塞入额外选项 拼出的命令行多了一个参数 构建机上以服务账号身份执行 读走部署密钥与云平台令牌 用正规流水线把后门打进制品

把别人的证书挂在自己链上，就算通过了

CVE-2026-130778 · Incus 7.6.0 之前 · 同日另有至少七条 CVSS 10.0 · 不持有私钥也能冒充集群成员

11 月 18 日一天，NVD 里多了至少八条 Incus 的记录：一条 10.0、五条 9.9、两条 9.6。Incus 是 LXD 分家出来的容器与虚拟机管理平台，管的是集群、存储池、虚拟机的生命周期，通常直接挂在运维网段上。

10.0 那条的机制简单到有点荒谬。Incus 的 HTTPS 监听器会向客户端要证书，但只验证客户端送来的证书链里的第一张，而认证逻辑又拿链上所有的证书去和信任库比对。于是攻击者只要把自己那张自签证书和一张受信证书（比如服务器自己的证书，或者某个集群成员的证书）拼成一条链送过去，就会通过认证，而他并不持有那张受信证书的私钥。过了这一步，就能拿到集群级权限、改信任库、影响基于脚本的授权判断。

配套那几条也都指向"授权判断写得太松"：130786、130784、130773 是项目隔离被绕，130780、130771、130779 是路径穿越（迁移、备份、自定义卷的元数据里塞快照名），130783 是事件流把证书和集群加入令牌给泄了，130774 是命名空间映射提权。官方给的缓解只有一句：没有配置层的绕过办法，把 HTTPS 监听器限制在受信主机，升级到 7.6.0。

AI 网关成了提款机，一群假爬虫在敲 .env

CVE-2026-40217（LiteLLM）· Octopus 与 Gecko 扫描活动（Tin Computer，11-18 公开） 无统一评分 · 十秒三百个路径，三十二个轮换 UA

今天这两件事要放一起看，因为它们说的是同一个位置：存着模型密钥的那台机器。

第一件，LiteLLM 进了 KEV。/guardrails/test_custom_code 允许对字节码做重写，等于远程执行代码，CISA 给到 12-02。LiteLLM 是这两年被大量自建的 LLM 网关，一个界面后面挂着 OpenAI、Anthropic、DeepSeek、通义、Kimi 的 key，谁能碰到它，谁就同时碰到好几家云的钱包。

第二件，安全公司 Tin Computer 在 11 月 18 日公开了两组扫描器，代号 Octopus 和 Gecko。它们伪装成 GPTBot、ClaudeBot、PerplexityBot，还有一堆没在任何官方名单里出现过的名字（DeepSeekBot、GrokBot、ChatGLM-Spider）。手法很直接：先用真浏览器头访问首页、读 robots.txt 和 sitemap.xml、看 Next.js 与 Vite 的 manifest，然后在十秒内打大约 300 个敏感路径，每请求换一个 UA。

目标包括 /.env、/.git/config、LiteLLM 的管理路径，以及这一批新出现的智能体凭据：/.claude/.credentials.json、/.cursor/mcp.json、/.codex/auth.json、/.gemini/settings.json。

Gecko 那边更专注，它是个 .NET 客户端，UA 有个 60 字符截断的毛病（(KHTML, like Gecko) 那一段被截掉），9 月 30 日开始专门问 Claude Code 的配置，10 月到 11 月扩展到 MCP JSON、Codex 的 auth.json、Gemini 的 settings.json 和 LiteLLM 的 config。AI 工具相关路径从它扫的 4% 涨到了 10%，涨的速度正好等于这些工具新增配置文件的频率。

为什么值得关注：第一，"给 AI 爬虫放行"这个习惯正在变成漏洞。很多站为了 SEO 或训练透明度，按 UA 白名单放行 GPTBot 一类，Octopus 就是吃这一口：32 个轮换名字，一台 Google Cloud 主机，几百个路径。按名字放行等于没放行，要按官方公布的 IP 段校验。

第二，这一批新目标文件是 IDE 自己写出来的。.claude/.credentials.json、.cursor/mcp.json、.codex/auth.json 这些文件很多人根本没意识到它们存在，而 CI 只要把仓库（包括被 gitignore 的智能体配置）拷进 public/ 或 dist/，扫描器就能拿到，不需要利用你应用的任何逻辑。

第三，AI 网关的风险是"一把钥匙开很多扇门"。一个管理界面弱，后面几家的账号一起完。Ollama 默认只监听 127.0.0.1 且不鉴权，一旦有人为了"让同事也能用"把端口开出去，等于把模型和账单一起挂到公网。

第四，自查很便宜。/.env、/.git/config、/.claude/settings.local.json 这些应该返回 404。返回了真内容的，那把 key 就该换了。
