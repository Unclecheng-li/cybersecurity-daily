四十条记录一分钟落库，四个 10.0 全在底座上

11-10 01:17 UTC 单分钟提交 40 条 · 9 严重 / 17 高 / 13 中 / 1 低 · 另一口径 38 条、34 份说明 四条 10.0 同向量 AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H · 均不在 KEV · 厂商未报在野

2026 年 11 月 10 日 01:17 UTC——美国中部时间十一月九日晚上七点十七分——SAP 的 CVE 编号机构在同一分钟里提交了 40 条 CVE 记录，赶在周二的安全补丁日之前。按 NVD 查询的分布是 9 条严重、17 条高危、13 条中危、1 条低危。中文侧的口径是 38 条新记录、34 份 SAP 安全说明、9 严重 / 15 高 / 13 中 / 1 低（合 38），差的两条大概率是同一批里的重复计数或后续补录，两个数都记在这里。

真正值得注意的是那四个 10.0 的位置。没有一条在 ERP 模块、CRM 前端或者报表工具里，四条全在底座：CVE-2026-89103 在 SAP Gateway（CWE-863，note 3798345）、CVE-2026-76964 在 NetWeaver AS ABAP 的 ICM（CWE-1287，note 3778530）、CVE-2026-89126 在 Web Dispatcher（CWE-122 堆溢出，note 3778556）、CVE-2026-120017 在 NetWeaver AS ABAP / ABAP Platform 的 SAML2 服务提供方（CWE-347，note 3849308）。四个共用同一个向量，可利用率子分 3.9，影响子分 6.0，全部是 SAP 自己给的分数——它也是自己产品的 CNA。

89103 要读两遍，因为它不是编码失误。SAP 自己的描述是产品"以高权限激活默认访问控制列表"，导致外部未认证攻击者被归类为内部应用服务器。换句话说：有漏洞的状态就是安装完成后的状态。不需要管理员误配，不需要打开某个可选功能，装完就是这样。受影响内核横跨 KRNL64NUC 7.22、7.22EXT，KRNL64UC 7.22 / 7.53 / 8.04，KERNEL 7.22、7.54、7.77、7.93、9.16、9.20、9.21。

SAML2 那条的现实影响面可能更大。受影响版本是 SAP_BASIS 702、731、740，以及 750 到 758 的每一个版本，加 816、920、921、922。断言验不严意味着：只要知道一个用户名（DDIC、某个业务管理员），就能自己造一张"认证通过"的票进去。而 ABAP 系统的用户枚举成本极低，这条更像是"知道账号名就等于拿到账号"。

其余五条严重级：109795（9.9，CWE-94，S4CRM 远程启用功能，低权限即可代码注入）、109803（9.9，CWE-94，知识管理 XML Forms 的 XSL 转换选择不受限）、76965（9.9，CWE-749，note 3792735，缺授权检查一路走到操作系统命令执行）、89119（9.6，CWE-352，Web Dispatcher 与 ICM 的 CSRF，九条严重里唯一需要用户交互的）、109798（9.1，BusinessObjects Web Intelligence 的 XXE）。

尚未确认在野。这 40 条一条都不在 CISA KEV 里，SAP 也没报告主动攻击。但 KEV 里已经躺着 14 条更早的 SAP 漏洞——这个数字说明 SAP 底座是被人翻过的，不是没人看的角落。补丁窗口排不开时，先做两件不依赖补丁的事：把 Gateway、Web Dispatcher、ICM 的端口收到内网，然后去 ABAP 里核一遍 SAML2 配置有没有真的在验签。89103 尤其要查：默认高权限 ACL 是装完就有的，老系统上如果没人动过这个配置，它一直开着。

KEV 一次加四条，一个加号后面接的是系统命令

11-09 加四条 · catalogVersion 2026.11.09 共 1773 条 · 联邦整改截止 11-12 FreeSWITCH 116779 · CVSS 3.1 9.8 · CWE-77/78/749 · 1.11.3 修 · 从公开到死线 7 天

十一月九日，CISA 往 KEV 里加了四条，全部给同一个截止日：2026 年 11 月 12 日。联邦民事机构只有三天。四条是 GPUStack 102895、OpenSSH 123158、SignalWire FreeSWITCH 116779、IBM Aspera Faspex 123218。前两条我们在十一月六日已经写过本体机制（GPUStack 的 force_auth_localhost 默认 false 加 client_ip_getter 收 X-GPUStack-Real-IP；OpenSSH 那个 musl crypt() 失败返回星号、刚好等于 shadow 字段里的星号）。CISA 是在它们公开四天后才收进 KEV 的——这不是补录的错，是两套时钟的正常差速：厂商的在野证据比 KEV 的收录早，KEV 的收录比很多人的补丁早。真正新的只有后两条。

FreeSWITCH 的缺陷在 sofia_presence_handle_sip_i_message()。它支持在 SIP 上跑聊天，判断一条消息投给哪个聊天后端的方式是把 To 头里的 user 部分按加号切开，左半边当协议名。于是往 api+随便什么@你的交换机 发一条 MESSAGE：api 这半边选中了 mod_dptools 注册的聊天接口，而这个接口把载荷原样递给 switch_api_execute()。那是命令分发器——status、reloadxml、sofia profile、originate 都从这里走，system 也从这里走，而 system 背后是 popen。链条短的原因是：聊天面和控制面共用了一个解析器。

默认配置决定分布面。入站聊天在出厂的 internal 和 external 两个 SIP profile 上都是开着的，而收紧 apply-inbound-acl 并不能覆盖 SIP MESSAGE。认证这关也没想象中牢：auth-messages 从 1.10.7 起默认开启，所以"该 profile 上任意一个注册账号"就够了；更糟的是出厂 conf/vanilla 目录里带着没有密码、没有 a1-hash 的用户，除非显式把 allow-empty-password 设为 false。一个照着入门镜像装起来、把 5060 开到 SBC 上、忘了删 1000 到 1019 号分机的呼叫中心，正好就是公告里说的"任意一个已认证账号即可"。

时间线本身也是样本：修复提交 8 月 26 日进 master，标题就写着加开关；8 月 28 日 1.11.3 发布，参数默认关闭；10 月 28 日 GHSA 才公开，距修复 63 天；11 月 5 日 CVE 公开；11 月 9 日进 KEV。这 63 天里，任何看 master 的人读一遍提交标题、读一眼 vanilla profile 里的注释，就能复现打补丁前的原语。公告那句"已在野观察到利用"和这个时间差放在一起看，更像是在描述一件已经发生的事。

Aspera Faspex 123218 是另一回事：CWE-863，影响 5.0.0 到 5.0.19，IBM 十一月七日修（5.0.19 PL1，容器部署要确认 faspex-core 报 5.0.19 (1ce4b13)），没有给任何变通方案。公告措辞是"已认证用户构造特定消息可跳过授权检查、拿到完整管理员权限"，而向量写的是 PR:N。两者不矛盾：PR:N 描述的是"一旦持有任意一个有效账号，不需要额外角色"。真正的门槛是一张能用的登录，而文件传输门户的登录恰恰是钓鱼和撞库最容易拿到的那个——它本来就是给外部合作方用的。这个产品有过前科：2022 年 12 月修的 CVE-2022-47986（未认证 YAML 反序列化 RCE，9.8），几周内就被 IceFire 和 Buhti 拿去打对外的 Faspex。

该怎么做：FreeSWITCH 升 1.11.3 后重启；升不动就先 reload profile（会关掉该 profile 全部入站 MESSAGE 聊天），再删掉空密码目录用户、设 allow-empty-password=false，disable_system_api_commands=true 能摘掉最大的坑但不算完整修复。被暴露过的机器按失陷处理：翻 MESSAGE 与 403 日志、查 autoload 里多出来的模块、查新用户与 cron、查守护进程发起的呼出。Faspex 用 docker ps 确认镜像版本，补不上就只能把服务从公网拿下来——对一台合作方要从外部访问的传输服务器，这是业务决定。

对端发 SIP MESSAGE To 头按加号切开 左半边当协议名 api 选中 mod_dptools 聊天接口 载荷直达 switch_api_execute() system API 背后是 popen 以守护进程身份执行系统命令 升 1.11.3 或先 reload profile
3 口径断裂

一个未文档化后门，评了 6.1 中危

11-09 12:16 至 13:17 UTC 同一 CNA 交 20 条 · 最高 9.2 · 全部无 CPE · 全部 CNA 自评 CVE-2026-112169 · 6.1 MEDIUM · CWE-288 + CWE-912 · 向量 AV:L 压住结果

2026 年 11 月 9 日 12:16 到 13:17 UTC 之间，20 条 CVE 落到 NVD，全部来自同一个 CNA，引用的只有 acn.gov.it 上的页面（意大利国家网络安全局，CSIRT Italia 的上级）加一份 CompuGroup Medical 的新闻稿。受影响产品是 CompuGroup 的 XDent、XMedical、Infantia、Profim、Venere、Phronesis、Wingesfar，以及 GALENO SISTEMI 的 MAGISTRA 3.12。

这批里最该坐一会儿的是 CVE-2026-112169。描述第一句是："Magistra 软件包含未文档化的后门功能，允许绕过认证并在不验证凭据的情况下创建特权用户账户。"弱点标了 CWE-288（替代路径绕过认证）和 CWE-912（隐藏功能）。评分：6.1 MEDIUM。向量解释了为什么：CVSS:4.0/AV:L/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N/E:U——机密性、完整性、可用性影响全是 High，不需要任何权限，但 AV:L（本地攻击向量）把结果压在中段。

这个分不算评错。CVSS 问的是"这个洞有多难够到"，软件跑在诊所自己的 Windows 机器上，本地向量确实降低可达性。问题在于 CVSS 不问"厂商是不是自己留了一扇门"。CWE-912 这个分类存在的意义就是描述隐藏功能，记录也确实用了它。但一个绕认证的、能创建特权账户的内部入口落到 6.1，在周一的分诊队列里就会排在一堆中危 Web 漏洞后面。更讽刺的是同款产品还有三条：6.0、6.3、4.4——后门不是它自己软件里分最高的那条，6.3 的 112170（升级文件不校验完整性）比它高。

版本数据这层更麻烦。118462（9.2，CWE-494，本批最高）：更新组件下载并执行代码而不做真实性验证，受影响 cgm.files.delivery 到 1.3.0、cgm.liveupdates 到 2.12.0——漏洞就在更新通道本身，用一条"会执行未验证代码"的通道去投递它自己的修复。118458（8.1，CWE-798）：生产环境里发布出去的测试用 DAO、明文比对、固定管理员账户，受影响包 cgm.it.ais.common，上界写 lessThanOrEqual 5.1.15.1.1、versionType: semver。那不是语义化版本号，五个点分段而 semver 只有三段。而同一个 CNA 在这条之前 19 秒提交的 118459，同包同产品，上界写 5.1.1。同一分钟两条记录给了两个不一样的答案，其中一个还不是数字。

Wingesfar 四条用了两套不兼容的版本方案：118790（7.2）上界 lessThan 2026.07a，118791（7.2）上界 lessThan 10.2.1，118792（6.1）与 118798（4.4）又回到 2026.07a。一个产品，一个日历版本号和一个语义版本号当两条边界，没有任何东西关联两者。更有五条根本没有范围：118450 只写 Venere version 8.33.2 没有 lessThan；四条 MAGISTRA 只写 version 3.12、versionType: custom——3.11 受不受影响，记录不说。20 条里没有一条带 NVD 自评分数，核过的记录都没有 CPE，读完整的几条还停在 vulnStatus: Received。没有一个扫描器能靠 CPE 匹配到这 20 条。

链条断在哪里很清楚：厂商新闻稿说"技术细节、CVE 标识符和受影响版本见公告"，公告在 CSIRT Italia 网页上（意英两条路径对自动抓取都返回客户端错误），CNA 五天后才把结构化记录交上去。每一环单独看都站得住，整条链走完没交出一个版本号。CompuGroup 的新闻稿落款 11 月 4 日，说修了认证系统、密钥分发、更新投递和日志留存，补丁自动下发，未发现被利用证据——通篇不提产品名、不提版本号、不提 CVE。自动下发关掉了那些代码路径，但它没法告诉管理员硬编码凭据在这之前有没有被用过。

该怎么做：确认更新真的落地了，别信"应该已自动装了"；118462 是更新通道里的 9.2，一条会执行未验证代码的通道不是好的自我修复工具。Phronesis/Venere 别自己去解 5.1.15.1.1，按兄弟记录支持的读法把 5.1.1 及以下全当受影响。MAGISTRA 3.12 在 GALENO 明说之前按更早版本也受影响处理，并且不管那条 6.1，先把现存特权账户审一遍。

厂商新闻稿 不写产品与版本 CNA 五天后再交结构化记录 版本串不是 semver 扫描器无法比对 未文档化后门 因本地向量落 6.1 同款另有 6.3 比后门更高 20 条全无 CPE 扫不到
4 全量关停

让所有人立刻关服务器，却还没说是哪个扩展

11-08 12:33 UTC 首警告 · 约 80 分钟后全量关停 · 攻击 09:22 已开始 单一运营者损失 2,285,545 sats（≈0.023 BTC）· 截至 11-09 09:00 UTC 无修复版本

LNbits 是比特币闪电网络上用得最广的开源自托管钱包/账户系统之一，个人和小机构拿它开自托管钱包、给多个用户分账户、在上面写扩展。它是自托管的，所以项目方没有总开关。

11 月 8 日 12:33 UTC，项目方发第一条警告：跑 Paywall 扩展的运营者立刻关掉这个功能，正在排查一个可能的缺陷。大约 80 分钟后，警告升级成对所有人："所有 LNbits 用户立刻停掉你们的 LNbits 服务器。在一波攻击之后，我们有一批安全补丁要推。"托管服务 my.lnbits.com 一并停掉。

最清楚的一笔损失来自荷兰运营者 Kevin Ravensberg，他的实例上跑着 Telegram 打赏机器人 Bittipbot：攻击者在他的实例上新建账号，在 11 月 8 日 09:22 到 14:00 UTC 之间提走了 2,285,545 sats（约 0.0229 BTC，按当时约 75,800 美元算约 1,730 美元）。注意这个时间：攻击 09:22 开始，第一条警告 12:33，已经晚了三个多小时。他说会个人赔付受影响用户，但资金要等补丁推出来才能动。

截至 11 月 9 日项目方最后一次更新，没有发布任何修复版本；GitHub releases 页最新的还是 v1.6.2，一个 9 月 18 日的 PostgreSQL 备份热修。核心贡献者 Ben Arc 估计补丁在 24 到 48 小时内合并可用——那是估计，不是发布通知，也不是"可以安全重启"的许可。他确认团队已查清"用的是哪个扩展的漏洞"，但至今没公开是哪一个，也没说是不是 Paywall。总损失、受害实例数量、受影响清单，一概未公布；项目方也没有给出任何"自查是否被打过"的方法。

另一头：2026 年早些时候 LNbits 做过外部审计（V12），发现一个认证缓存绕过和一个 PayPal 集成缺陷，都在 1.6.0（9 月）修了。目前没有证据把那次审计的问题和 11 月 8 日的攻击连起来，但时间上离得很近。

该怎么做：现在关掉，等官方修复版本再开。别把"关掉一个扩展"当成完整响应——项目方自己在一个半小时内就把口径从"关 Paywall"扩到"全关"，这个扩口径的动作本身就是答案。恢复前：留证据（日志、数据库快照、配置），查新建账号与异常提现，轮换 API key 和管理凭据，然后按"这台机器可能被打过"做隔离，而不是按"网页能打开所以没事"。

5 无正式版

修复提交在开发分支上，正式固件里一条都没有

11-06 修复进开发分支 · 发布分支该文件自六月未动 · 16.0.0 为最新正式发布 CVE-2026-119756 · CVSS 3.1 9.8 / 4.0 9.3 并存 · CWE-805 · UDP 4447 · 无 CPE

Tasmota 是 ESP8266 / ESP32 上装机量最大的开源固件之一，智能开关、插座、传感器、电表大量跑在家庭和小商户的局域网里。CVE-2026-119756 出在 SendReceiveDeviceGroupMessage()——Device Groups 功能收消息的那个函数。Device Groups 用 UDP 4447（组播 239.255.250.250）在设备之间同步状态：构造的消息让 log_remaining 计数器变成负数，随后的写入超出那个固定的 512 字节缓冲区，形成堆越界写。ESP8266 和 ESP32 都没有 ASLR，也没有堆 cookie，所以"崩机"和"原生代码执行"之间的差别只取决于攻击者愿意花多少功夫。

问题在修复的位置：提交 e97e1e4 于 11 月 6 日进了开发分支，发布分支（master）上这个文件自六月以来没有被动过。换句话说：16.0.0 是当前最新的正式发布，而没有任何一个已发布固件包含这个修复。不要等 16.0.1——它不存在。

这条还带两个"扫不到"的属性：没有 CPE，基于 CPE 的匹配完全不会命中；按版本号匹配会把 16.0.0 标成受影响、但找不到可比的修复版本，于是一直挂在扫描结果里，直到真有一个发布出来。同一份记录挂了两个分数：CVSS 3.1 9.8 与 CVSS 4.0 9.3，都是 VulnCheck 给的，这里不替它选。

同一天还有一条同型的：rConfig CVE-2026-124079（9.8，CWE-502）。未认证攻击者把构造好的序列化任务推进 Redis 支撑的 Laravel Horizon 队列（受影响部署里这个队列不带认证），Laravel 的 CallQueuedHandler 反序列化时不限制类，于是可以实例化产品里现成的 App\Jobs\TaskDownloadRun 去调用自己控制的 Artisan 命令。产品自带 laravel/tinker，等于任意 PHP 加任意系统命令，以队列工作进程身份执行；能往 storage/app/public 写持久化 webshell，也能读出数据库口令、存着的设备凭据和 API token。Redis 够不到时，已认证攻击者还能通过"把设备目标指向服务器自己的回环地址"投递同样载荷。这里的问题只是版本号：记录里的范围止于 8.2.19，而官方公告页叫 Core 用户装 8.2.20。装高的那个。

该怎么做：Tasmota 唯一今天就能做、且不涉及未发布固件的改动，是把 Device Groups 关掉。在每台设备上跑 SetOption85 看返回值，官方排障文档说结果应该是 ON；返回 off 说明那台设备上没有可达路径。开着又不需要的，SetOption85 0 关掉——那会摘掉漏洞赖以到达的监听器。需要保留的，就把 UDP 4447 和组播 239.255.250.250 当控制面：设备放隔离 VLAN，和普通用户网、访客网之间不留通路，段边界上拦入站 UDP 4447。这是替代补丁的缓解，不是补丁。

7. 那个 10.0，给分的人和拆固件的人不是同一个

VulDB 在 11-10 01:17 UTC 提交 CVE-2026-125086（D-Link M60，固件 1.12.B01），描述指向 /etc/emDaemon/mosquitto.conf 的 system 函数里的硬编码凭据，CWE-259 + CWE-798，并写明"利用已向公众披露并可能被使用"。一条记录挂了三个分：CVSS 3.1 10.0（AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H）、CVSS 4.0 9.3、CVSS 2.0 10.0（NVD 给 v2 的 baseSeverity 标的是 HIGH，因为 v2 分档就到 HIGH）。记录的第一个引用是公开仓库 XueDugu/dlink-m60-easymesh-mqtt-credential-evidence，作者自己在 README 里贴的向量是 CVSS:3.1/AV:A/AC:L/PR:N/UI:N/S:U/C:L/I:H/A:L——两个向量在八个基础指标里有四个不一致：找洞的人说相邻网络、范围不变、机密性低影响，CNA 说网络、范围变了、机密性高。仓库的技术主张（出厂 EasyMesh MQTT broker 用编译期写死的 admin/admin；/usr/bin/commander 开机从二进制常量重写配置与 passwd，机主改不掉也删不掉；自带 mosquitto 2.0.14 监听 0.0.0.0:1883 与 [::]:1883；订阅 acs/ 主题的控制守护进程以 root 运行并能走到执行 /tmp/acs.sh 的 system()）均为单一来源、未经独立核实，仓库只有一个 commit。同批还有 CVE-2026-125079（DCS-6501LH 3.03.02，Media Service，同两个弱点类，5.3 中危）在 0.45 秒前提交——两条同弱点、同作者、同批次的记录之间差 4.7 分，差距几乎全在 scope 和影响三元组上，两条都没解释为什么。两条都没有修复版本，NVD 状态 Deferred，找不到 D-Link 对应公告。真正可操作的那句不依赖分数之争：broker 在所有接口上监听 1883 且凭据改不掉，去查 1883 是不是只在本段可达，不是就在边界拦掉。

8. UnrealIRCd 8.6：任何用户都能注入服务器之间的命令

CVE-2026-114713（CVSS 3.1 8.6，AV:N/AC:L/PR:N/UI:N/S:C/C:N/I:H/A:N），影响 6.0.0 到 6.2.7.1 之前。labeled-response 模块在把 IRCv3 的 label 消息标签回显进回复时不做转义，于是任何在"有两台以上服务器互联"的网络上的人，都能注入本应只在服务器之间传递的命令，并以服务器权限执行。注意这条的向量是 S:C 但 C:N——影响全在完整性上，也就是"能改"，不是"能读"。NVD 状态 Deferred，不在 KEV。有一个聚合类日报称它"已在野被滥用"，但没有任何一手来源（厂商公告、CISA、研究者）确认，此处按二手标注。跑 IRC 网络的升到 6.2.7.1。

9. SuperTokens Core 9.9：改父级连接 URI 域名的权限检查不足

CVE-2026-123800（CVSS 3.1 9.9，AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H），11-09 收录，vulnStatus: Received。Multitenancy.checkPermissionsForCreateOrUpdate 对"更新父级连接 URI 域名"这件事的授权检查不足。受影响版本从 6.0.0 起，直到 6.0.24、7.0.23、8.0.7、9.0.6、9.1.6、9.2.7、9.3.5、10.0.8、10.1.9、11.0.9、11.1.4、11.2.4、11.3.8、11.4.8、12.0.11、12.1.2、12.2.1、12.3.1 为止——每一条维护线各有一个修复点，这种列表本身就是"你很可能还在某条旧线上"的提示。PR:L 意味着需要低权限账号，但 S:C 加三项 H，低权限到跨租户接管只差一步。SuperTokens Core 是自托管的认证服务器，改父级 URI 域名在多租户场景下等于把某个租户的认证流量整体导向攻击者。

10. Redpanda Connect 9.8：管理 API 默认不开认证，4.39 到 4.110 全中

CVE-2026-123270（CVSS 3.1 9.8，AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H），11-09 收录。4.39 到 4.110 版本在 streams 模式下把管理 HTTP API 开在 0.0.0.0:4195，认证默认关闭，stream 的增删改查路由上没有任何认证关卡。能连到 TCP/4195 的未认证攻击者可以直接 POST 一个 stream 配置进去——而 stream 配置里本来就有 processor 和 input/output 组件，这条路通向代码执行。默认值是"关"的产品，暴露面取决于谁把它开在了公网网卡上。版本区间跨了 70 多个小版本，说明修的时间点离发现的时间点很远。

11. 两个 7.5 的双因子绕过，更新日志里没有"安全"两个字

CVE-2026-118201 与 CVE-2026-118202，都是 CVSS 3.1 7.5（AV:N/AC:H/PR:L/UI:N/S:U/C:H/I:H/A:H），都在 3.4.1 之前。118201：Limit Login Attempts Reloaded 没有在每一条密码认证路由上强制双因子，知道密码的攻击者可以从另一个登录入口进去，不完成第二因子就拿到该用户会话。118202 更难看：它不确认第二因子那一步成功了就完成登录，并且把"构造这一步失败"当成成功——攻击者只要发一个能让该步骤报错的请求头，第二因子就被跳过。两个都在 3.4.1 修了，更新日志里没把它们称为安全修复；而紧接着的 3.4.2 在同一种更新日志里给一个 SSRF 标了"Security:"。这条的形状和十一月九日写过的 Contact Form 7 是同一种：修了，但没告诉你有事。
