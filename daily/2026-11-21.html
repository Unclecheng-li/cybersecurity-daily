1 9.8 · 在野两个半月 · 未进 KEV

补丁发出去那天，洞已经被用掉两个半月

CVE-2026-123890 · VMware vCenter Server 目录服务 · VMSA-2026-0009 · 修在 9.1.1.0200 / 9.0.2.0200 / 8.0 U3m CVSS 3.1 记 9.8 · 未认证拿管理员会话 · 7.0 无公开修复

11 月 19 日，Broadcom 发了 VMSA-2026-0009，修 vCenter Server 目录服务（vmdird）里的一个认证绕过。按 NVD 记录，网络可达的攻击者不需要任何凭据，就能拿到一个管理员会话。同一天，Google 威胁情报组与 Mandiant 说这个洞在九月初就已经被用了，比补丁早两个半月。

技术路径写得很具体：vmdird 的 DCE/RPC 接口在 TCP 2012 上泄露 SRP 会话密钥，外面的人拿到密钥就等于拿到一个 administrator@vsphere.local 的已认证会话，不用密码。工具链是成套的：BONESAW 走这个洞复制 SSO 目录库、抽走 SAML 签名密钥、建一个隐藏的 SSO 管理员；SAWSNAKE 拿签名密钥伪造 SAML 断言与 session cookie，也就是常说的 Golden SAML，伪造出来的令牌在改密码之后依然有效，MFA 也拦不住；BEARBONES 是一个改过的 Dropbear SSH，挂在 TCP 33992 上；LAZYBONES 用 Slack 当 C2。除此之外还有五个新命名的恶意家族。

进入点不是 vCenter 本身。Mandiant 的描述是从一台 BeyondTrust Remote Support 设备的零日（CVE-2026-102764）进来，横向到一台没有装 EDR 的内网 Linux 应用机，再从那里打 vCenter。vCenter 从头到尾没有暴露在公网上，它是被别人家管理平面带进来的。

值得关注的原因：

  • 时间窗比日志留存还长。两个半月大约 75 天，中型企业日志常见保留 30 到 90 天。入侵如果落在上限之外，你今天去打补丁的时候，能查的证据已经滚出保留期了。
  • 改密码不解毒。Golden SAML 伪造的是签名，只要签名证书没换，攻击者随时可以再签一张。处置顺序是轮换 SAML 签名证书，再重置 administrator@vsphere.local 与 vpxuser。
  • 公告不提在野，KEV 也不收。Broadcom 的公告没有写正在被利用，功劳记在 Mandiant 名下；截至 11-18 版 KEV（1,786 条）里没有这一条。只跟 KEV 打补丁的团队，这一条会被漏掉。
  • 七月的补丁不算数。Broadcom 的 FAQ 明确说这个洞与七月的 CVE-2026-59309 不是同一个，打过七月那版的人今天仍然暴露。

2 七个 4.0 记 9.2 · 十月补丁不覆盖

七个 9.2 一起发，其中一个不是人找到的

CVE-2026-126714 PHPAfterShell · CVE-2026-129289 FPM 走私 · PHP 8.5.13 / 8.4.28 / 8.3.37 / 8.2.36 17 或 18 条 CVE 两套口径 · 无在野报告 · 上传进度默认开

11 月 18 日 PHP 团队提前一天预告"最高级别为 critical"，19 日 14:00 UTC 后放出四个分支的更新。数字有两套口径：PHP 自己的公告覆盖 17 个 CVE，Aikido 与 BleepingComputer 按 18 个算（多出来的是打包的 uriparser 库漏洞，PHP 侧没有对应公告）。七个 critical 在 CVSS 4.0 下全是 9.2。

最受关注的是 CVE-2026-126714，代号 PHPAfterShell。它落在默认的文件会话处理器上，也就是绝大多数站点实际在用的那一套。会话记录是"键加序列化数据加长度字段"，但没有"写完了"的标记。如果 worker 在一次写入中途死掉，文件里会留下新记录的开头拼着旧记录的尾巴。研究方 Depthfirst 证明，只要长度凑得巧，残留字节会在下一次会话启动时被当成另一个对象反序列化。再往下要代码执行，还需要应用里存在 gadget 链，或者像他们演示那样串第二个 PHP 洞；但即使不执行代码，这个原语也能改登录状态、改 CSRF token、读别人的会话。

进门的路径是上传进度：session.upload_progress 在这版之前默认开着，一个带进度字段的 multipart 请求会在任何应用代码跑之前触发一次会话写入，所以不需要有上传表单，只要有一个之后会开 session 的页面。

3 官方判 critical · NVD 记 7.4 · PoC 11-25

一个 ß 变成两个 S，缓冲区边界差一位

CVE-2026-132825 Ruby2Shell · 同批共七个内存问题 · GitLab 19.6.0 与 GHES 3.22.5 仍带受影响解释器 3.3.14 / 3.4.13 / 4.0.10 修复 · 从 2.4.0 起就有这段代码

11 月 18 日 Ruby 发了三个分支的修复版，一次修七个内存安全问题。CVE-2026-132825 是其中最重的一个，研究方 Veria Labs 给它起名 Ruby2Shell。

机理短到能一句话讲完。Ruby 的几个单字节编码（ISO-8859 系列、Windows-125x）里没有大写 ß，转大写时它要变成两个字符 SS。转换循环只检查了缓冲区里够不够放一个字节，写第一个 S 之后，第二个 S 直接落在边界外面——一个字节的堆溢出。输入长度决定溢出落在哪里，所以攻击者对位置有控制权，21 个 ß 就够跨过分配边界。触发路径是 upcase、swapcase、downcase(:fold)、casecmp?；UTF-8 走另一条代码路径，不受影响。

两个口径必须并列写，不然会误判风险等级。Ruby 官方安全公告判 critical，并说"已知有 PoC 在某些场景下能达成远程代码执行"；NVD 现在给的是 7.4，向量是 AV:L（本地）。Veria Labs 的说法是默认配置的 Rails 与老式 Sinatra 未认证可达，但他们没有公开请求路径，PoC 定在 11-25 08:00 UTC 发布，如果主要厂商届时还没出包就再往后推。也就是说今天是 11-21，留给运维的时间是四天。

真正的麻烦在"绑定了自己解释器"的产品上。系统包管理器升级对它们无效：披露时 GitLab 19.6.0、GitHub Enterprise Server 3.22.5、Chatwoot 4.20.0 仍然带着受影响的 Ruby，Mastodon、Discourse、OpenProject 已出修复版。旧分支没有修复，3.2 及更早全部 EOL，而按研究方的说法，2.4.0 起的每一版都有这段代码。

值得关注的原因：

  • 字节小不等于门槛高。一个字节足够改掉相邻对象的头部或指针低位，配合堆布局塑造就能走远；这类原语在实践中被反复证明可用。
  • PoC 有确切日期。11-25 08:00 UTC 是研究方自己写的时间，这种"预告式披露"给出的是可执行的倒排工期，不是模糊的"近期"。
  • WAF 大概率拦不住。触发输入是一串合法的编码字符，21 个 ß 在日志里看上去只是乱码，不像攻击载荷。
  • 同批还有六条。正则编译的 double free、转换的整数溢出、正则匹配的越界读、Regexp#to_s 的堆溢出。Rails 应用里用用户输入拼正则的写法并不罕见。

4 18/25 · 已有 PoC · 模型报的

装完就该删的安装文件，还在那儿等着被重装

CVE-2026-132165 · SA-CORE-2026-017 · 修在 10.6.22 / 11.3.22 / 11.4.13 · 同日另有 132166 Drupal 自评 18/25 · 未认证 · 报告方 Anthropic OSS Scanner

11 月 18 日，Drupal 安全团队发 SA-CORE-2026-017，修 core 里 install.php 的一个洞。Drupal 每个发行包里都带这个安装脚本，默认的 .htaccess 规则不会挡它，装完之后它是否可达完全取决于站点自己的配置。在特定条件下，未认证的攻击者可以让它重跑安装流程，结果是站点被接管或者服务器上执行任意代码。有几条利用路径在 Web 服务器不能写、不能改 settings.php 权限时会被挡住，这是最直接的一道闸。

发现者这一栏写的是 Anthropic OSS Scanner，内部编号 ANT-2026-GMRPK0BU，报告里带了复现与候选补丁。这个扫描器十月才上线，这是它一个月内送出的第二个公开 critical——11 月 13 日那个 Apache mod_http2 的 9.8 也是它报的。Drupal 安全团队自己提到，近期安全报告里 AI 生成的比例在明显上升。

同一天还修了 CVE-2026-132166（7.2），一条管理员配合反序列化才能走通的 gadget 链。10.5.x 及更早、11.2.x 及更早、Drupal 8 与 9 全部 EOL，没有包可打。

值得关注的原因：

  • 这是"配置债"而不是"代码债"。install.php 是设计上就存在的文件，问题在于它不该在装完之后还被访问到。封掉它的收益是长期的：这个洞以及未来所有安装器相关的洞一起消失。
  • 封禁写法有坑。Apache 的 Require all denied 必须写在 server 或 vhost 配置里，写进 .htaccess 会让整站 500；nginx 是 location ^~ /core/install.php 直接 return 404。封安装器不影响 update.php。
  • EOL 分支没有任何选项。按第三方统计，仍在报数的站点里约 29% 跑在 10.5 及更早、8 或 9 上，这些站点今天拿不到补丁，只能封路径加迁移。
  • "模型报的"正在变成常态。三个月前这还是个新闻点，现在已经需要按流程处理：报告量大、带复现、审核压力全在维护者这一侧。
请求 /core/install.php 默认 htaccess 不挡这个路径 触发重装流程 Web 用户能写 settings.php 覆写配置 接入自己的数据库 站点接管或服务器执行代码 封路径 可一次解决所有安装器洞
5 无 CVE · 停摆十余天 · 未归因

系统停了十天，查不到入口在哪

欧盟委员会 · 10-22 发现 · Sysper 与 MyPMO 停摆 · CERT-EU 指认 ARTEX 无勒索要求 · 无数据泄露结论 · 入口未公开

11 月 19 日 Politico 报道后，欧盟委员会确认了这起事件：10 月 22 日发现异常，10 月 26 日初步调查确认，随后把多个应用下线。受影响的是 Sysper（人事平台，工资单、工时、休假）与 MyPMO（医疗费用报销），翻译服务在 11 月 17 日也停过；Sysper 在 11 月 18 日恢复后又短暂崩了一次。工资按时发了，但一部分员工有十来天没法填工时、没法请假。

CERT-EU 在 11 月初识别出攻击方使用了 ARTEX，一套开源的人工智能渗透框架。它的工作方式在 CERT-EU 11 月 5 日的技术通告里写得很清楚：操作者用自然语言给一个目标，框架把它拆成子任务，交给多个智能体去调真实的攻击工具。它自己不训练模型，接的是操作者选的外部模型。原作者的仓库在十月因为被滥用而下架，但独立副本还在流通，下架原仓库不解决问题。

必须分开写清楚的三件事：委员会自己没有点名 ARTEX，是 CERT-EU 识别、Politico 报道；没有公开信息说明攻击者是怎么进来的，ARTEX 究竟用于打进去还是只用于扫弱点，官方没说；没有证据表明员工数据整体泄露，也没有收到勒索要求，但调查没有结束。按欧盟 2018/1725 条例，确认个人数据泄露后要在 72 小时内报 EDPS，这个时钟只有在"确认"之后才开始走。

值得关注的原因：

  • 门槛从"会打洞"降到"会写字"。11 月 14 日那期写过 ARTEX 的行为体与报价，这次落到一个具体机构头上，是第一次有大型公共机构公开承认与之相关的停摆。
  • 下线不等于止损。服务恢复只证明它能用，不证明数据没被复制。委员会的公开口径一直是"相信已控制大部分"，而"有没有丢数据"到 11-20 仍然没有答案。
  • 下架原仓库不起作用。开源框架一旦流出，删除源仓库只能影响后来者，已经拿到副本的人不受任何影响。这类工具只能靠行为检测，不能靠封域名。
  • 这是今年第三次。1 月是管理员工手机的系统的痕迹泄露了姓名与电话，3 月是 Trivy 供应链投毒进了 AWS 环境。三次之间没有公开的关联，但同一家机构一年三次，说明问题在流程而不是某一次运气。
操作者给一句自然语言目标 框架拆成子任务 多个智能体调真实攻击工具 10-22 发现异常 Sysper 与 MyPMO 下线十余天 11-18 向全体委员通报 入口与数据归属仍未公开
6 无 CVE 无补丁 · 物理接触 · 当日复现

锁屏不是墙，Narrator 给它开了条缝

FastUnlock · 11-19 公开 · Chaotic Eclipse · Windows 11 26H2 加 11 月补丁仍可复现 代码以 WsiAccount 运行 · 不破加密只破锁屏 · 12-08 才是补丁日

11 月 19 日，研究者 Chaotic Eclipse 在 GitHub 放出 FastUnlock，一段没有和微软协调过的公开披露。场景很窄但很实在：一台开着、锁着、BitLocker 全盘加密的 Windows 11，攻击者只要坐在键盘前。

路径是这样的：锁屏的"我忘记 PIN"入口按 Win+U 起 Narrator，Narrator 的新界面被放在锁屏账户上下文里跑，焦点落在一个本不该可见的窗口上。用 Caps Lock、方向键、回车走进 Narrator 设置，再到蓝牙和其他设备，再打开自动播放，插一个 U 盘，资源管理器就开了，从 U 盘启动的程序以 WsiAccount 身份运行，也就是锁屏用来托管界面的那个低权限账户。研究者说在装了 11 月补丁的 26H2 上，五分钟能走完。ThreatLocker 当天复现，确认代码执行限制在 WsiAccount，不是管理员。

三个必须纠正的说法。第一，它不是"破解 BitLocker"：加密没被破，密钥没被取出，只是 TPM 单独托管的那套配置下，开机时盘已经解好了，锁屏是唯一那道门，而这个洞开的正是这道门。第二，需要至少一个账户绑定在线微软账户，因为入口是找回流程。第三，研究者自己说没跑完最后一步，手上没有 U 盘，视频演示到进入设置为止。

值得关注的原因：

  • 它打的是"已开机"这个状态。TPM 单独托管的笔记本，关机时是加密的，开着锁着时不是。办公区、会议室、咖啡馆里最常见的状态恰好是后者。
  • WsiAccount 不等于无害。它不是管理员，但能读已解锁卷上的用户文件、能装带持久化的程序、能用这台机器去打内网。对一台丢失的机器来说，这已经够了。
  • 没有补丁的窗口是十九天。11-19 公开，12-08 才是补丁日。这期间唯一的硬防线是开机前 PIN，而多数企业的 BitLocker 部署是 TPM 单独托管、没有 PIN。
  • 检测只能靠事后。Narrator.exe 拉起 cmd.exe 或 powershell.exe 是极强的异常信号，但需要物理在场才有这个进程链，日常告警里几乎不会自己出现。

速览

7. Mitel MiCollab 一条 10.0，盲注命令拼接

CVE-2026-133323，10.0（CVSS 3.1，AV:N/AC:L/PR:N/UI:N/S:C），影响 MiCollab 到 10.3（10.3.0.18）的 AWV（音频、Web 与视频会议）组件，厂商编号 MTLVULN-1864：参数过滤不足导致未认证的盲注命令执行。S:C 意味着影响会越出组件本身，落到宿主系统。MiCollab 这两年被反复打过，边界设备一旦被拿下，攻击者拿到的是能进内网的会议与语音网关。

8. Splunk 一轮清掉近 140 条，SOAR 里有两条 9.9 与 9.6

Splunk Enterprise、Enterprise Security 与 SOAR 一并更新，合计近 140 条。SOAR 8.8.0 修 59 条，其中 CVE-2026-131253（9.9）与 131287（9.6）都需要一个持有 Apps 或 Playbooks 编辑权限的已认证用户。更值钱的是 CVE-2026-76536（9.4，未认证）：在 10.4.5 / 10.2.9 / 10.0.12 / 9.4.17 之前的版本上，集群共享密钥为空时，单机实例的集群配置 REST 接口可以被未认证用户读写。SIEM 是日志的唯一副本，它在攻击链里通常是被删的那一环。

9. WatchGuard Dimension 三条 9.3，日志采集服务不需要认证

CVE-2026-86130（9.3，CVSS 4.0）：日志采集服务缺失认证，远程未认证即可执行任意 SQL，最终以 Dimension WebUI 进程用户的身份执行代码。另两条 84322 与 86094（均 9.3）是在管理 API 响应和诊断日志里返回未打码的会话标识，低权限用户可借别人的会话。日志与报表平台常被当成"只读的旁路系统"，它手里握着全网的会话标识。

10. Postgres Enterprise Manager 三条 9.4，监控代理自带读写文件的权限

CVE-2026-132658 / 132659 / 132660 均 9.4（CVSS 4.0，PR:H / S:C）。132658 的核心是角色设计：每个 PEM agent 登录都继承的 pem_agent 角色，同时是 PEM 后端库上 pg_read_server_files 与 pg_write_server_files 的成员。控制任何一台被监控的主机，就拿到了那台主机的 agent 证书，于是能在 PEM 服务器上读写文件。监控系统天生要"看得见所有机器"，这个设计把"看得见"变成了"写得进"。

11. 伦敦交通局 26.5 万张 Oyster 照片卡，泄露的是安全问题答案

TfL 11 月 16 日发现异常，18 日通知用户，20 日把数字定在约 26.5 万个网络账户（此前口径 25 万，可能还会涨）。泄露字段是全名、邮箱、电话、住址、出生日期，以及账户的安全问题与答案；密码、银行卡与支付信息、行程记录、照片均未泄露，持 Zip 卡的儿童姓名与生日也未泄露。门户仍下线，已通报 ICO。这份数据里最贵的不是生日，是安全问题答案，人们几乎不会改它，而"第一所学校""母亲娘家姓"这几个问题在银行、运营商、政务系统里反复出现。另一处细节：用户是靠收到 TfL 自己系统发出的异常邮件才发现出事的，也就是说攻击者能驱动官方事务邮件，这类信会顺利通过 SPF、DKIM 与 DMARC。

12. KEV 停在 1,786 条，连续两天没有新增

CISA 的目录仍是 2026.11.18 版，1,786 条，11-19 与 11-20 都没有新增。但这不代表风平浪静：11-18 那批四条里有三条的整改期限是 11-21，也就是今天，其中包括那个厂商明确不出修复版的 Apache Axis 9.8。KEV 是"确认被利用"的名单，不是"有危险"的名单，vCenter 那条两个半月在野的洞至今不在里面。
