六十四个 A 加一个等号，堆就写坏了

CVE-2026-114938 · Java4Shell · Calif 披露 · OpenJDK 17.0.6 及以上，需 AVX-512 VBMI CVSS 4.0 记 9.2 · Oracle 记录按 3.1 记 8.1 · 65 字节触发未认证 RCE

这条放在最前面，因为它把"补漏洞"这件事的层级讲清楚了：修的是运行时，不是你那个应用。

研究机构 Calif 于 11 月 17 日公开，取名 Java4Shell。它是这家机构在 PHP2Shell 之后的第二个作品，公告开头那句挺老实："在我们披露 PHP2Shell 之后，发现很多人不知道 PHP 是什么，所以我们选了个更眼熟的东西：Java。"

缺陷在 OpenJDK 的 Base64 解码器里，具体在 x86-64 上那条手写的 AVX-512 VBMI 加速路径。这段代码由 JDK-8268276 引入，2023 年 1 月随 17.0.6 进入 Java 17 线（backport 编号 JDK-8296735）。它处理字符串结尾的填充时算错了输出长度：送进去 64 个 A 加一个 =（共 65 字节），解码器给输出分配 50 字节，先干净地解完前 64 个字符，再处理那个孤零零的等号时，output_len 下溢成负数。负数传给掩码计算没有任何拦截（bzhiq 之后掩码变成全 1），随后一条 VMOVDQU8 把整个 64 字节寄存器一次性写下去，比 50 字节的缓冲区多写了 62 字节。

Java 在下一毫秒就拒绝了这段畸形输入，但内存已经坏了。

Calif 给的利用链分四段。第一段用堆排布把溢出打到相邻数组的长度字段上，让那个数组"以为自己很大"，固定值写于是变成可控写；第二段对另一个数组做同样的事，把内容回显到应用响应里，得到一个堆泄露原语，他们叫它 JavaBleed，走的是 Heartbleed 那条路，堆里有会话令牌、凭据、密钥；第三段用泄露出来的原始字节把被改坏的对象头修回去，让 JVM 不崩、可以重试；第四段才是把可控写打进 JVM 内部，摸到代码缓存拿下执行。跨网络的堆排布靠两招：把成对的对象喷到 G1 的不同 region，以及用 TCP ACK 的节奏去控分块发送的 HTTP 请求体，让分配顺序可控。失败的尝试通常直接把 JVM 打崩，吵，但可以重试。

它之所以敢叫"Shell"，是因为打中的位置太普遍。Calif 在默认配置下验证了预认证 RCE：Keycloak、Atlassian Jira、Atlassian Confluence、JFrog Artifactory、Jenkins、PingFederate；认证后 RCE：Apache Kafka、Apache Solr、Elasticsearch、Gerrit、Netflix Spinnaker；Spring Boot 与 Apache Struts 的样例应用也复现了。名单明确写了"不穷尽"，任何把攻击者可控字节送进 Base64 解码的端点都是候选。samczsun 还补了个反向场景：一个 Java 程序只要主动去连一个恶意 TLS 服务器，自己一个端口都不开，照样被打。出站连接也是攻击面。

为什么值得关注：第一，修的是 JDK，不是产品。Jira 出了新版本、Confluence 出了新版本，都不解决问题。运维清单上要查的是"这台机器的 java -version 是什么"。这条对打包型产品尤其致命：Jenkins、Jira 这类东西在几千个部署里构建方式和内存布局高度重复，Calif 说的"没有通用利用、每个目标要单独做链"在它们身上会打折扣。

第二，两个官方分数差得有点远。Calif 按 CVSS 4.0 记 9.2，Oracle 在自己的 CSPU 记录里按 CVSS 3.1 记 8.1，两份都是"官方"数据。评级打架的时候，按"能不能预认证、能不能从公网打到"来排，比按小数点排更有用。

第三，这次披露里最该被记住的数字不是 9.2。Calif 说他们一名研究员一小时找到这个 bug，两小时后有了可用利用，AI token 成本不到 200 美元，靠的是预先搭好的智能体流水线。Wiz 也做了一遍：他们的 AI 研究装置在细节公开后两小时内产出可用 PoC，并对 Jenkins、Confluence、Tomcat 验证了远程执行。这条接在昨天 GTIG 那份"全自动补丁到利用"后面：漏洞发现的边际成本正在肉眼可见地往下掉。以后公告里那句"AI 辅助代码审计发现"，会越来越常见。

第四，暴露面要先盘硬件再盘软件。AVX-512 VBMI 是 2021 年之后的服务器 CPU 才有的东西，很多老机器天然免疫，而新建的云主机几乎全中。这类"看 CPU 才知道自己有没有事"的漏洞，资产库里通常没有对应字段。

挑战串本来只用一次，没人说它只能用来做挑战

CVE-2026-100397 · Rucio（CERN 主导的科学数据框架）· CWE-287 · 1.14.0 起，35.9.1 之前的四条线 CVSS 3.1 记 10.0（S:C）· 两步拿到任意账号，含管理员

这个洞的技术含量不高，但它的形状特别值得记：两种东西存在同一张表里，校验函数却不知道手上拿的是哪一种。

Rucio 管的是 PB 级科学数据，ATLAS、CMS 这些大科学装置都在用。问题出在 lib/rucio/core/authentication.py 的 validate_auth_token：短期有效的 SSH 挑战 nonce 和真正的认证令牌存在同一张 token 表里，这个函数不区分两者。

利用只有两步。先拿 X-Rucio-Account 头指定任意账号（包括管理员），请求 /auth/ssh_challenge_token，服务端规规矩矩返回一个挑战串；然后把这个挑战串当成 X-Rucio-Auth-Token 去请求别的 API 端点，就通过了。

修复版本是 35.9.1、38.6.1、40.4.2、41.1.1，对应四条维护线，安全公告来自 GitHub 的 security-advisories 通道，附了四个 commit。

环节本该如此实际如此
挑战 nonce只能配合签名验一次，不能当凭据落在同一张 token 表里
校验函数按用途分流两条路径只看"表里有没有这条"
账号参数绑定已经证明过的身份直接取请求头里的 X-Rucio-Account
后果——任意账号，包括 admin

为什么值得关注：第一，这类缺陷几乎不可能靠扫描发现。没有畸形输入、没有异常报错、没有越界，请求在日志里看起来完全合法。第二，审查认证代码时该问的问题变了。不是"令牌有没有签名"，而是"这张表里躺了几种东西，校验函数怎么知道它拿到的是哪一种"。第三，10.0 分不算夸张。S:C 是因为下游所有接了 Rucio 令牌的服务一起被穿透，科研计算环境里那种"一次认证、处处通行"的便利，在这种洞面前就是放大器。

这两条放一起，因为它们的失败点是同一句话："他说他是谁"被当成了"他是谁"。

CIRCUTOR 那条更赤裸。PowerStudio SCADA WAVE 桌面版（Windows 64 位，24.8.0 到 24.11.16.x）的共享 JWT 校验组件接受 alg 设为 none 的未签名令牌，不验证任何密码学签名，于是自己编一个 JWT 就能以别人的身份进系统。CWE-347，CAPEC-39，教科书级。CVE 记录引用了一个 PoC 仓库，研究者没有独立验证其内容。修复版 24.11.17.0 及以上，厂商没给临时缓解。

为什么值得关注：第一，alg: none 是 2015 年就被写进 JWT 库默认黑名单的东西，2026 年还能在出货软件里出现，说明"用了 JWT 库"和"用对了 JWT 库"是两件事。第二，硬编码密钥等于把密钥发给了所有拿到二进制的人，换密钥只能靠发新版本，所以这类洞的实际寿命跟产品的更新率一样长。第三，两条都能十分钟自查完：搜 alg、搜 verify 的调用点、搜代码里的长字符串常量。工业网络不是隔离网，远程维保普及之后，"它在内网"不再是一条防护措施。

补丁两周前就发了，今天才进 KEV

CVE-2026-115731 · Perforce Puppet Enterprise · 11-03 披露带 PoC，11-17 进 KEV CVSS 4.0 记 9.4 · 设计上就是"客户端给的元数据被当成代码"

11 月 17 日，CISA 把这条收进 KEV，目录版本 2026.11.17，第 1,782 条。而在两周前的 11 月 3 日，OpenVox 的 GHSA-ffr6-rwpm-p5wq 与 Neodyme 的 write-up 就已经带着可用的示例报告公开了。

机制值得完整看一遍，因为它是"客户端给的元数据被当成代码"的标准样本。Puppet agent 每次跑完会往 PUT /puppet/v3/report 发一份 JSON 报告，里面列这次运行的事件。服务端为了让时间戳、二进制、资源引用这些原生类型能往返，会走一层 rich-data 转换，而这层信任客户端给的类型名：事件体进 FromDataConverter.convert(data, {:allow_unresolved => true, ...})，攻击者可控的 __ptype 字段被 Types::TypeParser 解析，然后对解析出的类型调 .create(value)。如果没有为这个类型注册实现类，Puppet 会自己生成一个：RubyGenerator.new.create_class(self) 用类型声明的函数拼出一段 Ruby 类定义，再交给 cls.class_eval(class_def)。反引号在类定义时就会执行，对象根本不需要被实例化，命令就跑了。

前置条件是"持有一张由该 CA 签发的证书"。听起来像门槛，实际不是：很多环境开了 autosign，autosign.conf 还写着宽泛的名字匹配，这时候未认证的网络攻击者先去要一张证书，再拿它打这个端点，两步就到。

为什么值得关注：第一，这是配置管理服务器。它给全网发证书、推配置、在每台节点上跑代码，被打穿等于整片受管机群失守，而且走的是你信任的通道。

第二，打完补丁还有第二件事。代码执行发生在 puppet 用户下，这个用户握着 CA 签名密钥。发现中招就要按"CA 私钥已泄露"处理：重建 CA、重新注册 agent。光打补丁不够，因为穿透它的那把钥匙还在。

第三，KEV 的通知节奏再次落后于公开 PoC。11 月 3 日有 PoC，11 月 17 日才进 KEV，中间这两周，等 KEV 才动的组织什么都没做，而攻击者手上已经有能直接发的东西。

第四，CISA 是"在野"的唯一信源，条目里没说用的是 autosign 证书、偷来的 agent 证书还是已经被拿下的节点。三种路径打到同一个端点，处置时都要查。查法也不难：把 11 月 3 日以来 CA 签过的证书过一遍，问一句"这张是我批的吗"。

一个此前没有任何记录的勒索品牌，11 月 17 日上线了一个叫 "Inception, Chapter 1" 的泄露站，一天之内把五家美国大公司标成 Leaked。同日，一个叫 InceptionGroup 的账号在俄语犯罪论坛 Exploit 上挂出数据，账号注册日期就是当天，五条帖子，零托管交易记录。媒体与 ransomware.live 都找不到这个牌子更早的活动。

两家媒体实际下载并检查了两份文件：

PepsiCo：一个 72 MB 的文件，500,817 行员工目录，几乎每行有全名、工作邮箱、头像引用，多数带职位，约二十分之一带部门。没有密码、没有电话、没有家庭住址、没有生日、没有工号、没有薪资。行结构里出现 checkedInCampus、skills 这类字段，看起来是某个"办公位预约 / 同事查找"类工作场所应用的导出格式。

Cigna：421,661 张 IT 服务台工单，来自 Cigna 的 ServiceNow，内部链接指向 cigna.service-now.com，最新一张更新到 10 月 31 日，这个日期排除了"翻出旧泄露充数"的可能。里面 31,593 个去重邮箱、84,398 个报障人、306,089 张带回调电话、7,791 个内网 IP 与设备名、5,120 张提到会员或投保人编号、2,552 张带理赔号、156 万条评论与处理记录。还有一条要单独说：40,837 张工单里出现了 password 这个词，2,808 张里的文本形状像是一个被明文写出来的密码。

为什么值得关注：第一，这批数据的价值不在密码上，在可信度上。一个能报出你的工单号、部门代码、主管是谁、上次找 IT 是为什么的人，在电话里几乎无法被识破。Cigna 那 30 多万个回调电话加上 8 万多个报障人，是一份现成的社会工程剧本。

第二，泄露源看起来不是"打进内网"，而是"从应用里导出"。两份文件的形态都指向业务应用的导出能力，而不是数据库被拖，这意味着传统边界防护和 EDR 可能全程没有信号。

第三，新品牌第一天上五家，本身就该被当成营销行为看。注册当天开站、零托管记录、五家一起标 Leaked，这套打法更像拿"半成品数据 + 大品牌名字"抬价，而不是五起独立入侵。

第四，处置动作不受"是否真实"影响：员工目录与工单历史本来就该按敏感数据管，导出权限、导出审计、工单里不写明文密码，这三件事今天就能做。

某工作场所应用与服务台系统 一份可用登录 或 一次导出接口滥用 72 MB 目录 加 42 万张工单 新品牌当天开站 当天标五家 论坛账号同日注册 零托管记录 五家都没确认 单一来源 真正的风险是身份能被冒充

速览

7. Apache Roller：9.8 未认证反序列化，公告里直接写了"已在被利用"

CVE-2026-129448，CVSS 3.1 9.8，Apache Roller 4.0.0 到 6.1.4。XML-RPC 端点接受"厂商扩展类型"，并且在认证请求方之前就完成反序列化，所以是未认证 RCE。Apache 公告原话是 This issue is being actively exploited，修复版 6.1.6（禁掉扩展类型，XML-RPC 关闭时直接拒请求）。临时缓解只能改 WEB-INF/web.xml 的 enabledForExtensions 为 false，或删掉 /roller-services/xmlrpc 的 servlet 映射再重启；在管理界面里关 XML-RPC 不够，老版本是先反序列化再读这个开关。一条口径冲突：Apache 说已在被利用，CISA 的 SSVC 记录却写 Exploitation none，截至 11-18 也没进 KEV。同一漏洞还有个旧编号 CVE-2026-82384，当时只列了 6.1.5 受影响。

8. ZoneMinder：任何一个登录用户都能把监控服务器变成执行点

CVE-2026-28273，CVSS 3.1 9.9（S:C），1.38.4 之前。/api/configs/edit/{name}.json 背后 ConfigsController::edit() 没有执行 System=Edit 授权检查，所谓"系统变量保护"也无效。攻击者把 ZM_PATH_FFMPEG 改成带命令的值，再请求一次抽帧，web/views/image.php 或 web/includes/Event.php 里的 exec() 就执行了，权限是 Web 服务用户。摄像头画面、录像、数据库一并暴露。开源监控系统常年放在"内网所以不管"的位置，但它往往同时接着摄像头网段和办公网。

9. 一家餐饮 POS，一天六条 CVE，全是同一次审计的产物

ICRTouch 的 PocketTouch 1.700 build 2025.3726：CVE-2026-122055（9.8）套接字默认密码就是字面量 password；CVE-2026-122147（9.8）套接字、配置、关机三个密码全是硬编码默认值；CVE-2026-122149（9.1）SAVECONFIG 命令能远程覆盖收银机配置文件；CVE-2026-122150 CHECKPAYMENT 流程接受调用方自报的收银员编号，不校验他是否有权代表这个收银员；CVE-2026-122142（9.8）管理登录无失败次数限制，且不同 siteID 返回不同响应；CVE-2026-122122 订单跟踪不校验归属，改个订单号就能看别人的单。POS 的价值不在数据量，在"它连着钱"。

10. 两个国产 AI 平台，同一天两个 9.3，都是默认密钥和没关的初始化接口

CVE-2026-130840（BISHENG 3.0.0 之前，CVSS 4.0 9.3）：AuthJwt 用了硬编码的默认 jwt_secret，离线伪造一个 user_id 为 1、角色 admin 的 HS256 令牌，塞进 access_token_cookie，直接拿到用户、工作空间、知识库、工作流的全部管理权限。CVE-2026-130856（53AIHub 0.5.5 之前，9.3）：公开的 POST /api/init 没有鉴权，任何人可以"重新初始化"已安装实例，重置已有账号密码、把自己提成最高 creator 角色、拿 token 接管。这类平台通常由业务部门自己试装，不在运维的资产表里，这正是最危险的地方。

11. Zyxel 9.8：固件里的越界写，WAN 默认关着也挡不住内网

CVE-2026-79614，CVSS 3.1 9.8，DX3301-T0 / EX3301-T0 固件 5.50(ABVY.8.3)C0 及更早，libclinkc.so 的越界写，未认证攻击者发一个构造的 HTTP 请求就能提权并执行命令。NVD 描述里那句"WAN 访问默认关闭"是厂商给分级理由用的，它只说明"从公网直接打不到"，不说明"内网安全"，这类设备的典型位置就是内网边界，同一个二层里还有办公终端。

12. Atomic Server：9.8 分，但没有完整修复版本

CVE-2026-69157，CVSS 3.1 9.8，0.29.0 到 0.40.2。服务首次启动会创建一个 /setup 邀请，写权限、目标是 Drive 根、usagesLeft 为 1；而 server/src/plugins/invite.rs 的 construct_invite_redirect 丢弃了兑换者身份。结果是一个未认证请求带上攻击者自己的公钥，就能创建一个新 Agent 并授予整个 Drive 的写权限。在没有被认领的新部署上，等于把整个库交出去。CVE 记录明确写了"截至审查未确认完整修复版本"。这类自托管 headless CMS 部署量不小，而且常常由非安全岗的人一键起。
