AI 找到了洞，人类还在排队打补丁

PHP 那两枚 9.2 是三家团队在同一周里用前沿模型撞出来的：Calif 用 GPT-5.6 Sol 在 8 月 1 日找到第一枚，Wiz 用 Gemini 4 Argon 在 8 月 19 日独立复现，而 PHP 基金会复盘说这个隐患 2024 年就被人看见过，只因为"几种修法各有代价"搁了两年。补丁 10-21 发了，FBI 与 NSA 让修不了的就下线，六国部分政府站点真的关了。同一天，Trend Micro 的 AI 扫描器把两枚 9.0 的 KSMBD 报告甩上公开邮件列表——没有补丁、没有 CVE，因为内核项目只在稳定版修好之后才发编号。发现侧在踩油门，修复侧还在排队。

PHP2Shell 从"一个漏洞"变成"一次公共事件"：AI 找到的洞，人类还没准备好接住

2026-10-21 补丁发布 · 10-22 六国政府站点预防性关停 CVE-2026-109618 / 109619 · 各 CVSS 4.0 9.2 · 全球约 70% 网站使用 PHP

补丁之后发生的事，比漏洞本身更值得记：美国 FBI 网络部门公开警告，NSA 建议"修不了就先下线"，英、芬、荷、法、德、丹六国部分政府站点预防性关停，日本首相在社交媒体上发文提醒站长查 PHP 版本。这是近年来第一次，一个开源语言的补丁日直接触发了政府的断网动作。

先把"AI 发现"这件事说准，因为它已经被传得比事实更玄。

要注意的是：模型没有"自己找到"这个洞。Calif 的 Ryan Austin 明确说，他没用什么特殊框架、也没用公众拿不到的模型；起作用的是他挑目标的判断——他选 PHP 是因为熟悉它的漏洞史，从 2004 年 Stefan Esser 报的第一个 PHP 内存限制漏洞、到 2020 年一份被忽视的 bug 报告、再到 2024 年那次没能证明可利用性的审计，一条线追下来。模型压缩的是"知道"到"证明"之间的苦工，方向感还是人给的。

真正失控的是披露那 24 小时。

Chainguard 那一步最要命：任何攻击者都能先读二进制的修复 diff，而全世界其他用户在等自己的包。PHP 基金会把这句话写进了复盘。而漏洞在补丁之前就已经被打了——AWS 的 MadPot 蜜罐在 10-17 记录到第一次利用尝试，比补丁早四天，来自商业匿名化网络、载荷带 Mirai 风格加载器；10-21 之后攻击源换成另一批匿名基础设施，载荷形态也不一样，说明至少有两拨人在各自尝试。

"修好了"这句话在这里有三个坑，必须分开说。

  • 坑一：更新 PHP 包会重启 PHP-FPM，但长驻的 CLI worker 不会自己重启。队列消费者、Swoole 或 RoadRunner 常驻进程、CLI 定时任务仍跑着旧二进制，风险一点没减
  • 坑二：自动安全更新不一定管 PHP。Laravel Forge 的公告说得很直白——它的自动安全更新不覆盖 PHP 包，那些包来自另一个仓库、不在自动更新范围内。流程按配置正常运行，PHP 依然是脆的
  • 坑三：老分支只有源码回移，没有发行版包。7.4 / 8.0 / 8.1 已停止常规安全支持，能否落地取决于你的发行版或商业 LTS 供应商

暴露面各家不一，但都在百万级。VirusTotal 侧统计超过 510 万台公网可达的 PHP 主机；另一组给的是约 380 万台；W3Techs 的语言占比是 69.3%。差异在口径（是否算 CDN 后面的、是否只算 banner 可识别的），但结论一致：这是一个按"占比"而不是"台数"计算影响面的漏洞。

值得关注的原因：三句话。第一，这是第一次由前沿模型主导发现、并且公开承认"AI 可能比攻击者先找到"的漏洞——OpenAI 把它叫"Defender's Window"，但窗口只在防守方真的在窗口内打完补丁时才存在，而今天六国的做法是关站。第二，瓶颈不在写 patch，而在分发：源码修好之后还要变成包、镜像、厂商更新，再经过兼容测试、审批、重启、验证，这一段没有任何 AI 能加速。第三，PHP 基金会自己承认这是"结构性失败"——不是没人看见，是人手和决策机制撑不住。这句话对每一个维护关键开源组件的团队都成立。

Arista VeloCloud CVE-2026-114625（9.9）：一个"只读"账号，够拿到整张 SD-WAN 的总控

2026-10-22 披露且已确认在野 · Arista Security Advisory 0199 CVSS 3.1 9.9（v4 9.4）· 最低角色 Enterprise Read Only · 未入 KEV

VeloCloud Orchestrator（VCO）的一枚 SQL 注入零日，已确认在野利用。攻击者需要的东西少得离谱：一个能登录 VCO 的账号，最低角色 Enterprise Read Only——也就是那种"只让他看仪表盘"的账号。拿到之后可以提到 operator，也就是编排整个 SD-WAN 的超级用户，甚至可能拿到 VCO 宿主机的本地 superuser。

为什么这比分数更严重：VCO 是 VeloCloud SD-WAN 的大脑。谁控制它，谁就控制边缘设备的开通、隧道策略、路由，以及所有租户的隔离边界。一个被攻陷的低信任账号，等于整张 WAN 同时失守——这是典型的"力量倍增器"，防守上应该按域控制器的标准对待，而不是按"一台设备"对待。

这是 VCO 四个月里的第三枚在野零日，而前两枚不需要登录。7 月的 CVE-2026-16812 未认证；9 月的 CVE-2026-93952 未认证、当时评到满分 10.0；今天这枚 114625 需要低权限登录。

一条非常容易踩的坑：修过 7 月和 9 月的，今天依然在范围内。因为修那两枚的版本（5.2.3.16、6.4.2.8）比今天这三版旧。更糟的是 6.1 分支上 9 月那枚 93952 一直没有修复版本，于是 6.1 的用户处在"双重暴露"状态——旧的没修完，新的又来了。

"默认暴露"这件事没有开关。Arista 明说 VCO 默认对外可达，没有任何配置能关掉这个暴露。唯一的做法是把它挪到 VPN、跳板机或带 mTLS 的反向代理后面——这是网络层的事，不是产品设置的事。

处置顺序：① 按分支升到 5.2.3.18 / 6.1.3.10 / 6.4.2.12，不在这三个分支的联系 Arista TAC，别假设 EOL 版本安全；② 把 Web 界面从公网摘掉，只留管理网可达；③ 审计并清掉休眠的 Enterprise Read Only 与合作伙伴账号——每一个都是通往 operator 的已知路径；④ 查 VCO 审计日志里的异常角色变更、新建 operator 账号、配置导出、来自非管理员会话的 API token 签发；⑤ 查宿主机上的后门守护进程、webshell 与非预期出站。

值得关注的原因：三次在野零日、四个月、从"未认证"走到"低权限即可"，这个演进顺序不是巧合——攻击者已经把 VCO 当成了一个需要系统性挖穿的目标，而不是顺手打一发。第二轮用的是"合法登录"，这意味着只盯异常登录的检测思路在这里会失效：会话是真的、凭据是真的，只是这个人本来不该有这么大权限。真正要收紧的是"最小角色到底能接触到什么"，以及"编排器凭什么在公网上"。

KSMBD 两枚 9.0 被甩上公开邮件列表：没有补丁，没有 CVE，扫描器也不会告警

2026-10-21 与 10-22 ZDI 提交六份报告 · 全部附在公开列表 · 无一附补丁 ZDI-CAN-33774 与 33549 各 9.0 · 主线与 linux-next 均无已命名修复

Trend Micro 的零日计划（ZDI）向 Linux 内核邮件列表提交了 6 份报告，其中两枚是内核内置 SMB 服务 KSMBD 的远程代码执行，各评 9.0。两枚都没有 CVE 编号，主线和 linux-next 里都没有已命名的修复，而报告是发在公开列表上的。其中 ZDI-CAN-33774 无需任何认证。

33774 是一场比赛。KSMBD 在请求入队时选好由哪个协议处理器处理，但工作线程是在取任务时才去读这个选择。攻击者在同一次 TCP 写里先塞一串短 SMB1 报文、再塞一个 SMB2 报文，连接被切到 SMB2 处理时 SMB1 的缓冲区还在队列里，于是 SMB2 的代码去读了更短的 SMB1 缓冲区之外的内存。据转述，被读出来的内核堆字节会随错误回复一起回到攻击者手里——这就不只是崩溃，是信息泄露。ZDI 另外描述了一条越界写路径，在解析安全描述符时触发，需要先能访问一个共享。演示环境是 7.3-rc3。

33549 是一次算术回绕。SMB Direct 走 RDMA，客户端可以送一组缓冲区描述符，让第一项的长度大于声明的载荷长度，服务端的大小计数器回绕成一个大数，后面那次内存拷贝就越过了缓冲区尾部。它需要三样东西凑齐：RDMA 接口、可写共享、协商 SMB Direct。SMB Direct 本身是单独的编译选项、默认关闭——这是它比 33774 窄的原因，但"默认关闭"不等于"没人开"，HPC 与存储集群恰恰是开着的那批。

真正的新鲜事不是漏洞，是流程。这批报告把 TrendAI（Trend Micro 自家的 AI 扫描器）列为发现者。Linux 内核的安全文档在 2026 年 5 月（按 Linus 的意见）更新过一条规则：AI 工具发现的缺陷，按定义就是已经公开的，应当直接发给子系统开发者列表。ZDI 的投递方式看起来是在执行这条规则——同时抄送公开列表，且所有报告都没附补丁。

稳定版维护者 Greg Kroah-Hartman 在几分钟内连续回了三条，措辞一次比一次短。对 vmwgfx 那份："不知为什么你把它发到了公开列表，而且没带补丁，所以我们也没什么可做的。"十七秒后对 nvmet 那份："又是没补丁、又发到公开列表？请修正你们的提交流程。"

于是就出现了这个空档：报告公开 与 无补丁 与 无 CVE 加在一起，等于扫 CVE 的扫描器全都不报，但攻击者已经能读到细节。Phoronix 说 33549 的修复已由 SMB Direct 维护者 Stefan Metzmacher 提交到面向 Linux 7.5 的分支，可能会被快进，但这一条没有得到其他来源确认。主线修完到进入稳定版、再到发行版内核，通常还要几周。

动作清单（在你还没 CVE 可查的时候）：用 systemctl status ksmbd 看是否在跑、lsmod | grep ksmbd 看模块是否加载、zcat /proc/config.gz | grep CONFIG_SMB_SERVER 看是否编进内核。不需要共享的直接停掉并禁用；需要的把 445 只对白名单源开、在 KSMBD 配置里禁掉 SMB1 协商（这是 33774 的触发前提）、不需要 SMB Direct 的关掉 RDMA 传输。检测抓手是同一次 TCP 会话里出现"一串短 SMB1 加 SMB2"，这在现代环境里是异常形态。RHEL 及衍生版默认不含 KSMBD，这是少数可以松一口气的地方。

值得关注的原因：这条和头条是同一个故事的两面。AI 扫描器把发现速度提上来了，但披露流程没有配套的"带补丁再公开"机制，于是产出的是一批"细节已公开、补丁在路上、编号还不存在"的漏洞。对防守方最不友好的状态不是零日，是这种半公开：你知道有洞、知道怎么打，但没有版本号可以对、没有 CVE 可以让扫描器告警、也没有补丁可以装。

4 高危

QPACK「Header Accordions」：十个 HTTP/3 栈里七个中招，一个连接就能打爆内存

FoxIO · Sébastien Féry · 2026-10-20 公开细节与 PoC· 报备最早追到 2025-11 quic-go CVE-2025-64702（5.3）· quiche CVE-2026-12523（7.5）· 无在野

被测的 10 个 HTTP/3 实现里 7 个有问题：一个未认证的远端客户端，能让服务器为它分配几十到几千倍于实际收到字节的内存。FoxIO 的原话是："一个连接就够把一台默认配置的服务器 OOM 或把 CPU 钉死。"

根因不是某个库的 bug，是同一句话被七种方式理解错了。QPACK 压缩 HTTP/3 头部：常见字段走静态表索引，出现过的字段进动态表，之后用一个字节的索引指回去。RFC 要求服务端按"解压后"的大小来限流，并且每个字段还要加 32 字节开销。现实是：有的只限制了压缩后的字节数不管解出来多少；有的先全部解完再检查（那时内存已经吃掉了）；有的漏掉每字段 32 字节开销；有的把这个限制解析了但从来没执行。

打法做法与实测放大倍数
静态或动态表灌水一个 HEADERS 帧塞海量短小且互不相同的字段；quic-go 默认配置 1 MB 压出约 16 万字段、约 15 MB 常驻，约 17 倍（quic-go 自己的公告说上限接近 50 倍）
索引复用（更狠）动态表里存一个 4 KB 条目，再用 1 字节索引指它几千次，每次都要重建完整条目；Bun 约 4,000 倍，lsquic 600 到 1,800 倍

Bun 还多一个坑。它用 lsquic，但把"限头部内存"那段换成了自己写的代码——逐条检查每个 header，却从不累加总量。于是解出来的头部一过 2 GB，计数器溢出归零，解码器进入一个永远出不来的循环。FoxIO 测到：单条流、线上约 516 KB，就能把一个核钉在 100%，且不恢复。PoC 的规模说明这件事有多便宜：50 个连接、总共不到 10 MiB 流量，一秒内把容器的 5 GiB 内存上限打满。

IIS / Envoy / ngtcp2 / nghttp3 / Google quiche不受影响，边解码边累加，做对了

"我用的不是这些库"这句话多半是错的。quic-go 是 Caddy、Traefik、cloudflared 的底层；lsquic 是 LiteSpeed Web Server 与 OpenLiteSpeed 的底层；Bun 的 HTTP/3 服务端也跑在 lsquic 上。你只要用了这些产品，就继承了它们底下那个库的问题。

临时缓解：Bun 不要把 HTTP/3 服务端暴露到公网；mitmproxy 启动加 --set http3=false；h3 crate 设一个合理的 max_field_section_size；通用兜底是给进程设 cgroup 或 systemd 的 MemoryMax 并在防火墙上对 UDP 443 限速——但这只是减轻，不是修复。

值得关注的原因：这是同一类错误的第七次、也是覆盖面最广的一次。FoxIO 在 7 月报过阿里 XQUIC 的 XRING（本刊 7-11 期已报，约 260 字节合规流量打崩服务端），两次命中的是同一个攻击面——QPACK 的表管理。这说明问题不在某个仓库的代码质量，而在"协议规定要按解压后的大小限流"这句话，实现者普遍只做了字面的一半。另外一点：HTTP/3 走 UDP，很多为 TCP 调的 L7 WAF 规则根本没机会看它，所以这条路对攻击者来说更"干净"。

5 高危

Node.js CVE-2026-111497（Node2Shell）：跑官方镜像就中，而且这个库是 Node 自带的

2026-10-21 发版修 10 个漏洞 · 10-22 Imperva 发布 PoC 与命名 Brotli 解码器越界写 · 4 枚高危 · 无在野利用报告

这件事的关键在于：出问题的不是应用代码，是运行时自带的那份 Google Brotli。Imperva 的 Ron Masas 发布的 PoC 在官方 node:24.22.0 的 Linux arm64 镜像上跑通了任意代码执行，同一份输入在 24.22.1 上被拒。

只要你解压了攻击者选的字节，就在攻击面上：直接调 node:zlib 的 Brotli 解压；fetch() 收到一个 Brotli 压缩的响应（这条最容易忽略——你没写解压代码，运行时替你解了）；Express 5.0.0 到 5.3.0 或 body-parser 2.0.0 到 2.3.0 解压请求体（裸 http 服务端默认不解压，这是唯一的好消息）。

机制据 Imperva 的描述：解码器在一个"流结构上本来不可能"的块切换处没有停下，反而把它当成"需要更多输入"，带着非法的内部状态继续跑，最终写出界。上游 Brotli 的修法就是——遇到这种情况直接返回格式错误。Node 的修复是从上游摘了那个提交。

分支修复版本
26.x26.12.1
24.x24.22.1（Imperva 用它验证 PoC 已被拦住）
22.x22.23.4
20.x 及更早不会有补丁，已 EOL，只能迁移

关于"能不能真的 RCE"，两种说法要分开记。Imperva 说在它自己的环境里执行成功，需要多次尝试，且只测了 Linux arm64 与自家应用配置。另一家测试的结果是：PoC 只在刻意削弱的测试构建上打通，标准构建上只看到崩溃和有限的内存读。Node 项目自己的措辞是"最坏情况可导致远程代码执行"。目前无在野利用报告。

另外三个高危不在 Brotli 上，而在 TLS 的地址判断上——同一个模式：CVE-2026-105483（IP 写成全角数字时证书主机名校验被绕过，26.x 与 24.x）、CVE-2026-106069（主机名解析为 IP 时绕过，三条线）、CVE-2026-106072（中危，证书里的 DNS 名可以给 IP 端点背书）、CVE-2026-105482（dns.resolve 遇到含 NUL 的名字会截断）。

一个模式说清楚：地址写成不常见的形式时没被认成 IP，校验就"掉"到了证书里的 DNS 名上，于是一张给域名签的证书，替一个 IP 端点做了担保。修法是让 TLS 拒绝非规范形式的 IP。还有一个中危值得单独提：CVE-2026-106074——用了启动快照或单文件可执行程序的应用，crypto.randomUUID() 与 randomInt() 背后的熵缓存被打进了快照，从那快照起的所有进程会重复同一批值。

动作：升级 22.23.4 / 24.22.1 / 26.12.1；容器镜像要重建并重启服务，光换二进制不算；跑在 20.x 上的计划迁移。

值得关注的原因：这已经是本月第三个"运行时或编译器自带组件"出事的案例（前两个是 PHP 的引擎、GitLab 的 Onigmo 正则编译器）。共同点是：它不在你的依赖清单里，你在 SBOM 里看不到它，但它在你的进程里。防守上要补的一课很具体——SBOM 要覆盖运行时的内置第三方库，否则"我们扫过依赖了"这句话根本不成立。

6 重点

CARLIY0S：一个犯罪团伙把 Claude、Grok、Kimi 编成流水线，瞄准 400 多家拉美金融机构

Straiker STAR Labs · 2026-10-21 发布 · 基于 PentAGI 开源自主攻击框架 无 CVE · 单方报告 · 受害方匿名 · 400 是目标数不是攻陷数

被追踪为 AiPT-67 的团伙（对外用 Tr4nsHack Team，前台公司 Hexagon Security Labs Mexico，与 2012 年起活动的 CyberCartel 有关）搭建了 CARLIY0S，几个月内把 400 多家拉美银行与支付机构列为目标。先把口径说准：400 是"目标数"不是"攻陷数"，且数字来自 Straiker 单方报告、未经第三方独立核实。

角色谁在干 / 干什么
决策层Claude Sonnet 与 Opus（四个角色）：评估攻击选项、就目标"辩论"、由指定仲裁者出最终决定
情报采集Grok（五个 miner）：收集目标信息，写进一个叫 FinancialSoft 的数据库

提示词包装加基础设施都是"正规军"打法：把任务描述成"授权安全测试"来影响模型响应；配浏览器自动化、流量检查、住宅代理；下一步动作由共享的知识图谱驱动。

FinancialSoft 那份 9-24 的快照，是这个案子最有说服力的物证——4,493 条记录：邮箱 2,911、金融账号 903、明文密码 67、门户登录 51、数据库连接串（含内嵌 SQL 账号密码）43、通用 API key 391、支付基础设施凭据 43（其中一家金融科技受害者的 11 个 API key 加 32 个加密密钥）、JWT 签名密钥 20、Keycloak 凭据 20、数字证书 4、Wasabi S3 19、Mailgun 15（可用官方发信基础设施做钓鱼）、明确的后门 6（主密码绕过、共享 root 与系统账号）、未公开漏洞 200+（2026-05 至 09，含零日，覆盖 Web、API、后端）。

那 20 个 JWT 签名密钥和 20 组 Keycloak 凭据，比密码危险一个量级：密码泄露要一个个用，签名密钥泄露可以批量伪造令牌；身份提供方凭据泄露，等于把发证机关搬走。而那 43 组支付基础设施凭据，Straiker 说与墨西哥 SPEI 银行间清算系统的滥用路径一致，也解释了调查里观察到的"哨兵交易"（小额试探性转账）。

供应商的响应：Anthropic 吊销了该团伙用来访问 Claude 的凭据，这条路被切断；xAI 收到通报后开始调查 Grok miner 相关活动。

值得关注的原因：这份报告的价值不在"犯罪团伙也用 AI"，而在它是从团伙自己的工作环境里取证的——配置、脚本、知识图谱、数据库全都拿到了，因此能看到编排而不只是"用了什么模型"。它给出的教训非常朴素：AI 压缩的是侦察、分析、协调这些人力密集的环节，它不生产凭据、不生产漏洞、也不生产访问权。这四百家机构被列进名单，靠的不是模型聪明，是有人先把 4,493 条真实凭据攒起来了。对防守方的动作因此也很朴素：轮换 API key 与凭据、收窄权限、盯住身份系统与支付链路的异常，然后把"我们有哪些 AI agent、它们能碰到什么"列成清单。

7. GMO 旗下 Onamae Desktop Cloud：26,739 台客户服务器被装马，全部套餐停机

9. Apache Kylin 一次修 14 个漏洞，三枚 9.3 全在"未认证"档

10-23 的安全公告汇总了 Apache Kylin 的 14 个漏洞，修复版本 5.0.5。三枚 CVSS 4.0 9.3 且全部无需任何权限：CVE-2026-64959 是后端缓存 API 的 SQL 注入（部分端点连认证都没有）；CVE-2026-68571 是 JDBC URL 白名单校验可被特殊参数绕过，从而注入并执行代码；CVE-2026-108743 是 Spark 作业处理里把输入拼进操作系统命令。另有 68573 与 108709（均 6.9）为认证缺失、108762（5.3）为路径穿越，可删元数据备份目录之外的文件。官方口径很关键：主要影响"直接暴露在公网"的部署，多数内网自建实例不受影响——换句话说，先把 Kylin 从公网摘下来，比抢在今晚打补丁更有效。这类"大数据分析平台"常年被当成内部工具，却经常带着默认口令和裸奔的 REST 端点挂在公网上。

10. Interpol「Serengeti III」：21 国、1,462 人被捕、10,909 个恶意网络被拆

行动期 2026-06-29 至 08-31，协调方 Interpol，参与国 21 个（含美国），10-22 公布结果：逮捕 1,462 人，捣毁 10,909 个恶意网络，追回超过 1.05 亿美元非法资金；已识别 65,929 名受害者，金融调查关联的损失超过 3.85 亿美元。重点案例：乌干达拆掉两个跨国诈骗团伙、逮捕 365 名外籍人员（用脚本话术与假交易平台骗亚洲的养老金人群）；安哥拉端掉两个非法加密货币矿场，抓 9 人、缴 2,000 多台矿机与 6 座非法变电站（光电力设施就值 100 万美元以上）；尼日利亚抓到一个大规模钓鱼与 BEC 操作者，囤了约 210 万个邮箱地址与软件凭据。这已经是 2024 年以来第三次 Serengeti。值得记的是它的形式：先由 20 个非洲国家加美国拿到"可疑域名、IP、C2 基础设施"的情报，再落地抓人——这是"基础设施情报共享"这条路径少见的、能算出成果的样本（合作方含 Group-IB、卡巴斯基、Fortinet、Team Cymru、Meta 等）。

11. Qilin 与 INC 的新战术：从"打个 VPN"升级到"直接打 vCenter 与 ESXi"

Unit 42 的威胁简报在 10-23 仍在更新，明确说依然观测到针对 CVE-2026-0257（PAN-OS GlobalProtect 认证绕过）的利用尝试。这条本身往期报过（10-12 与 10-21 期），今天新增的是战术位移：这两个团伙（Qilin 即 Spikey Scorpius、INC 即 Tarnished Scorpius，Unit 42 在 10-19 点名）已经从"拿一个看起来正常的 VPN 会话"走到直接攻击 VMware vCenter 与 ESXi——至少有一例是从域控制器的虚拟磁盘里把凭据刨出来的，这条路绕开了几乎所有端点防护；而加密一台 hypervisor，等于一次性放倒几十上百台虚拟机。一个必须说清的边界：Unit 42 自己只确认"尝试利用"，公开报道里的"已完成入侵"来自其他研究方，两边并不矛盾——它只看得到自己的客户与传感器。防守要点：把 VPN 会话当"正常远程办公"是这类攻击最难发现的地方；真正该盯的是 vCenter 与 ESXi 的凭据使用、快照与导出行为。

12. 「上下文炸弹」：给攻击型 AI agent 喂假情报，成功率能砍掉九成

安全公司 Tracebit 公开了一种纯防守的技术：在攻击型 AI agent 会爬取的地方埋"上下文炸弹"——伪造成渗透测试报告、无穷无尽的服务列表、层层嵌套的假密码、递归数据库等，让 agent 把诱饵当成高价值目标、把真系统当成陷阱。实测结果：组合多种炸弹时效果最强，让 Claude Opus 5 的成功率下降 91%、GPT-6 Astra 下降 54%，并把成功攻击的算力成本抬高到最高 23 倍；GPT 5.6 Cyber、Kimi K3、Qwen 3.8 Max、DeepSeek V4 Pro 这几个模型的攻击在测试中被完全阻断。最强的一颗单弹是"假的渗透测试报告"——它把真实路径标注为金丝雀、把诱饵标注为"已被拿下的战利品"。这条要跟今天第六条对着看：一边是犯罪团伙用多模型编排去放大攻击，另一边是用几十行假情报去给对手的 agent 加税。在攻防双方都开始用 agent 的阶段，"污染对方的输入"可能比"加固自己的输出"更便宜。
