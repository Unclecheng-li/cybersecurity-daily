AI 找出来的洞，修复那一栏是空的

Apache HTTP/2 那个 9.8，是 Anthropic 的扫描器在 10 月 26 日先报的，Google Cloud 的两位研究员在 11 月 3 日独立报了同一个问题，修复版等到 11 月 11 日才发。Fortinet 一天发 89 份公告、近 100 个漏洞，公告里自己写着"用了前沿 AI 模型"，同时说提前发是因为 AI 把从披露到攻击的窗口压短了。群晖一次修 27 条，最高那条 9.8 在登录接口上，公告明说没有变通方案；至于它到底是"读写任意文件"还是"零点击 RCE"，厂商和发现方各写一套。微软一年前给 CLFS 加的完整性校验，被一个没有 CVE 编号的 PoC 反过来用成了 SYSTEM 提权路径。有个产品三月就停止服务了，今天公开的三条 9.8 永远不会修，其中一条是写在代码里的后门密码。Red Hat Quay 里，你只要在命名空间名字里放一个下划线，就能捞到别人租户的机器人账号令牌。六条里两条明确写着发现者是 AI，两条写着修复版本不存在，三条的两份官方说法互相打架——这不是巧合，是同一件事的不同侧面。

没有请求体的那个请求，让两个线程拿到同一块内存

CVE-2026-119618 · 2.4.55–2.4.70 与 mod_h2 2.0.8–2.0.42 · CWE-362 · 修复版 2.4.71（11-11 发布） CVSS 3.1 9.8（Red Hat 评）· 无在野 · PoC 只到堆破坏

2026 年 11 月 11 日，Apache 发布 HTTP Server 2.4.71，修了三个漏洞。最重的那个在 mod_http2 里，Red Hat 给的向量是 AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H，9.8。

触发条件写得非常具体，具体到可以直接拿去写检测规则：一个没有请求体、带 Content-Type、但没有 Content-Length 的请求，在请求头表已经写满的时候到达。这种情况下，assign_headers() 里的工作线程会往共享的 stream 表里补写一个合成的 Content-Length: 0——而按 mod_http2 的设计，工作线程本来只用自己私有的分配器，共享的那个归连接线程。这一笔写下去，就和连接线程在无锁空闲链表上撞了车，两个线程可能拿到同一个内存节点。

堆被破坏之后能走到哪一步，各家的说法分层得很清楚：Apache 与 Red Hat 承认"可导致远程代码执行"；Red Hat 的公告说已公开的研究在标准的、启用了 mod_http2 的服务器配置上演示了可靠的攻击手法，但公告里既没有细节也没有引用；GitHub 上有一份 PoC 复现了内存破坏和 Apache 子进程崩溃；公开材料里还没有人演示任意代码执行。Wiz 在 11 月 11 日写分析时也说自己没看到完整的公开利用。

事项具体值
受影响Apache HTTP Server 2.4.55–2.4.70；独立 mod_h2 2.0.8–2.0.42，且 Protocols 里含 h2 或 h2c
不受影响只跑 HTTP/1.1 的服务器（Apache 默认就是 HTTP/1.1）；RHEL 6/7/8 不含该模块代码
同批修复CVE-2026-106023（mod_md 空指针解引用）、CVE-2026-109163（mod_vhost_alias 单字节栈溢出）
已发补丁RHEL 9：mod_http2-2.0.26-7.el9_9.1（RHSA-2026:98981）；RHEL 10：mod_http2-2.0.29-5.el10_3.1（RHSA-2026:98978）；Debian sid 2.4.71-1
未修Debian bookworm / trixie / forky 仍无修复；Amazon Linux 全部 pending；JBoss Core Services 与 Hardened Images 列出受影响但无修复
暴露面（Wiz）观察到的云环境里 64% 含受影响版本，51% 有对公网暴露的实例（不含"是否真的开了 HTTP/2"这一层）

发现过程本身是今天最值得记的一笔。Apache 的致谢名单里，第一个报告方是 Anthropic 的 OSS Scanner，10 月 26 日；第二个是 Google Cloud 漏洞研究团队的 Anthony Weems 与 Simon Scannell，11 月 3 日，独立报同一个问题。两个机构、相隔八天、互相不知道，最后指向同一行函数。

为什么 9.8 在 RHEL 上只有 Important。这条容易被误读成"Red Hat 在压分"。Red Hat 的说法是：RHEL 9 和 10 的 mod_http2 包给每个 HTTP/2 流单独分配内存，而这个漏洞依赖的是线程间共享的那块内存，所以利用难度实质变高——分数降到 Important 是结果，不是动机。判断这条对自家环境的风险，真正要回答的是三个问题：mod_http2 有没有加载、Protocols 里有没有 h2/h2c（包括每一个 VirtualHost）、以及你前面那层 CDN 或负载均衡是不是把 HTTP/2 终结掉了。第三种最容易被漏——浏览器走 HTTP/2，回源是 HTTP/1.1，你的 Apache 根本不走那条代码路径。AWS ALB 默认就是 HTTP/1.1 回源。

还有一个坑：已经为 CVE-2026-23918 升到 2.4.67 的服务器并不安全，2.4.67–2.4.70 全在这条的影响范围里。11 月 11 日之前构建的容器镜像，全都带着有问题的版本。

无请求体 带 Content-Type 不带 Content-Length 请求头表恰好已满 工作线程补写合成的 Content-Length 零 写进共享表 而不是私有分配器 与连接线程在无锁链表上竞争 两个线程拿到同一节点 堆被破坏 公开 PoC 到此为止 子进程崩溃

厂商写的是读写文件，研究员说的是零点击 RCE

Synology-SA-26:19 + SA-26:18 · 27 个 CVE（1 critical / 9 high / 17 medium）· 四个分支各有修复构建号 CVE-2026-76954 · 9.8 · 官方明写无变通方案

群晖在 11 月 10 日 17:06（UTC+8）发了两份公告，一共 27 条。最重的是 CVE-2026-76954，CWE-89，位置在 DSM 的 Auth API——也就是登录那条路上，CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H，9.8。

厂商原文的影响描述是：远程攻击者可以读取或写入任意文件，并造成拒绝服务。发现方是 Viettel Cyber Security 研究实验室的 Nguyễn Bá Nam Dũng（@greengrass19000）与 Hà Thế Long（@vcslab），他们对外把这条描述成预认证、零点击的远程代码执行。

这两句话不矛盾，但也不是同一句话。"读写任意文件"是可验证的行为，"零点击 RCE"是从这个行为推出来的结论——写文件写在能被执行的位置就是代码执行，写在别处就不是。NVD 记录里只有前者，后者是研究者的定性。写文案、做通报的时候要分清哪句有出处。

微软自己加的那道校验，成了提权的入口

SignDrop · 无 CVE 无公告无补丁 · PoC 11-10 19:20 UTC 上架 · Win11 26H2 / Server 2025 本地提权到 SYSTEM · 微软未确认 · 独立测试：能跑，但不够稳

11 月 10 日，微软发十一月补丁的那一天，研究者 Nightmare Eclipse（GitHub 账号 MSNightmare）在 19:20 UTC 建了个仓库，四个半小时后最后一次改动，23:53 UTC。仓库里是一个叫 SignDrop 的本地提权 PoC，和一个写得很细的说明。

它打的东西很有意思：不是漏洞，是微软一年前为了防漏洞加的那道校验。

2025 年 10 月的更新里，微软给 CLFS（通用日志文件系统）的日志文件加了 HMAC 认证——用日志数据和每台机器独有的密钥算校验码，驱动只解析自己写过校验码的日志。实现方式是每条日志旁边多一个 .cnpf 伴生文件，存恢复数据，创建时继承原日志的安全属性。SignDrop 打的就是这个"创建伴生文件"的动作。

流程是：普通用户在自己能控制的目录里准备一个 CLFS 日志和容器，用对象管理器符号链接把后续的创建动作指向别处，然后诱导一个特权进程去打开这份日志（公开代码里用的是 Defender，通过本地 RPC 的 ServerMpUpdateEngineSignature）。clfs.sys 这时会在特权进程的安全上下文里创建伴生文件，而文件继承的是那份原日志的 DACL——原日志是普通用户的——于是得到一个 SYSTEM 创建、但普通用户可写的文件，再接一步就链到 SYSTEM shell。

研究者的自我评价是那句最值得抄下来的话："微软这里每一步都做对了，是逻辑本身可以被滥用。"校验是真的、HMAC 是真的、继承 DACL 也是设计如此，问题在于"继承谁的 DACL"这件事，在一个由普通用户准备好、由 SYSTEM 打开的日志上，结论是可被利用的。

边界说清楚
性质本地提权。攻击者必须先在那台机器上跑代码，不能从外网打进来
生效范围注册表 HKLM\SYSTEM\CurrentControlSet\Services\CLFS\Authentication 下 Mode 为 0（强制）或 1（学习）；新系统从学习模式开始，90 天后自动转强制，所以装了很久的机器默认在范围内
别做的事不要为了躲它把缓解关掉。改成 2 或 3 会让 CLFS 重新解析任意日志文件，把这层保护本来要防的内存破坏漏洞全部放回来
独立验证只有一份：韩国 78researchlab 的 Heewon Song（PurpleHound）确认能跑通，但判断可靠性不足以实战；跑起来每个 UAC 弹窗会同时开出普通与 SYSTEM 两个 shell，机器前有人就会看出来
80% 这个数研究者自己的猜测，没有样本没有方法，别当数据用
厂商状态微软未确认、未分配 CVE、十一月更新里没有修；CISA KEV（版本 2026.11.10 / 1,779 条）里也没有

今天能做的两件事都不需要等补丁：查上面那个注册表值确认 Mode 是 0 还是 1；给"MsMpEng.exe 在 C:\Program Files\Common Files\microsoft shared\ink 下创建 hid.dll"这条加告警——这是公开 PoC 里普通用户变 SYSTEM 的那一步，也是目前最干净的检测点。顺带留意异常的 CLFS 错误码，比如 ERROR_LOG_METADATA_CORRUPT。

同一位研究者今年已经交过一串：4 月的 RoguePlanet（微软 6 月确认为 CVE-2026-50656，7 月修）、8 月的 ShieldBreak（CVE-2026-69414），其中三个 Defender 漏洞被实际利用过。他交的东西历来先在 GitHub 上放代码，再等厂商追认。

Red Hat Quay · CVE-2026-110697（9.9）+ CVE-2026-123710（9.8）· 均 Awaiting Analysis 一条要低权限 · 一条什么都不需要

同一天（11-11）Red Hat 放出两条 Quay 的，性质完全不同，但都能把镜像仓库翻个底朝天。

第一条：110697，9.9。机器人账号的列表函数把用户控制的命名空间名字直接拼进 SQL 的 LIKE 模式里，没有转义通配符。LIKE 里 _ 匹配任意单个字符，% 匹配任意串。攻击者只要把自己命名空间的名字里放一个下划线，那条查询就会匹配到别人租户的命名空间，把对方的机器人账号以及解密后的认证令牌一起返回。向量是 PR:L 但 S:C——低权限进来，影响跨出安全边界，所以分比 9.8 还高。

第二条：123710，9.8，PR:N。这条不需要任何账号：拿一个匿名 registry token，把 audience 设成自己控制的；把这个令牌提交给服务密钥轮换端点；Quay 接受，并允许安装攻击者的签名密钥且不带过期时间；接下来用自己私钥签一个任意仓库、任意权限的令牌，验证会通过——因为那正是它刚装上去的公钥。

为什么这条比 9.9 那条更该紧张。9.9 那条要一个账号；9.8 这条什么都不需要，而且拿到的是签发权——不是某一张令牌，是所有令牌的伪造能力。装进去的那把签名密钥没有过期时间，也就意味着"改密码、吊销令牌"这套常规处置动作对它无效。供应链场景下这最要命：你能换 tag，就能把别人 CI 里拉的那个镜像换成一个长得一样的东西。

Red Hat 的处置建议很短：把可能暴露过的机器人账号凭据、registry 凭据、签名密钥全部当成已泄露，然后核对 tag 与 digest 是否对得上、翻 token 签发记录里有没有陌生 IP 或 UA、看签名密钥轮换事件有没有不是自己做的。

7. ScreenConnect 六个 MSP 被打穿，恶意客户端反手劫持技术员工位

Huntress 在 11 月 11 日 17:47 UTC 首次检测到。入口是第三方扩展 RMM+ 1.0.31 / 1.0.32 的共享访问密钥为空时会被直接放行，绕过 ScreenConnect 自己的账号、角色和 MFA。进来之后用 Run Command 给客户终端批量装未授权客户端，再投一套叫 SCKit 的工具包，其中 RelayTrap 会在技术员连上去的一瞬间劫持他的工位、偷浏览器与 ScreenConnect 会话 cookie，然后顺着他的管理面横到所有他管的客户。数一下口径：6 家 MSP、47 家下游机构、286 个端点（另一份写 48 家 / 288 个 / 90 分钟内）。ConnectWise 已停用五个第三方扩展（Labtech Plus、RMM Plus、RMM+、RMM Plus Password Link、RMM+ Password Link），本地部署的客户要自己手动关。IOC：185.99.255.28（中继）、155.94.150.39、ns[.]mo7sen[.]dev。最实用的一条建议是反直觉的：别用 ScreenConnect 去连疑似中招的机器，因为它的传播路径就是会话本身。

9. eMudhra 再撤 8 张中间 CA，根因是一段自己写的 Python 脚本

11 月 11 日，这家证书机构公布调查结果：2025 年 4 月 30 日做 HSM 之间密钥迁移时，用脚本处理私钥。先披露的那 8 张 ECDSA 证书，私钥被脚本错误截断到只剩 1 字节——恢复成本几乎为零。这次新增撤销的 8 张 RSA 证书没有同样的弱化，但私钥曾被导入普通主机进程内存，无法证明符合 CA 密钥管理规范。8 张里 6 张用于 TLS 网站证书签发、2 张用于代码签名。这条的意义不在数量，在于它说明：HSM 保得住存储，保不住流程。

10. rubygem-safemode 9.6：沙箱白名单被"复合赋值"绕过

CVE-2026-107360，CWE-183（允许输入白名单过于宽松），AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:N。safemode 是 Ruby 的模板沙箱，靠 Jail 白名单拦截方法调用；复合赋值表达式在求值时没有经过 Jail 中介，于是能对暴露给模板渲染器的对象调用任意无参方法——包括删主机、读出不在白名单里的对象状态。Red Hat Satellite 6.16.15 / 6.17.13 / 6.18.11 已修（RHSA-2026:99949 / 99950 / 99952）。补丁前的临时办法只有一个：只让可信管理员编辑模板。

11. Citrix NetScaler 9.5，但没人说得清它是什么

CVE-2026-107412，CVSS 4.0 9.5，描述全文两句话："NetScaler ADC 与 NetScaler Gateway 存在多个内存溢出漏洞，可导致不可预测或错误的行为以及拒绝服务。"没有 CWE、没有版本范围、没有修复版本、没有向量明细（AT:P 攻击前提为"存在"）。vulnStatus 是 Received，CNA 是一串 UUID 而不是机构名。NetScaler 是边界设备，历史上出过 CitrixBleed 那种级别的东西，所以"9.5 但没细节"这件事本身要跟进——分数先到了，信息还没到。
